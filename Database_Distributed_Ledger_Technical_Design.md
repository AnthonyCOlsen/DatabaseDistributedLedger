## 1. Purpose and layer boundaries — CONFIRMED

Build a public-data, disaster-resilient, cryptographically authenticated distributed event ledger supporting an eventually consistent relational database on top. **The immutable ledger, not a relational database, is the authoritative data history.** The ledger may exist without a database. Only an **empty** database can initially adopt an existing ledger; it derives schema and data solely by consuming ledger events. Existing database SQL interfaces and SELECT/query facilities may be retained or compatibly extended, but there must be no supported direct SQL-to-official-storage mutation path: ordinary INSERT/UPDATE/DELETE or other supported user-managed data/schema changes submitted through any normal client connection must first produce authenticated ledger events; official storage changes only by ingesting ledger events. The implementation may use different internal components, but bypassing this invariant through an alternative SQL client, administrator-accessible supported interface, or unwrapped server endpoint is nonconforming.

An authorized master receives SQL write requests, evaluates them against the relational state it currently knows (or provisional transactional state), and publishes the resulting **concrete atomic changes** to the ledger before they are ever applied to official materialized storage. The same ledger consumer then applies locally produced blocks as it does remotely received blocks. A successful write acknowledgment can precede local SELECT visibility; client developers must accommodate stale reads. The database and application layers may implement stronger transactional protocols, but the underlying ledger neither promises global synchronous agreement nor interprets a client's business transaction as an atomic group.

**Every block is independent. No block references any predecessor, previous block, head, fork, or chain link.** “Blockchain” is a descriptive term for the authenticated historical collection and must not be interpreted as a hash-linked chain. There is no fork-choice election or dropping otherwise valid blocks to choose a preferred branch. A single logical order is calculated over the accepted blocks presently known to a participant.

## 2. Participation, identity, and authority — CONFIRMED

- **Ledger GUID:** immutable globally unique identifier shared by every block belonging to one ledger.
- **Block GUID:** immutable identifier of an individual block, independent of its ledger GUID.
- **Master:** participant holding an authorized Ed25519 private signing key and permitted to publish blocks and delegate master authority.
- **Read-only replica:** anyone may join, verify, retain, exchange, and materialize blocks without permission or a signing key. A replica may relay a block to a master even when their respective originating masters cannot directly communicate.
- **Entity GUIDs:** every table, column, and row has its own immutable GUID, independent of SQL-visible names or declared keys. Names may change without changing identity. A deleted GUID cannot be reused; recreating a same-name entity uses a new GUID.
- **Genesis master:** initial sole signing authority established by the special genesis block; other masters are added with ledger events.

**Grant — CONFIRMED:** Any currently authorized master may issue a `GRANT_MASTER` event identifying a public key. A valid grant sets that key's authorization state to **authorized** at the grant's canonical position. Grants do not stack into separately surviving permissions: a redundant grant to an already authorized key is permitted but does not protect it from a subsequent valid revocation. A later valid grant can re-authorize a previously revoked key; no grant retroactively validates earlier blocks.

**Revocation — CONFIRMED:** A `REVOKE_MASTER` event must be approved by **the master being revoked and one other distinct currently authorized master**, in either order. One provides the ordinary Ed25519 outer block signature and the other provides a countersignature inside the payload. The target's original grantor has no special role. At the event's canonical position, a valid revocation sets the **target public key** to unauthorized as a whole, not merely one grant instance. Subsequent blocks signed by that key remain in retained history but have no materialized effect unless a later valid grant restores authorization prospectively. The two-distinct-authorized-signers condition prevents revoking the sole remaining authorized master. A lost final private key is an operational catastrophe, not an exception to this rule.

**Canonical authorization replay — CONFIRMED:** Process grants, revocations, and other events in the total block order defined in Section 4, irrespective of receipt order. A block is applicable only when its signer is authorized at that canonical position. Late-arriving earlier history can invalidate or revalidate dependent grants and projected effects; re-evaluate those consequences without erasing retained block bytes. A previously accepted block is not guaranteed permanently applicable when missing earlier history later arrives. No separate independent grant-lineage model or grant-block-specific revocation is used.

**CONFIRMED:** The `REVOKE_MASTER` payload field order is fixed in Section 6.3. A block identity is the pair (`ledger_guid`, `block_guid`). Repeated identical serialized blocks are idempotent duplicates, not new events. If different serialized bytes claim the same block identity, **neither variant may be chosen by first-arrival order or applied while that identity is disputed**; quarantine conflicting variants for explicit diagnosis. If one variant was already projected before the conflict became known, the official projection must be reconciled to remove effects that are no longer unambiguously applicable; immutable received bytes are retained. Use a full-block SHA-512 digest to detect byte-level differences. Blocks awaiting missing earlier authorization evidence must be retained as **pending**, without materialized effects, and reconsidered/requested again when relevant evidence becomes available. **CONFIRMED Version 1 disposition:** Retain and quarantine both conflicting authenticated variants; neither may be selected by arrival order or arbitrarily overridden. If either was previously projected, reconcile its affected effects out of the unambiguous official projection. A later separately approved, authenticated protocol extension would be necessary to establish a different winner rule. Expose stable statuses `applied`, `pending`, `quarantined`, `opaque`, and `rejected` with machine-readable reason identifiers; exact CLI/JSON field shapes are defined separately. The older proposal to sign only the reusable fixed phrase `I AGREE` is **not approved**. There is no additional Version 1 key-compromise recovery mechanism beyond these ordinary signature/authority rules.

## 3. Genesis and database initialization — CONFIRMED

On creation, each **empty** database must choose one of two paths:

- **Create a new ledger:** generate a new ledger GUID and initialize with a supplied or freshly generated Ed25519 keypair under the adapter contract, publish a valid self-signed genesis block, and establish the first master authority through authenticated genesis and binding. Merely installing or selecting that key never grants authority.
- **Join an existing ledger:** select an **existing local ledger** identified by its ledger GUID. Adopt its already-established genesis authority and reconstruct the database solely by replaying authenticated ledger events. A populated unrelated database cannot join.

**CONFIRMED:** A genesis block uses the same fixed binary envelope as other blocks but has an **empty payload** (`payload_size=0`, compression `0x00`, SHA-512 of the empty bytes). Its outer Ed25519 signature is verified against the public key in the header, which becomes the initial authorized master key. Ordinary non-genesis blocks may not claim genesis status merely by being self-signed.

**CONFIRMED trust safeguard:** When joining, pin both `ledger_guid` and the **SHA-512 fingerprint of its unique genesis block**, rather than trusting any self-signed block that claims the same GUID. If conflicting genesis blocks claim an identical ledger GUID, do not silently choose one. A ledger GUID identifies the intended chain, but alone does not cryptographically prove that a particular genesis is the user's intended one.

**CONFIRMED Version 1:** The block header `version` is the big-endian unsigned 16-bit value `1` (`0x0001`), including for genesis. Genesis uses the exact standard 211-byte envelope with empty payload and its normal self-signature. Its fingerprint is `SHA-512` of the **entire serialized 211-byte genesis block**, including the outer signature. Only one pinned genesis is accepted for a ledger identity. An incoming genesis candidate with the same ledger GUID but a different full-block fingerprint is rejected as belonging to the wrong ledger, not silently merged. An unknown later protocol version may be safely retained as an opaque, unapplied record, but must not change the Version 1 projection. **CONFIRMED:** The management interface provides `ledgerctl init` and `ledgerctl join` with required ledger GUID and pinned full-genesis fingerprint when joining; expose structured identity-mismatch diagnostics. Safe storage of unknown future-version records as `opaque` never gives them Version 1 materialized effects. Exact operational flags and JSON schemas belong in the separate management API specification.

## 4. Canonical chronological order and clocks — CONFIRMED

Accepted blocks are ordered by the tuple `(timestamp_utc_ms, signer_public_key, block_guid)` ascending. Timestamps are signed 64-bit integers representing **milliseconds since 1970-01-01T00:00:00Z**. Compare public keys using their **raw 32-byte Ed25519 encoding** as unsigned lexicographic bytes, not textual Base64. Compare block GUIDs using their canonical 16-byte binary representation. Masters should synchronize clocks frequently against an agreed trustworthy UTC reference, preferably atomic-clock-backed. A signer should not intentionally issue more than one block in a millisecond; if needed, advance to the next millisecond. The block GUID serves as a tertiary tie-break if collisions occur anyway.

No block is rejected solely for its timestamp appearing far in the future or past. A block with an incorrect clock is processed according to its declared signed timestamp, **subject to authorization at that canonical position**. Arrival order never defines canonical order. There is no general guarantee that a participant knows all earlier blocks; late earlier blocks may revise derived state.

**CONFIRMED tie behavior:** Equal-millisecond timestamps, including authority operations, are resolved by raw signer public key, then raw block GUID as specified above; they are not ordered by arrival or by block GUID before signer public key. **CONFIRMED 2026-10-22:** SQL leap-second literal inputs with seconds field `:60` are rejected, not normalized by local clock rules. Operational time synchronization methods remain implementation choices. No clock-skew quarantine is required.

## 5. Custom binary block wire format — CONFIRMED

Blocks are raw binary, not JSON, Base64, CBOR, or serialized SQL. The layout is packed, with no alignment padding. Multibyte integers use **big-endian** byte order and GUIDs use canonical RFC 9562 byte ordering. Fields are laid out sequentially:

| Field | Encoding | Bytes | Zero-based offset |
|---|---|---:|---|
| `version` | unsigned 16-bit | 2 | 0–1 |
| `ledger_guid` | UUID binary | 16 | 2–17 |
| `block_guid` | UUID binary | 16 | 18–33 |
| `timestamp_utc_ms` | signed 64-bit epoch milliseconds | 8 | 34–41 |
| `signer_public_key` | Ed25519 raw public key | 32 | 42–73 |
| `payload_sha512` | raw SHA-512 digest | 64 | 74–137 |
| `payload_size` | unsigned 64-bit byte count | 8 | 138–145 |
| `payload_compression_type` | unsigned 8-bit | 1 | 146 |
| `payload` | transmitted raw payload bytes | N | 147 through 146+N |
| `signature` | Ed25519 signature | 64 | 147+N through 210+N |

The header length is **147 bytes**; the signature is **64 bytes**; each entire block is **211 + N bytes**, with `N = payload_size`. `version` uses 2 bytes, and `payload_size` uses 8 bytes, permitting values beyond 4 GiB subject to practical resource restrictions. The payload field is not Base64 encoded. 

**Hash:** `payload_sha512 = SHA-512(exact transmitted payload bytes)`; this includes any internal compression properties within those bytes. **Signature:** Ed25519 signs the complete exact serialized block bytes from `version` through the last byte of `payload`, excluding the trailing 64-byte signature. The verified signature authenticates header, timestamp, signer's public key, compression method, payload length, hash, and payload. Ed25519 is a signature scheme, **not symmetric encryption**; the data are public. AES-256-CBC is not used to authenticate blocks.

**Compression type — CONFIRMED:** `0x00` = uncompressed raw event payload; `0x01` = **raw LZMA2** compressed event payload, not a `.7z` archive or Base64. For `0x01`, the first byte **inside `payload`** is the LZMA2 decoder-property byte `p`, followed by the raw compressed stream; the property byte is included in `payload_size` and in the transmitted-payload SHA-512. Version 1 encoding uses **`p=20`, a 4 MiB dictionary**. Other dictionary properties are reserved for future protocol versions. Decoding must require the LZMA2 end-of-stream marker and reject trailing garbage. The signature and SHA-512 digest are checked over transmitted bytes before decompression. Other compression type IDs are reserved. Compression is optional for small events.

**CONFIRMED safety/resource policy:** Implementations must provide **configurable** input-size, decoded-size, CPU/time, memory, and decompression limits. No arbitrary small universal maximum is imposed merely because the outer payload length is 64-bit. Apply bounded incremental processing or reject safely before exhausting resources. Malformed blocks, failed hash/signature checks, unknown event kinds, unknown future versions, and unverifiable authority must never mutate official materialization. An implementation may retain such bytes for diagnostics or later dependency recovery with clear status; this does not authorize their application. **CONFIRMED 2026-10-22:** Oversized, malformed, incorrectly authenticated, unknown-version or unsupported event bodies never change official storage. An unknown future-version block may be retained safely as opaque, unapplied data with status; missing required authorization or schema evidence is pending rather than a permanent rejection. Resource-limit violations produce bounded, structured errors, not uncontrolled memory growth. The implementation must expose configurable maximum raw-block bytes, maximum decompressed-event bytes, and in-flight import-memory limits, plus practical processing/time/CPU limits. **CONFIRMED Version 1 operational defaults (all configurable; not protocol-wide maxima):** maximum raw received block 16 MiB, maximum decompressed event payload 64 MiB, maximum in-flight import memory 128 MiB, and per-block processing timeout 60 seconds. Limits must be enforced safely without uncontrolled memory/CPU allocation; timeouts and limit violations return structured diagnostics and never cause unauthenticated storage effects. Peer connections and resource usage must also be bounded. The exact configuration option names and minimum supportable values are documented in the accompanying management API contract.

## 6. Binary event payloads — CONFIRMED Version 1 event encodings

Each non-genesis block normally describes one independently meaningful **typed ledger event**, not arbitrary source SQL text. The master evaluates SQL using its currently known local database state and captures the resulting change. For row DML, the smallest atomic event is **one changed row per block**. A statement modifying 100 rows therefore emits up to 100 independent blocks. Zero rows affected means **zero change blocks**. Multi-row and multi-statement operations are not an all-or-nothing ledger unit.

Row events need to represent `INSERT_ROW`, `UPDATE_ROW`, and `DELETE_ROW`, using the **row GUID and table GUID** as their identity. **UPDATE_ROW records only the columns actually changed**, each identified by **column GUID**, together with its resulting value; it does not replace unrelated fields of the row. SQL-visible table and column names are not used as persistent identity or as the normal lookup keys in ledger row changes. Insert events must provide enough values/identities to build the row. An update that refers to a column renamed elsewhere still operates on its GUID.

DDL/administrative changes use the Version 1 events enumerated in Section 6.1: `CREATE_TABLE`, `DROP_TABLE`, `RENAME_TABLE`, `ADD_COLUMN`, `DROP_COLUMN`, `RENAME_COLUMN`, `ALTER_COLUMN`, `GRANT_MASTER`, and `REVOKE_MASTER`. SQL `ALTER TABLE` and column creation/modification use that event vocabulary; `ALTER_TABLE` and `CREATE_COLUMN` are not additional Version 1 event codes. The ledger must reconstruct both schema and data. The originator prefers one smallest practical atomic change per block; row changes must be one-row atomic.

### 6.1 Compact payload grammar — CONFIRMED Version 1 event codes and payload fields

**CONFIRMED:** A block’s uncompressed event body is binary, not SQL; row UPDATE events identify only the columns actually changed by GUID. **CONFIRMED:** Put a `uint8 event_kind` first in every non-genesis uncompressed event body. The chosen outer compression method compresses this *entire event body*; it does not change the body schema.

| Event code | Version 1 event | Uncompressed body after the one-byte code |
|---|---|---|
| `0x01` | `INSERT_ROW` | `table_guid[16]`, `row_guid[16]`, `column_count[varuint]`, repeated `(column_guid[16], typed_value)` |
| `0x02` | `UPDATE_ROW` | Same identifiers and repeated **changed columns only**; no implicit changes to other columns |
| `0x03` | `DELETE_ROW` | `table_guid[16]`, `row_guid[16]` |
| `0x10` | `CREATE_TABLE` | `table_guid[16]`, length-prefixed table name, `column_count[varuint]`, then full column definitions (Section 6.2.2) in declared order |
| `0x11` | `DROP_TABLE` | `table_guid[16]` |
| `0x12` | `RENAME_TABLE` | `table_guid[16]`, new name |
| `0x13` | `ADD_COLUMN` | `table_guid[16]`, complete column definition (including `column_guid`) from Section 6.2.2 |
| `0x14` | `DROP_COLUMN` | `table_guid[16]`, `column_guid[16]` |
| `0x15` | `RENAME_COLUMN` | `table_guid[16]`, `column_guid[16]`, new name |
| `0x16` | `ALTER_COLUMN` | `table_guid[16]`, complete **resulting** column definition (including unchanged `column_guid`) from Section 6.2.2 |
| `0x20` | `GRANT_MASTER` | `grantee_public_key[32]`; authorization is a per-key state, not separate grant instances |
| `0x21` | `REVOKE_MASTER` | `revoked_public_key[32] || countersigner_public_key[32] || countersignature[64]` (Section 6.3) |

`varuint` is **minimal-length unsigned base-128 variable-length integer** (ULEB128; no redundant leading encodings). Length-prefixed text is `varuint byte_length || UTF-8 bytes` (no zero terminator). Length-prefixed BLOB is analogous. Raw GUIDs are 16 bytes in canonical UUID ordering. To prevent multiple valid byte encodings of the same logical row mutation, sort its changed-column entries by ascending raw `column_guid` and reject repeated column GUIDs within an event. This payload encoding does not automatically standardize SQLite/other-engine expression evaluation.

### 6.2 Binary value types and NULL semantics — CONFIRMED Version 1 encoding

**CONFIRMED:** Version 1 supports the eight non-NULL wire types below plus the explicit NULL value tag `0x00`; all nine existing tag encodings remain unchanged. The outer block uses raw binary; values appear within the uncompressed typed event body (before any optional LZMA2 compression). All row changes use table, row and column GUIDs as identity. The Version 1 encodings of `DECIMAL`, `DATETIME`, and column nullability flags below are **CONFIRMED** by the originator (2026-10-21).

| Tag | Value type | Approved value bytes following tag |
|---|---|---|
| `0x00` | `NULL` | **Zero bytes.** Tag alone encodes explicit NULL. |
| `0x01` | `INTEGER` | Signed 64-bit logical range, ZigZag-encoded minimal ULEB128 (1–10 bytes) |
| `0x02` | `FLOAT` | IEEE-754 binary64, 8-byte big-endian |
| `0x03` | `TEXT` | Minimal ULEB128 byte length followed by UTF-8 bytes |
| `0x04` | `BLOB` | Minimal ULEB128 byte length followed by raw bytes |
| `0x05` | `DECIMAL` | ZigZag ULEB128 signed **scale**, then ZigZag ULEB128 arbitrary-precision signed **coefficient** |
| `0x06` | `DATETIME` | Signed 64-bit big-endian UTC Unix **epoch milliseconds** (8 bytes) |
| `0x07` | `BOOLEAN` | 1 byte: `0x00` false; `0x01` true |
| `0x08` | `GUID` / UUID | 16 bytes, RFC 9562 network byte order |

#### 6.2.1 Explicit NULL versus omitted column — CONFIRMED

Each `INSERT_ROW` or `UPDATE_ROW` encodes a minimal unsigned `column_count` of **zero, one or more**, followed by exactly that many entries sorted by raw `column_guid`: `column_guid[16] || value_type[1] || value_bytes[0..N]`. All identity references use GUIDs, not SQL-visible names. A duplicate column GUID inside one event is malformed.

- **UPDATE with a column omitted:** leave that column unchanged. Omission is NOT a NULL assignment.
- **UPDATE with a column present and type `0x00`:** explicitly assign NULL, with no additional value bytes. Example: `UPDATE Customers SET MiddleName = NULL WHERE CustomerID = 123` becomes an `UPDATE_ROW` event targeting the row GUID and the `MiddleName` column GUID with value type `0x00`.
- **INSERT with a column omitted:** its value is implicitly NULL under the current base rule, subject to separately defined schema defaults or nonnullable-column correction policy. INSERT events **omit NULL-valued columns**, including explicitly supplied SQL NULLs.
- An INSERT with `column_count = 0` is valid and creates the row identity with no supplied non-NULL columns. An UPDATE with `column_count = 0` is a legal no-effect event shape; a SQL UPDATE that changes no column values does **not** need to publish a no-effect mutation block. Ordinary SQL affected-row counts may still count matched rows even when no change block is created. **CONFIRMED default behavior:** During supported local SQL `INSERT`, omission of a column with a supported declared typed-constant default causes the originating master to evaluate that default **before block publication** and include its resulting non-NULL value in the signed INSERT block. Explicit SQL NULL does **not** invoke a default. Omission without a declared default resolves to NULL and is omitted from the INSERT block. Every receiving node consumes the transmitted resulting values and does not re-evaluate SQL defaults on replay. `UPDATE ... SET column = DEFAULT` likewise records the locally evaluated resulting value, including explicit NULL where appropriate.

**Concrete uncompressed explicit-NULL update example (51 bytes):** `event_kind 0x02` (1 byte) || `table_guid` (16) || `row_guid` (16) || `column_count 0x01` (1) || `column_guid` (16) || `value_type 0x00` (1). The signed outer block size for this uncompressed example is 211 + 51 = **262 bytes**. No bytes follow the NULL tag.

#### 6.2.2 Column definition grammar — CONFIRMED Version 1

**CONFIRMED by the originator on 2026-10-22:** Each complete Version 1 column definition uses the following ordered binary fields, with no separators or padding:

`column_guid[16] || name_length[varuint] || name_utf8 || declared_type_tag[1] || column_flags[1] || type_parameters || default_presence[1] || optional_typed_default`.

- `column_guid` is the immutable 16-byte identity; `name_length` is minimal ULEB128 counting UTF-8 bytes.
- `declared_type_tag` is one of the non-NULL value type tags `0x01` through `0x08` (INTEGER, FLOAT, TEXT, BLOB, DECIMAL, DATETIME, BOOLEAN, GUID). `NULL` (`0x00`) is a value marker, not a declared column type.
- `column_flags` bit 0 equals `1` for nullable, `0` for NOT NULL. Other bits are reserved and MUST be zero for Version 1.
- For DECIMAL (`0x05`), `type_parameters` are `precision[varuint] || scale[ZigZag-ULEB128]`, with `precision=0` meaning unrestricted. Other eight-type-list parameters are absent for the Version 1 base declarations, unless an explicitly revised wire version later defines them.
- `default_presence` is the single byte `0x00` for no declared default or `0x01` for a typed constant default (including an explicitly typed NULL); with `0x01`, `optional_typed_default` is `value_type[1] || value_bytes` using Section 6.2 values. Unknown presence/flag bytes are malformed for Version 1.
- `CREATE_TABLE` contains `column_count[varuint]` then all complete column definitions **in declared order**. `ADD_COLUMN` transmits one full definition. `ALTER_COLUMN` transmits the complete resulting definition with the existing column GUID; it does not use ambiguous partial attribute masks. Existing row event column-value entries remain ordered by raw column GUID.

**CONFIRMED 2026-10-22 — SQL defaults:** Version 1 supports typed **constant** schema defaults, including numeric, text, boolean, GUID, datetime and NULL constants that have a valid typed encoding. Default expressions requiring function calls, randomness, current time, sequence allocation or other computed/volatile evaluation are **unsupported** in Version 1 unless explicitly added in a later approved extension; reject their declarations, do not silently approximate them. Defaults are evaluated once at the originating master into concrete row values, as detailed in Section 6.2.1. **CONFIRMED 2026-10-22:** Supported typed literal defaults and lossless conversions must yield exact portable typed values; declarations depending on unsupported expression evaluation fail explicitly. DECLARED DECIMAL precision/scale must not cause silent rounding or truncation. The accompanying PostgreSQL SQL compatibility and execution contracts define the required literal/cast subset, exact DECIMAL limits, collation, metadata boundary and error-code mappings; additional advanced forms remain explicitly unspecified.

**CONFIRMED policy:** Version 1 does not reject an otherwise authenticated and authorized block solely for violating application-level NOT NULL metadata. If a deterministic declared typed-constant default is applicable, an authorized master may publish its resulting value in a **separate signed UPDATE_ROW correction block**; otherwise, a master must choose and explicitly publish a valid corrective value. **Never invent `0`, empty text, epoch zero, or any other arbitrary datatype fallback merely because it fits a column.** All nodes, including the originating master, consume the correction through normal authenticated ledger ingestion. Proposing, signing, publishing or durably retaining the corrective block alone does not resolve the affected official value. The correction becomes official only when the applicable authenticated event is ingested and applied to the materialized database; until then the inconsistency remains unresolved. A read-only replica may apply that authenticated history but cannot independently originate a corrective block. No automatic logical correction may directly modify official database values or schema, and ordinary replay never echoes a new event merely because it applies an existing one. Duplicate corrections from independent masters remain permissible. Until an applicable authenticated correction block is ingested and applied, any unresolved NULL remains a recorded/visible inconsistency or pending projection condition rather than an invented historical block. Exact PostgreSQL handling of unresolved incompatible or NULL values and error/diagnostic codes is defined in the accompanying execution and SQL contracts; normal declared constant-default evaluation is defined above.

#### 6.2.3 Canonical DECIMAL — approved binary encoding

A decimal represents the exact number `coefficient × 10^(−scale)`, with signed arbitrary-precision integer **coefficient** and signed integer **scale**, stored in that order as `signed_scale[ZigZag-ULEB128] || signed_coefficient[ZigZag-ULEB128]`. For each signed integer `n`, ZigZag maps nonnegative `n` to `2n`, negative `n` to `−2n−1`, and the result uses minimal, little-endian-base-128 ULEB128 bytes. No floating-point conversion occurs.

Canonicalize numeric values: if coefficient is zero, encode `(scale=0, coefficient=0)`; otherwise divide out all factors of 10 from the coefficient and decrement scale accordingly. Thus `12.3400` is `(scale=2, coefficient=1234)`, while `1000` can be `(scale=−3, coefficient=1)`. Declared column precision/scale, if any, are separate **schema attributes**, not inferred from the canonical value. This preserves exact numeric meaning, but not redundant textual trailing zeros; SQL formatting can use declared schema scale. Implementations must preserve the approved canonical exact-number representation and reject implicit conversion that would round or truncate. Configurable resource bounds apply to very large integer/decimal values. Required explicit cast combinations and DECIMAL declared-limit diagnostics are defined by the accompanying SQL compatibility and execution contracts, without silent rounding; exact-artifact approval is recorded separately against file hashes.

#### 6.2.4 Canonical DATETIME — approved binary encoding

Encode a DATETIME **instant** as an 8-byte, signed, big-endian count of **milliseconds since 1970-01-01T00:00:00.000Z** (UTC). Dates before the epoch use negative values. Time-zone-aware input values are normalized to UTC by the originating master **before** emitting the block; other nodes never reinterpret that instant using their local time zones. This preserves precision to milliseconds but does not retain the originally written time-zone offset. If an application requires original offset or local wall-time representation, it can store additional fields (or TEXT). **CONFIRMED 2026-10-22:** Interpret timezone-naive SQL DATETIME inputs as UTC and reject inputs with unrepresentable submillisecond precision rather than silently rounding. **CONFIRMED:** SQL input containing a leap-second field `:60` is rejected; nonrepresentable submillisecond input is rejected. The accompanying SQL compatibility and execution contracts define required SQL timezone aliases and error mapping without changing this 8-byte epoch-millisecond encoding.

#### 6.2.5 Type edge-case policy — CONFIRMED principles; adapter conversion matrix specified separately

**CONFIRMED 2026-10-22:** Reject `NaN`, positive infinity and negative infinity in FLOAT input; normalize IEEE-754 negative zero (`-0.0`) to positive zero (`+0.0`) in the canonical FLOAT encoding. Preserve valid UTF-8 text exactly; do **not** perform implicit Unicode normalization (NFC/NFD/etc.). Do not silently apply lossy type conversions; reject a conversion unless it is explicitly requested under a supported and documented conversion rule. DECIMAL remains exact with no implicit FLOAT intermediary, and DATETIME follows Section 6.2.4. **CONFIRMED 2026-10-22 — explicit and implicit conversions:** Origin-side supported deterministic SQL expressions produce concrete typed values before block creation. No implicit lossy cast may silently round or truncate. An explicitly requested cast may change representation only under a separately documented, supported deterministic conversion rule; until a conversion is specified it is not approved. **CONFIRMED 2026-10-22:** Lossless conversions are permitted; explicit casts may use documented deterministic conversion rules but may not silently exceed declared precision. Incoming non-finite/noncanonical Version 1 FLOAT encodings must not be applied as valid ordinary numeric changes. Leap-second text literals are rejected. **PostgreSQL interoperability boundary:** The accompanying SQL compatibility and execution contracts specify required SQL type-name/literal/cast mappings, exact conversion and precision/scale diagnostics, and the collation/metadata boundary. No implicit lossy narrowing or unencoded metadata guarantee is introduced.

### 6.3 Second signature on revocation — CONFIRMED Version 1 signed intent and payload

The outer `REVOKE_MASTER` block is signed by one currently authorized master. Its payload contains the **revoked target's 32-byte Ed25519 public key**, the **other consenting master's 32-byte Ed25519 public key**, and that countersigner's **64-byte Ed25519 signature**. The two signers must be distinct and currently authorized at the event's canonical position. **The target must be one of the two signers**, in either role. The target's original grantor has no special role. Revocation affects the target's authorization state as a whole, not an individual grant. There is no grant-block reference.

**CONFIRMED by the originator on 2026-10-22:** The countersigner signs the following exact **149-byte** message, formed by concatenating the fields without separators, length prefixes, or padding:

| Signed field | Length and encoding |
|---|---|
| ASCII literal `DDL-REVOKE-v1` | 13 bytes, exactly those case-sensitive ASCII characters, without a trailing NUL |
| `ledger_guid` | 16 raw bytes in canonical RFC 9562 UUID wire order |
| `block_guid` | 16 raw bytes in canonical RFC 9562 UUID wire order |
| `timestamp_utc_ms` | 8 bytes signed two's-complement integer, big-endian |
| `outer_signer_public_key` | 32 raw Ed25519 public-key bytes |
| `revoked_public_key` | 32 raw Ed25519 public-key bytes |
| `countersigner_public_key` | 32 raw Ed25519 public-key bytes |

The countersigner's signature is the 64-byte Ed25519 signature over these **exact 149 bytes**. It is computed first. The outer signer then signs the ordinary complete serialized block (from `version` through the transmitted payload), thereby authenticating the payload including the countersigner's public key and signature. A verifier independently verifies both signatures and the authorization state of both distinct participants in canonical order. A revocation whose target is not one of the two signers is invalid. This rule prevents the sole remaining authorized master from revoking itself. Late earlier authorization history requires re-evaluation rather than permanent rejection by receipt order.

**CONFIRMED by the originator on 2026-10-22:** The `REVOKE_MASTER` uncompressed event body is exactly `event_kind 0x21 || revoked_public_key[32] || countersigner_public_key[32] || countersignature[64]`. The complete uncompressed body is therefore **129 bytes**. The field order is fixed; the 149-byte signed-intent message above is unchanged. A compressed version, if used, compresses the entire 129-byte body using the ordinary outer compression convention.

## 7. Deterministic reconciliation and conflict semantics — CONFIRMED

A node retains all authenticated blocks it has received; it validates the signer **against canonical authorization history**, then derives the current schema and rows from applicable events in canonical order. **Later modifications win over earlier modifications to the same affected field** unless a deletion applies; **deletions always win for the same immutable entity GUID**, including after earlier or later updates. The same rule applies to rows, columns, and tables. A deleted row/table/column cannot be recreated with the same GUID.

A delayed update to a GUID for which its earlier INSERT has not yet arrived is retained and logged as temporarily inapplicable; it has no visible effect until the missing earlier INSERT is received and the entity can be reprojected. Operations that cannot yet be interpreted because schema blocks are missing are similarly logged and reconsidered after recovery of dependencies. **A valid block is never ignored or permanently excluded solely because it arrives late or has an earlier timestamp.** When an earlier block changes the canonical interpretation of materialized history, the node **must correct the official projection**: it may roll back/recompute affected rows, schema and dependencies, or rebuild its materialized database **from genesis and the retained relevant full ledger history**. Rebuilding from scratch is conforming, even if slower. Any partial/recovery representation must not pretend the late valid block never existed. A block with missing authority/schema dependencies can remain pending until its prerequisites are known; that is not permission to discard it because of age. Unrelated rows need not be rolled back when selective replay is proven safe. Immutable event history itself never rolls back; only the derived materialized database state can be corrected. A raw block may remain retained even where later validation makes it unauthorized/inapplicable; it must not affect the projection.

**No secondary events from normal replay; all logical corrections are ledger-first — CONFIRMED:** Applying or replaying an ordinary block does not publish another block merely as an echo. Only an authorized master may originate a separate signed corrective event for any ledger-derived logical inconsistency, including a name collision, disallowed NULL, incompatible value, datatype or schema inconsistency, or any other automatic logical data/schema repair. Every such correction, including one proposed by the local master, must first become authenticated ledger history and then be ingested and applied through the same normal ledger pipeline used for remotely received events. No automatic correction may directly alter official database data or schema. A proposed or durably retained correction is not yet official materialization: the affected state remains unresolved until its applicable authenticated correction is ingested and applied. A read-only replica may recognize, retain and diagnose an inconsistency and apply a master's authenticated corrective history; it must not independently originate corrective blocks, generate replacement identities/names/values for official state, or mask a problem with an unsigned change. This prohibition does not prevent required local replay or reconstruction that derives a projection from already-authenticated events. Physical storage maintenance and ordinary supported lossless interpretation of recorded values are not permission to invent a new logical repair. The ledger does not distinguish human-proposed from automatically proposed signed changes.

## 8. Schema identity, name collisions, and conversion — CONFIRMED

Every table and every column has an immutable GUID. RENAME_TABLE and RENAME_COLUMN preserve that GUID. Concurrent rename events targeting the same GUID settle by the latest valid canonical event, unless deletion applies. A dropped column supersedes updates targeting it. Recreating a same-name table or column uses a new GUID; deleted GUIDs cannot be reused.

If distinct entities are created under the same SQL-visible table name, or the same column name within one table, both entities survive. The entity introduced first in canonical **creation-block order** retains the original name. Entity-GUID numerical order and receipt order do not determine priority. An authorized master proposes a separate signed corrective rename for a later-created conflicting entity. The ordinary first correction spelling is exactly `original-name-entityGUIDwithoutdashes`, using the complete dashless entity GUID. Neither ordinary replay nor a read-only replica independently invents this rename.

**Identifier-length fallback — latest owner decision:** For the PostgreSQL adapter's 63-byte SQL identifier limit, measure the proposed corrected SQL-visible name in UTF-8 bytes. If the required corrected name would exceed 63 bytes, the authorized master generates a fresh random UUIDv4 unrelated to the entity GUID, ledger GUID and block GUID. Use that UUID's lowercase canonical hyphenated textual representation as the entire replacement name, rather than truncating the required name or its GUID suffix. The random replacement is a name value, not a replacement entity identity, ledger identity or block identity. Carry that exact name in a separate signed RENAME_TABLE or RENAME_COLUMN event identifying the original target entity GUID. SQL quoting does not change the byte limit. Other database adapters' identifier limits belong in their own public adapter contracts; this paragraph does not silently impose a new protocol-wide wire-name length or truncate received names.

The originating master must ingest and apply its own signed correction through normal authenticated ledger processing before that name becomes official. Proposing a rename, publishing it or durably retaining its block alone leaves the affected official name unresolved. The same rule applies to all automatic logical value/NULL/schema corrections. Until application, name resolution must not arbitrarily choose one GUID or discard either entity; the visible ambiguity or error is deterministic for the applied history. Replicas may apply authenticated corrective history but never independently originate a correction or substitute an unsigned name/value.

Signed automatic and user-initiated renames are ordinary rename events under the same canonical ordering, authorization, identity and delete-wins rules. Preserve all valid independently signed corrections. If masters propose different random replacement names for one entity, each event carries its own literal chosen name; the latest applicable canonical rename determines the resulting name for that GUID. Consumers and reconstruction never rerun random name generation. Participants with different known history may temporarily differ; participants with the same complete applicable history derive the same result. No requirement makes independent masters choose the same random UUID.

If a corrected name conflicts again, an authorized master must resolve the remaining conflict through another distinct signed rename, adding another newly generated GUID-based suffix as needed under the ordinary rule. If that proposed corrected name exceeds the PostgreSQL limit, apply the random-UUID fallback again. Random UUIDs do not guarantee a name is collision-free; a remaining collision is diagnosed and resolved by further valid signed history, not by an unsigned local edit or arbitrary winner. Canonical first-creator precedence and the latest valid explicit rename rules remain in force. Do not suppress earlier signed history, repeatedly emit identical corrections for unchanged known state, or create an uncontrolled replay-triggered correction cascade. Convergence describes replay of the same history, not a bound on the number of future independently proposed corrections.

On a column datatype change, apply only declared supported lossless conversions automatically. An incompatible value is retained/diagnosed unresolved, not silently replaced. If a nullable column may be corrected to NULL, a master may publish that explicit value in a separately signed row correction. Otherwise an authorized master explicitly selects a valid corrective value or applicable typed constant default and publishes it in a new signed UPDATE_ROW block. Never invent zero, empty text, epoch minimum or another arbitrary fallback. Every receiving node, including the origin, changes the official logical value only by authenticating, ingesting and applying that correction. Replicas wait for such signed history. Operational progress/diagnostics and failed reconstruction follow Section 10; exact interim SQL error conventions remain in the adapter contract.

For the PostgreSQL adapter, newly submitted SQL identifiers longer than 63 UTF-8 bytes are rejected rather than silently truncated. Authenticated historical names outside the adapter's representable range are retained and diagnosed without inventing an alternate name or changing identity. This input rule is distinct from the automatic-correction overflow fallback above.

## 9. SQL semantics, constraints, and transactions — CONFIRMED

Version 1 **does not enforce ordinary relational application constraints** such as primary-key uniqueness or foreign-key referential integrity when deriving authoritative changes. Two rows with different row GUIDs may contain identical business primary keys. Ledger deletions are not vetoed by referencing rows or application locks. Internal storage integrity and synchronization cannot be disabled merely to bypass these application-level rules. User-defined triggers, stored procedures, user-defined functions with effects, and comparable user-defined implicit write facilities are **not supported in Version 1**. This excludes their use as alternate mutation paths; it does **not** require removing SQL built-ins or internal database functions necessary for parsing, expression evaluation, data conversion, indexing, recovery, or supported SELECT/DML. The base Version 1 supported and excluded SQL subset is confirmed below; required PostgreSQL forms are defined in the accompanying SQL compatibility contract; advanced forms not specified there remain explicitly unspecified. Indexes and SELECT/query support may be used for efficient materialization and reads.

**CONFIRMED 2026-10-22 SQL scope:** Version 1 supports ordinary `SELECT`, `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `INSERT`, `UPDATE`, and `DELETE`, with `BEGIN`, `COMMIT`, `ROLLBACK`, and savepoints for provisional local staging. **Additional approved entry paths:** `COPY FROM STDIN` (bulk inserts), `COPY TO STDOUT` (read-only export), `MERGE` (its per-row insert/update/delete effects), and `RETURNING` (reports values from locally evaluated changes). Every resulting row change from `COPY` or `MERGE` must publish its own authenticated ledger block **before official materialization**; none may bypass the same authority rules. `RETURNING` reports locally calculated result values, which are **provisional with respect to later block publication and local projection visibility**. The caller may receive `RETURNING` rows before the corresponding signed block is durably published and before the official SELECT-visible projection catches up. This is an accepted application-design responsibility, not a requirement that the engine make RETURNING synchronously visible. `RETURNING` must not be represented as proof that a multi-block COMMIT is atomic or entirely durable, and statement results may precede later publication failures. `COPY FREEZE`, `COPY PROGRAM`, unsupported user-defined triggers, stored procedures, user-defined functions **with side effects**, and other unapproved mutation paths must be rejected or made unavailable rather than allowed to bypass ledger-authoritative changes. PostgreSQL internal built-ins necessary for supported SQL remain available. This is a baseline feature subset, not a promise to preserve unsupported SQL extensions or direct writes. The accompanying PostgreSQL SQL/execution contracts define required MERGE branches, expression/join/CTE forms, lossless type mappings, utility restrictions and result/error conventions; genuinely unspecified advanced SQL forms are identified there, without narrowing the approved command categories.

SQL clients can use provisional transactions. `BEGIN` starts uncommitted isolated changes; `ROLLBACK` and savepoint rollback discard staged work without emitting blocks. No publication occurs before COMMIT. At COMMIT publish final effective provisional row changes (Option A): an existing row changed 1 → 2 → 3 produces one UPDATE_ROW carrying 3; a row restored 1 → 2 → 1 needs no effective row-change block; INSERT then UPDATE produces one final INSERT_ROW; INSERT then DELETE has no surviving row event; UPDATE then DELETE produces one DELETE_ROW. Preserve PostgreSQL-compatible provisional RETURNING values and statement counts. Every independently effective changed row still requires its own signed block. DDL must preserve immutable entity identities, valid dependencies and reconstructible final state, without an arbitrary schema-event count or publication order; unpublished DDL folding is permitted rather than a mandated representation.

Publication is **not group-atomic**. If a crash leaves only 60 of 100 intended blocks durably published, those 60 are permanent ledger history; remaining blocks may never exist. The materialized official database is updated only by authenticated ledger ingestion, including at origin, not by the provisional transaction directly. If the origin can determine that COMMIT stopped after publishing only some intended blocks, it must report failure or explicit partial completion accurately, never claim atomic rollback of already durable blocks. Network disconnects may leave the client uncertain; they do not annul independently durable blocks. Resumable publication is optional, not a fundamental ledger requirement. Applications must handle missing/partial outcomes and stronger business atomicity at a higher layer; compensating operations create new blocks and do not erase history.

Ordinary offline master writes do not wait for cross-master acknowledgment. A higher-assurance application may implement independent locks/reservations and require all masters' confirmation, recognizing that such applications can block during partitions and still need a true protocol to prevent simultaneous conflicting reservations.

**CONFIRMED SQL outcome policy:** Preserve normal PostgreSQL command tags/affected-row counts for supported SQL, including matched-but-unchanged rows where applicable. A failed partial `COMMIT` must not return ordinary full success. When the origin can determine partial publication, report a distinct SQLSTATE `ZL001`, an explicit partially-published status, and the known durable block count and GUIDs; durable blocks remain ledger history. When the outcome cannot be determined due to connection loss, do not imply rollback; `08007` can be used where the server can report uncertain transaction resolution, otherwise the client must inspect durable ledger history. Previously emitted `RETURNING` values remain locally evaluated provisional information and do not imply publication or immediate SELECT visibility. Application software, not the ledger database, is responsible for business workflows that require immediate read-after-write visibility or all-or-nothing multi-block results. The accompanying execution/management/SQL contracts define PostgreSQL error fields, JSON DETAIL and supported expression/CTE/cast/error conventions. Request resumption remains optional; it is not required as an implicit retry guarantee. Explicit NULL-versus-omission semantics are now specified in Section 6.2. The initial system makes no promise that ordinary SQL semantics imply global transaction finality.

## 10. Materialization priority, durability, and recovery — CONFIRMED

A received valid block must enter persistent ledger storage before altering the official database. Master-originated blocks follow the same rule. Once received blocks are available, the database **pauses ordinary activity to process the blocks it already knows** and keep its local projection caught up; local precedence over throughput is intentional. This never implies certainty that no missing blocks exist on the wider network. A master can operate while other masters are offline, apart from local synchronization needed to apply known blocks.

Crash-safe progress tracking and idempotent replay or reconstruction must ensure a crash between block durability and materialization can be recovered without permanently omitting or double-applying effects. **CONFIRMED 2026-10-22:** Late valid historical blocks and later-revealed earlier authority history must cause the projection to be corrected through safe rollback/replay of affected materialization **or a complete rebuild from authenticated ledger history**; no timestamp-age cutoff may permanently suppress those corrections. Master/replica outage, out-of-order delivery, partitions, and late authority changes may all require selective re-projection. The ledger itself is immutable; the projection is replaceable. Acknowledgment of successful ledger append implies local durable storage; a block lost with all copies is unrecoverable.

**CONFIRMED 2026-10-22 — local read barrier versus remote catch-up:** An ordinary `SELECT` must **not wait merely because peers may still hold unknown blocks**, because network completeness cannot generally be established. A node may serve a consistent, locally materialized but network-stale state until more blocks become known. Once a node undertakes a local projection modification, selective rollback/replay, or full rebuild to incorporate **blocks it already knows**, ordinary `SELECT` operations requiring that projection must wait until the current local reconciliation produces a consistent result; they must not observe an intermediate or partially rebuilt official state. A complete rebuild **must create a persistent diagnostic/error-log entry** explaining why the rebuild was necessary, the affected ledger/database, its outcome, and information sufficient for an operator to investigate. The entry is operational evidence, not an authenticated ledger block. Implementers may choose locking/projection-swap mechanisms, but must not indefinitely block `SELECT` solely to await hypothetical unseen network blocks. **CONFIRMED operational projection reporting:** Expose projection states `ready`, `reconciling`, `rebuilding`, and `failed`. A full rebuild must persistently log ledger GUID, database identity, UTC start/end timestamps, reason, outcome, and error details when unsuccessful. If reconstruction fails, an affected SELECT must return a clear error rather than stale/inconsistent projected data. Under continuous block arrivals, a node must not starve SELECT indefinitely: it may reconcile a finite known batch to a consistent point, admit reads, and then incorporate later blocks. Implementation-specific WAL/cursor/checkpoint details remain free; exposed status must not claim an inconsistent projection is ready. Exact log encoding and error codes belong to operational API documentation. Rollback/replay versus full rebuild is an implementation choice; neither may ignore applicable earlier blocks.

## 11. Peer-to-peer propagation and offline exchange — CONFIRMED behavior and management interface

Every node may receive, verify, store, serve, relay, and export an intact block, regardless of whether it may originate blocks. Block validity is transport-independent. Permit direct peer connections (TCP/QUIC or suitable supported protocols), decentralized peer discovery with configurable bootstraps, BitTorrent-inspired DHT, peer exchange, LAN service discovery, NAT traversal and relaying, HTTP(S), multipeer downloads, and real-time announcements. Nodes normally advertise new validated blocks to peers with resource/bandwidth controls. **No peer discovery or master quorum is necessary for an ordinary local write**.

Combine rapid announcements with periodic cryptographic **inventory reconciliation**, including Merkle-style summaries or equivalent, and comparisons by block ID/hash that do not depend exclusively on timestamps. Export and import must include individual blocks, timestamp ranges, a full ledger, and incremental missing-block batches; large whole-ledger archives can be imported as offline batch jobs, from arbitrary media. The ledger does not require a database to exist; a returning master can catch up through a read-only replica.

**CONFIRMED 2026-10-22 — management API:** Preserve compatible existing database SQL/client communications, and provide a documented **`ledgerctl` command-line interface producing machine-readable JSON results** alongside normal PostgreSQL SQL connectivity. The interface must permit new-ledger initialization, joining/pinning by ledger GUID and genesis fingerprint, raw signed-block publication/import, exact raw-block retrieval, export of individual or selected/all blocks, peer configuration, and inspection of retained/pending/quarantined/applied/rebuild/synchronization status. Implementations may additionally offer SQL administration functions or other APIs, but must provide the standard test-facing `ledgerctl` surface. The **exact subcommand names, option names, byte inputs/outputs, JSON schemas, errors, and launch/configuration contract** are specified in the accompanying v0.4 management/execution contracts and JSON schemas, rather than inferred by the verifier. Blind verification requires separate owner approval of the exact artifacts. Detailed peer discovery, gossip, retries, routing, transport libraries/protocols and scheduling remain engineering freedoms, provided locally configured peers demonstrably exchange all relevant blocks during offline/local-network testing.

**CONFIRMED 2026-10-22 — block exchange:** Single-block export returns the **exact original signed block bytes** without reserialization. A multi-block export uses the **CONFIRMED Version 1 binary container**: ASCII magic `DDLB` (4 bytes) || version `0x0001` (uint16 big-endian) || block_count (uint64 big-endian) || exactly `block_count` repetitions of (serialized_block_length uint64 big-endian || exact raw signed block bytes), with no extra footer or trailing data. Every batch preserves each full signed block **byte-for-byte**, including all header fields, raw payload, SHA-512 digest and trailing 64-byte Ed25519 signature. The container is merely unsigned transport framing; it does not modify, re-encode, re-sign, replace, aggregate, or vouch for individual block signatures. Export ordering is deterministic canonical order, using the full-block SHA-512 digest as a tie-breaker for disputed same-identity variants; each block remains independently verifiable. Truncated or overlong framing must fail safely. A partially completed import may retain preceding independently validated/durable blocks; a batch is not an all-or-nothing transaction. Ledger block identity is (`ledger_guid`, `block_guid`); a full-block cryptographic digest distinguishes conflicting variants. Exact identical duplicates are idempotent. Different signed bytes with the same identity are **quarantined for diagnosis**, not resolved by first-arrival order. Unknown future protocol versions may be safely retained separately as opaque, **unapplied** records. Blocks awaiting missing prior authorization/schema history are retained pending/requested; malformed or inapplicable inputs never mutate official storage. Such cases receive machine-readable statuses. Resource limits remain configurable as defined in Section 5.

**CONFIRMED management surface:** The CLI supports an instance selector and operations equivalent to `ledgerctl <instance-selection> init`, `join --ledger-guid <UUID> --genesis-sha512 <HEX>`, `block import --input <file>`, `block export --output <file>`, `block get --id <UUID> --output <file>`, `block publish --input <file>`, `peer add --endpoint <address>`, `peer remove --endpoint <address>`, and `status` using a consistent per-instance selector. The `<instance-selection>` placeholder is engine-specific; `--pgdata <directory>` is an illustrative PostgreSQL adapter spelling rather than a database-independent requirement. Return a single JSON result envelope with fields `ok` (boolean), `data` (object or null), and `error` (object or null); raw signed bytes travel in files, not JSON strings. For this PostgreSQL candidate, stable input/error codes and complete return schemas are integrated in `Distributed_Ledger_Management_API_Specification.draft.md` and its schemas; exact-artifact approval is recorded separately against file hashes. Conflicting authenticated same-identity variants remain quarantined with **no arbitrary manual winner** in Version 1. Peer communications must be bounded and cryptographic authority must never be inferred merely from peer connection. Configured localhost peers must work in the offline test environment; no mandated public DHT/NAT/TLS library or discovery algorithm. TLS is optional for Version 1 deployment rather than a mandatory dependency on a particular library. Defaults are in Section 5.

**CONFIRMED block/ledger status vocabulary:** `applied` means verified and materialized into the current official projection; `pending` means retained with unsatisfied authorization/schema/repair dependencies; `quarantined` means competing authenticated signed bytes for the same (`ledger_guid`, `block_guid`) that cannot affect official state; `opaque` means safely retained, unknown-future-version content not applied under Version 1; `rejected` means framing, identity, signature, or semantic validation failed and no official effect is permitted. Identical bytewise duplicates are idempotent. Exposed counts and errors must use these statuses consistently.

**Flood resistance / inbound validation — CONFIRMED requirement:** Every node must inspect every received block for framing, protocol version, well-formedness, hash/signature integrity, ledger identity, and signer authorization before it has any database effect. A hostile actor may flood arbitrary invalid blocks. Reject invalid inputs safely and limit untrusted resource consumption (including decoding, disk, CPU, memory and networking) without treating plausible timestamps alone as grounds for rejecting otherwise valid authorized blocks. An out-of-order block whose missing authorization evidence has not arrived must not be materialized before its authority is established. Exact inventory, caching and DoS budgets remain implementation choices.

## 12. Intended guarantees and deliberate non-guarantees

**Intended:** Public cryptographic origin/integrity verification, signed historical authorization, deterministic canonical replay on the same accepted history, append-before-apply, one-row-per-block updates, delete-wins identity semantics, eventual convergence for participants that ultimately receive equivalent relevant events, permissionless block redistribution, complete reconstruction from validated genesis and all ledger history, independent progress during network partitions, and crash recovery for durably accepted events.

**Not promised:** Simultaneous SELECT visibility, knowledge of an objectively complete history at an arbitrary instant, automatic rollback of **ledger blocks**, all-or-nothing execution of multi-block SQL transactions, preservation of foreign-key/unique constraints, instant failover without surviving block copies, globally irreversible application business outcomes, and successful application-level strong locking when required masters are unreachable. **Required despite these non-guarantees:** correcting/rebuilding the derived database projection when an earlier valid block changes canonical materialization; retaining history and never suppressing an applicable block simply because it arrived late.

## 13. Acceptance scenarios (conceptual, not hidden verification details)

1. A new ledger initializes a genesis signer; an empty replica adopts the ledger and derives an identical state when fed the same history.
2. A grants B; B grants C; a late invalidation of B's grant invalidates C's dependent authority and relevant projected effects.
3. A signer key has no authority at a block position before its own grant; a later revocation invalidates subsequent blocks, not prior ones.
4. A and B publish independently while disconnected; a replica relays blocks to a disconnected master when peer links permit.
5. A block arrives late with an earlier timestamp; the node corrects affected materialization by selective rollback/replay **or complete rebuild from the validated ledger**, without treating the block as too old to apply.
6. Partial-column updates on the same row preserve separately modified columns; deletion of the row, table, or column GUID wins over modifications.
7. Same-name columns/tables with distinct GUIDs both survive; corrective naming blocks are produced by an authorized master, not by direct projection writes.
8. Duplicate primary-key values across distinct row GUIDs survive in Version 1.
9. `BEGIN`+`ROLLBACK` emits no blocks; partial failure during `COMMIT` can preserve only a published prefix of independently durable row blocks.
10. Crashes between ledger persistence and projection recover idempotently; replicas converge once their accepted block sets and authority histories agree.
11. Unsupported or temporarily uninterpretable blocks produce diagnostics, remain available for dependency recovery, and never silently mutate official storage through a bypass.

### 14.3 Implementation freedom and change control

This specification defines externally required ledger behavior. Implementers may choose internal memory/WAL/index layout, SQL interception mechanism, rollback or from-scratch projection rebuild, crash recovery strategy, peer transport/discovery, and administrative-interface implementation **within the accompanying callable contracts**. An implementation cannot satisfy the requirements merely by providing an optional wrapper that leaves a supported direct SQL-to-storage mutation bypass. No particular PostgreSQL internal routine or code change is prescribed in this database-engine-independent design.

**Change control:** Incorporate future owner approvals into their primary sections, removing contradicted OPEN statements rather than appending overriding requirements. Do not equate approval of a principle with approval of an otherwise unspecified byte grammar or hidden-verifier convention.
