## 1. Scope and supersession

This document replaces the **PostgreSQL 18.6-specific v0.4 management adapter** as the current working interface specification. The previous `--pgdata`, `initdb`, PostgreSQL socket/process, populated-cluster adoption and AI-verifier-specific provisions are **retired**; they are not required of the SQLite implementation. Retiring those adapter-specific obligations does not change Ed25519 signing, authenticated authority, `.BLK` exact-byte retention, `DDLB` transport, dispute policy or recovery guarantees defined in [Database_Distributed_Ledger_Technical_Design.md](Database_Distributed_Ledger_Technical_Design.md). **Separately, the Owner approved a breaking signed-wire 1.01 value/schema grammar and amended the canonical ordering rule on 2026-11-09.**

[SQLite_Architecture_and_Implementation_Plan.md](SQLite_Architecture_and_Implementation_Plan.md) controls SQLite file format, SQL boundary, signing-key storage and incremental delivery. The ledger operates **independently of a relational database**. Commands must report which components are available rather than imply a projection exists in Phase 1.

## 2. General CLI behavior — Owner-approved Phase 1 conventions

**Approved Phase 1 CLI syntax:** `ledgerctl --instance-root ABS COMMAND ...`, with an explicitly selected local support root. The name `ledgerctl` and the command structure reflect the Owner-approved direction; command-specific extensions remain subject to later QA schema review. On any platform, paths must be validated and contained within intended configured storage roots when appropriate. No PostgreSQL executable, daemon, port, user, or cluster is assumed.

Finite CLI commands should produce exactly one UTF-8 JSON object terminated by a newline on stdout; errors/diagnostics go to stderr. Approved JSON envelopes:

```json
{"ok":true,"data":{},"error":null}
```

```json
{"ok":false,"data":null,"error":{"code":"CODE","message":"Human-readable text","retryable":false,"details":{}}}
```

The raw signed bytes are **always transferred by files or binary peer streams**, not JSON reserialization. Canonical UUID strings are lowercase hyphenated; SHA-512 hashes and Ed25519 public keys are lowercase hex in JSON. Private signing material never appears in status, logs, or successful responses. Exit-code groups and command response field types are specified in §§3 and 13. QA/Tester independently checks that contract and develops conformance vectors; the document does not claim test execution.

## 3. Phase 1 approved commands and lifecycle

**Global selector:** `ledgerctl --instance-root ABS COMMAND ...`; ABS identifies the intended same-basename support directory (`ABC/`), which can exist before `ABC.DLDB` is constructed. On CLI errors print one JSON failure object to stdout, details to stderr, and never fabricate successful durable outcomes. Unknown flags, out-of-range integers, invalid UUID/digest syntax and incompatible options fail `INVALID_ARGUMENT` without changing state. The approved command families and flags are:

| Command | Required / optional inputs | Expected `data.operation` and essential success output |
| --- | --- | --- |
| `instance init` | No required extras | `instance.init`: `instance_guid`, `public_key_hex`, `instance_root`; durably persists key and manifest before success |
| `instance status` | None | `instance.status`: `state`, nullable `instance_guid`/`public_key_hex`, `signing_available`, `recovery_codes` (including config errors when applicable) |
| `instance recover --from ABS [--confirm-unbound-initialization]` | Original backed-up identity directory; **or**, only with confirmation flag, canonical surviving original `signing-key.v1.json` path from an interrupted never-bound initialization | `instance.recover`: original `instance_guid`, `public_key_hex`, `recovered`; strict original-identity checks |
| `ledger init` | None | `ledger.init`: `ledger_guid`, `genesis_sha512`, `genesis_block_guid`; use existing instance key, never create another |
| `ledger recover-genesis --ledger-guid UUID --genesis-sha512 HEX` | Exact existing genesis identity required | `ledger.recover-genesis`: `ledger_guid`, `genesis_sha512`, `genesis_block_guid`, `recovered`; idempotent only for same pin |
| `ledger join --ledger-guid UUID --genesis-sha512 HEX` | Both required; importing/discovering genesis prerequisite | `ledger.join`: `ledger_guid`, `genesis_sha512`; specified digest is explicit trust confirmation |
| `key backup --directory ABS` | Destination | `key.backup`: `directory`, `instance_guid`; identity records preserved together |
| `key restore --directory ABS` | Source | `key.restore`: `instance_guid`, `public_key_hex`, `restored`; strict original-identity match |
| `block publish --event-file ABS` | Raw Version 1.01 event body; optional explicit block GUID/timestamp; both required for `REVOKE_MASTER` | `block.publish`: `ledger_guid`, `block_guid`, `sha512`, `durable`, `authorization`; signs with persisted local authorized key |
| `master countersign-revocation --block-guid UUID --timestamp-utc-ms INT64 --outer-signer-public-key HEX --revoked-public-key HEX --output ABS` | Healthy bound authorized second master, consent exactly §6.3 | `master.countersign-revocation`: consent SHA-512, signature hex, output path, countersigner public key; never private seed |
| `block import --input ABS` | Raw `.BLK` or `DDLB` | `block.import`: `results`, `durable_count`; per-item result contains `ledger_guid`, `block_guid`, `sha512`, `status`, `reason`, `duplicate`, `durable` |

| `block export --output ABS` | Optional `--ledger-guid`, `--id UUID`/`--sha512`, or inclusive timestamp bounds; peer missing-hash filter deferred to Phase 4 | `block.export`: `path`, `bytes`, `sha512`, `block_count` |
| `config get` / `config set` | `set` requires nonempty documented resource-limit subset | `config.get` / `config.set`: `limits` |
| `status` | None | `status`: `instance`, `binding`, `signing`, nullable `blocks`, required `projection` (Phase 1 `not_installed`), nullable `peers` |

**Approved outcome conventions:** Exit `0` success; `2` malformed argument/frame/signature/event/identity; `3` truthful `PARTIAL_IMPORT`; `4` identity/recovery/authorization/state preconditions; `5` configured time/resource limits; `6` I/O/internal failure. JSON failure is `{"ok":false,"data":null,"error":{"code":"CODE","message":"TEXT","retryable":false,"details":{}}}` and success is `{"ok":true,"data":{},"error":null}`, with command-specific `data` fields listed above. `retryable` describes whether the original condition might clear; it does **not** mean resubmitting SQL writes is safe. Codes include `INVALID_ARGUMENT`, `BAD_FRAME`, `HASH_MISMATCH`, `BAD_SIGNATURE`, `BAD_EVENT`, `UNSUPPORTED_VERSION` (exit 2); `PARTIAL_IMPORT` (3); `RECOVERY_REQUIRED`, `SIGNING_IDENTITY_UNAVAILABLE`, `IDENTITY_MISMATCH`, `DUPLICATE_INSTANCE`, `NOT_AUTHORIZED`, `ALREADY_BOUND`, `GENESIS_MISMATCH`, `BLOCK_NOT_FOUND`, `BLOCK_ID_DISPUTED`, `LEDGER_IDENTITY_MISMATCH` (4); `RESOURCE_LIMIT` and `PROCESSING_TIMEOUT` (5); `IO_ERROR` and `INTERNAL_ERROR` (6). Error `details` should include applicable `path`, `reason`, `instance_guid`, expected/observed public-key fingerprints, and processed block results without ever exposing private material. Exact closed per-command JSON Schemas can be released with QA vectors without changing these approved command/result conventions.

**Initialization:** `instance init` succeeds only for a genuinely new, explicitly initialized target after path/identity preflight. Write/flush/publish the encrypted key record first, then the nonsecret instance manifest; no automatic startup initialization. Any detected partial temporary/key/manifest remnants require explicit recovery. The key must be durably persisted before acknowledging initialization. `ledger init` then creates one durable **Version 1.01** self-signed 211-byte genesis signed by that saved identity. A crash after durable genesis but before manifest binding requires explicit reconciliation and binding recovery; never silently create a second genesis. `ledger join` requires previously imported/discovered verifiable signed genesis and the full expected SHA-512; a bare GUID never establishes trust. `instance.identity.json` persists the pinned ledger GUID and genesis fingerprint outside future `.DLDB` projection.

**Identity gate:** Missing, corrupted, mismatched or undecryptable key/manifest suspends all ordinary SQL and ledger processing, including reads, replay, imports, export and peer synchronization. Only `instance status`, `status` (diagnostic subset), `instance recover`, `key restore`, and safe read-only diagnostics are allowed (plus verified `ledger recover-genesis` when original identity is usable). Restore must reproduce the original expected Ed25519 public key; duplicate active identity is rejected on the same host. Removing `.DLDB` must never remove the manifest/key. No `.DLID` exists. `key backup` is an explicit operation, not permission for ordinary processing while key is unavailable.

## 4. Signed-block import, storage, status and export

### Storage organization

The source of truth is the set of independently authenticated **exact-byte** `.BLK` files. **Approved:** keep them under `<database-basename>/BLK/` where `<database-basename>` is the name (without `.DLDB`) of the database file; matching advisory status resides under a separate sibling `<database-basename>/STAT/`, with identical relative UTC-date paths and filename stems:

```text
<database-basename>/BLK/YYYY/YYYYMM/YYYYMMDD/
  YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.BLK
<database-basename>/STAT/YYYY/YYYYMM/YYYYMMDD/
  YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.STAT
```

This filename layout is not a protocol encoding. Verify actual bytes even if the name appears valid. `HHMMSSssss` consists of UTC `HHMMSS` plus four fractional digits with the last digit `0` at millisecond resolution. Support a documented non-calendar fallback for valid signed int64 timestamps outside host calendar range. The SHA-512 suffix is over the **entire raw signed block**, including the signature, and distinguishes disputing variants of one block GUID.

**Owner-approved inventory approach (exact peer/cache byte grammar under review):** Daily leaf inventory hashing sorts exact `.BLK` filename stems (remove only the `.BLK` extension) by ordinal ASCII bytes and hashes a versioned, binary, length-delimited serialization with SHA-256. Parent folders hash sorted child-folder names together with raw child digests. Filenames include the full-block SHA-512 and thus distinguish disputed variants; cache files are rebuildable and never authoritative. Hash comparisons are meaningful only for the same pinned ledger GUID and full genesis SHA-512, not merely the same local folder name.

### Retention and durability

- Parse, bound, hash, and verify received blocks before official projection effects. In Phase 1 an unknown signed protocol version is rejected with `UNSUPPORTED_VERSION` **without durable retention** (`opaque_count=0`). A cryptographically valid block missing historical authorization evidence is durably retained as **local-only pending `.XBLK`**, never treated as applied. Authority and identity-dispute quarantine follow §14.1.
- Write a unique temporary file in the target filesystem; flush exact bytes; publish with a safe atomic no-overwrite rename; ensure directory-entry persistence as supported on the host; only then report acknowledged durable receipt. Partial `.BLK` files must never be treated as accepted.
- Identical exact-byte blocks are idempotent duplicates. Distinct authenticated bytes sharing `(ledger_guid, block_guid)` are retained and **quarantined without a chosen winner**. The original Version 1 conflict policy remains in force.
- `.STAT` sidecars are **advisory, replaceable and potentially stale**. Rebuild them as needed; they never authorize materialization or override current canonical history. Projection generation/checkpoint records are committed in SQLite **with** official state changes.

A Phase 1 block's reported disposition uses `retained`, `pending`, `quarantined`, or `rejected` with a machine-readable reason; `applied` requires the future Phase 3 projector and `opaque` is reserved. **Retained**, **durable**, and **projected** are distinct. An authenticated authorized block is `retained`, even with no `.DLDB`; only missing historical authority is `pending`. A full replay or late earlier block can change statuses without changing original `.BLK` bytes.

### Import/export behavior

- Import exact single-block bytes or the existing `DDLB` container; validate framing, hash, signature and ledger identity safely. A partially completed batch retains independently durable preceding blocks; never claim all-or-nothing batch import.
- `block get` retrieves only **active `.BLK`** bytes. If the identity is disputed and archived, ordinary retrieval returns `BLOCK_ID_DISPUTED` without a usable active variant; `--sha512` never bypasses `.XBLK` exclusion. If a requested exact digest exists only in `.XBLK`, return `BLOCK_NOT_FOUND` with reason `ARCHIVED_NOT_EXPORTABLE`.
- `block get` returns the **exact original raw signed-block bytes**. **Every `block export`** (including zero- or one-block selection) returns the existing Version 1 `DDLB` framing: `DDLB` magic (4 bytes), version uint16 big-endian, count uint64 big-endian, then count repetitions of `(length uint64 big-endian, original full signed block bytes)`; no re-signing or reserialization.
- Deterministic batch ordering uses canonical event order with full-block digest as tie-breaker when needed. Incremental missing-set exchange compares hashes/IDs of **active `.BLK` files**, not only timestamps; local-only `.XBLK` files are not exported or included in peer reconciliation.
- Limits on raw bytes, decoded bytes, import memory, CPU/time and peer resources remain required and configurable. Earlier PostgreSQL adapter exact min/max validation tuples and test-harness timing conventions are **not automatically inherited**.

## 5. SQL behavior, read barriers, and errors

Except in identity-recovery state, this CLI is an operational surface **alongside** ordinary SQLite C API/SQL access; it is **not a substitute** for standard supported SQL mutation submission. An authorized master's supported SQL mutation path publishes authenticated blocks first. Only the trusted projector changes official `.DLDB`. Unsupported SQL commands or alternate mutation interfaces must fail safely rather than bypass the ledger. A replica refuses user mutations.

Supported SQL reads observe a consistent locally projected state and may be network-stale. Affected SELECTs pause while an already-known reconciliation/rebuild would expose intermediate inconsistent state; they never wait for hypothetical unreceived remote blocks. A successful write publication acknowledgment need not make the value immediately SELECT-visible. `RETURNING`, transaction result tags, and partial-publication reports must describe what actually happened, without promising group-atomic multi-block commits.

**Important distinction:** The original PostgreSQL-specific SQLSTATE codes `ZL001`, `ZL002`, `ZL003`, `08007`, server error fields, `COPY FROM STDIN`, `COPY TO STDOUT`, and PostgreSQL `MERGE` requirements do not automatically apply to SQLite clients. The SQLite implementation needs an explicit, separately reviewed mapping to SQLite's result/extended-error APIs and normal SQLite transaction behavior. This specification **does not claim that mapping has been finalized**.

## 6. Private signing keys and recovery

**SEC-002 approved baseline (2026-11-08):** Every explicitly initialized instance, master or replica, generates an Ed25519 keypair using secure randomness and durably persists it before initialization succeeds. Private material resides in a separate **versioned key file**, encrypted at rest with **AES-256-GCM**, a **fresh random nonce for each encryption**, and a **versioned application-wide symmetric key embedded in the public source**. The embedded wrapping key is recoverable by anyone reading the source: this is **obfuscation against casual inspection, not protection against determined file holders**. Use a portable `ISigningKeyStore` abstraction and appropriate best-effort OS file permissions; no mandatory DPAPI, Keychain, Keystore, hardware service, cloud provider or startup password/PIN. Keep the key and nonsecret instance identity record outside `.DLDB`, `.BLK`, `.STAT`, repository and normal projection backups. The identity survives projection deletion/rebuild. Verification/replay are unattended and require only public keys; loss of the original private key triggers **recovery-required suspension of ordinary SQLite and ledger operations** (including read-only replay), never silent regeneration; status/diagnostics/original-identity restoration alone remain available. Optional disaster recovery must restore **the identical Ed25519 public key**. The **Owner-approved exact** signing-key Version 1 JSON fields, AES-256-GCM nonce/tag/AAD and identity-manifest Version 1 fields are specified in [SQLite_Architecture_and_Implementation_Plan.md](SQLite_Architecture_and_Implementation_Plan.md) §§8.3–8.4; the approved 88-byte AAD remains unchanged.

This project uses **digital signatures**, not private-key encryption of public ledger bytes. The ledger GUID is an identity, not a signing credential. A private key's mere possession is not canonical master authorization. Normal startup, replay and reconstruction **must not prompt** for a phrase, PIN, password or key-unlock action. Existing keys whose file is missing, malformed, undecryptable or whose derived public key differs from the persistent instance-identity record put the instance in recovery-required state; do not silently replace them or serve ordinary read-only SQL/ledger operations. Key rotation, restore and version upgrades must preserve identity unless the Owner separately approves an identity replacement operation.

## 7. Replay, status, and diagnostics

Once identity availability is verified (or the original identity has been restored), the projector must reproduce state from signed retained history including genesis, authority history, schema events and row changes. Full deterministic replay is an acceptable first implementation. Without the expected private key, ordinary replay is paused by Owner operational policy even though signature verification itself needs only public keys. It should guard affected reads and official writers, use SQLite-supported recovery lifecycle, and atomically persist projection progress alongside projected changes. Reconciliation/failure states must be visible through management commands and persistent diagnostics; a failed rebuild must never silently expose half-reconstructed state. Selective replay and zero-downtime projection swaps are future optimizations, not exceptions to full-replay correctness.

A status report should distinguish current canonical applied work from unapplied retained variants, pending authority/schema dependencies, disputed identities, and missing projection. The status is a local snapshot and **cannot prove global network completeness**.

## 8. Incremental implementation and contract freeze

1. **Independent ledger:** instance identity, genesis/keys, signed protocol 1.01 codec, signing, verification, durable `.BLK`, import/export/status; no database required.
2. **Native SQL interception:** supported SQLite C API writes on authorized masters produce durable authenticated `.BLK` history or fail safely, while official `.DLDB` state remains **unmodified**. Limited isolated provisional SQL evaluation for tests may be used before any projector exists; no persistent alternate official store.
3. **Ledger-to-SQLite projection:** customized `.DLDB`, projector-only writes, exact types, `.STAT` regeneration, progress transactions, full rebuild and read consistency.
4. **Peer exchange:** configured peers, independent offline masters, missing-block reconciliation and eventual convergence.

**Phase 1 contract scope:** The Owner-approved manifest, key-file grammar and 88-byte AAD, timestamp fallback, commands/flags, basic result fields and exit groups are in force. Detailed Phase 1 command/state/error contracts are specified in §13 for deterministic QA. Peer protocol, advisory `.STAT` sidecar internals, and projector/SQLite error details are **later-phase gates**, not Phase 1 CLI blockers. These operational details are *draft engineering obligations*, not changes to the Version 1 signed-wire format. Tests and implementation are assigned by the Project Manager to the Developer and QA under their respective permissions.

## 9. ARCH-003 recovery and path policy — current Owner direction

Support folder `ABC/` beside intended `ABC.DLDB` contains **no `.DLID`**; `instance.identity.json`, `signing-key.v1.json`, optional approved `instance.config.json`, `BLK/`, `STAT/` and temporary `DELn/` are the approved basic layout. Manifest identifies the stable instance and ledger/genesis binding. ## 10. Persistent signing-key and genesis identity — OWNER APPROVED

The Owner-approved **Version 1 key-file JSON/AAD** remains in SQLite Architecture Plan §8.3: 32-byte Ed25519 seed AES-256-GCM-obfuscated under publicly embedded `application-wide-v1`, fresh 12-byte nonce, 16-byte tag and exact **88-byte** binary AAD. This key-file version is **independent** of signed protocol 1.01. The nonsecret `instance.identity.json` holds instance GUID, expected public key, key-file name and nullable trusted `{ledger_guid, genesis_sha512}` binding, independently of `.DLDB` and signed `.BLK`. `.DLID` is removed; its information is merged into the manifest. No mandatory OS keystore or human unlock, and no silent key replacement. Expired/unavailable original keys enter recovery state; all ordinary processing pauses. Recovery remains an explicit operation with old public key/ledger binding verification.

## 11. Protocol 1.01 and Phase 1 interoperability

Signed ledger block header `version=0x0101` (major/minor one byte each); all `0x0101` row-value tags are **five native SQLite classes** (`0x00` NULL, `0x01` INTEGER, `0x02` REAL, `0x03` TEXT, `0x04` BLOB). Column definitions encode the actual declared type text, not historical `declared_type_tag` or DECIMAL parameters. The `0x0001` historical protocol is incompatible; never reinterpret its signed bytes under the 1.01 grammar. The independent `DDLB` transport batch version `0x0001` remains unchanged. Full signed genesis remains 211 bytes. Canonical event order is `(timestamp_utc_ms, block_guid, signer_public_key)`.

**Approved out-of-range timestamp fallback:** A signed int64 epoch millisecond value outside UTC years 0001–9999 maps to `BLK/OUTOFRANGE/T<16 lower hex>-<block-guid>-<full-sha512>.BLK`, where 16 hex digits are the signed timestamp's 64-bit pattern XOR `0x8000000000000000`. Mirror the stem in `STAT/OUTOFRANGE/`; include this branch in inventory reconciliation. Timestamp age alone never makes an otherwise authenticated block invalid.

## 12. Local `.XBLK` historical archive (Owner-directed) and approved projection-delay setting (2026-11-09)

**Compact local names — Owner-approved directory/file convention:** `BLK/YYYY/YYYYMM/YYYYMMDD/` and separate matching `STAT/YYYY/YYYYMM/YYYYMMDD/` contain `YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.BLK` and the same stem with `.STAT`. `HHMMSSssss` is derived from the signed UTC millisecond timestamp with the fourth fractional digit zero. The proposed invalidation archive uses `YYYYMMDD-HHMMSSssss-<block-guid>-<signer-public-key>.XBLK`, where the signer public key is 64 lowercase hex digits. File naming is metadata, not a signed wire change. Owner direction: no specialized same-timestamp/GUID/signer `.XBLK` collision feature is required for Version 1; rename operations must never overwrite an existing file and must preserve original bytes if a destination unexpectedly exists.

**Historical invalidation — Owner-directed:** When newly available earlier authority history makes a formerly authorized signed block inapplicable, retain its exact bytes locally but remove/invalidate its advisory `.STAT` through the STAT manager, rename `.BLK` to `.XBLK` without overwriting existing files, and reconcile projection through full replay (or future equivalent selective replay). While archived, `.XBLK` **never propagates**: exclude it from peer inventory, announcements, ordinary block export and peer service. Reevaluate archived files whenever canonical historical authorization changes. If a former `.XBLK` is authorized again at its signed position, validate the retained signed bytes, recover the full-block SHA-512, rename it back to the standard `.BLK` filename, update `TREE.HASH` and restore normal push/pull eligibility; materialization still follows normal projection rules. `.XBLK` is not a corrupt-signature category. A no-overwrite failure pauses the transition and reports an error without deleting retained bytes. This approved local-only exception means equality of advertised active inventories does not imply equality of locally archived historical bytes.

**Projection delay — Owner-approved behavior:** Expose configurable nonnegative `projection_delay_seconds`, **default 0**, delaying **only** ordinary row/schema projection until `signed_timestamp_utc_ms <= node_UTC_ms - delay_seconds*1000`, with overflow-safe arithmetic. Inbound verification, durable acceptance, current canonical authority evaluation and master-signing eligibility are not intentionally delayed. Report `pending_by_age` separately from `pending_authority`, `reconciling`, and `failed` (serialized field names are draft). Return consistent but intentionally stale SELECT results while eligible work is held; apply normal read barriers during replay. Re-evaluate cutoff safely when configuration changes; never promise finality, missing-peer completeness, or absence of late-block rebuild. Exact flag/JSON schema, maximum value and clock-jump behavior remain to be finalized by Developer/QA and approved before public interface freeze.

## 13. ARCH-010 Phase 1 deterministic CLI contract — Owner-approved direction; Architect-specified details for Developer/QA review

This section closes implementation-facing **Phase 1** command and output ambiguities without changing the Owner-approved block, key, identity or transport bytes. The five material additions/clarifications approved by the Owner are: exact Version 1 manifest; REAL rules in Technical Design §6.2; `block publish` and independent ledger-library equivalent; `ledger recover-genesis`; explicit ledger choice where unbound history contains multiple ledgers. The remaining flag spellings, result keys and deterministic error prioritization in §§13–14 are the Architect's approved-decision-derived contracts offered to Developer/QA for conformance review. **Tests and test-vector production belong to QA**, not to this design document. Neither an unimplemented Phase 2 SQLite interceptor nor a Phase 3 projector is a prerequisite to Phase 1 `block publish`/`import`.

### 13.1 Common parsing, paths, output, atomicity

- `--instance-root ABS` is a required absolute path to the intended same-basename support root. Options are long-form, case-sensitive; no positional aliases or short flags are defined. All `UUID` values are canonical lowercase RFC 9562 hyphenated strings; SHA-512 digests are exactly 128 lowercase hexadecimal characters; public keys are exactly 64 lowercase hexadecimal characters. Decimal integer arguments are ASCII base-10 with optional leading `-` only for **signed** timestamps, no whitespace, decimal points, plus sign or exponent; reject overflow before any filesystem mutation.
- Exactly **one complete JSON object plus final LF** goes to stdout for **each finite command**, including failures; stdout contains no progress text or private material. UTF-8 without BOM. `message` and human diagnostics may vary, but **all code/status keys, required nulls and enum values below are stable**. Additional unrecognized schema fields are not emitted in Version 1 of the Phase 1 CLI contract. CLI errors go to stderr only as human-readable additional diagnostics, never as a replacement for stdout JSON. Machine-readable JSON numbers are nonnegative counts/byte lengths that fit signed 64-bit; timestamps are **decimal strings** when represented in JSON to avoid binary64 precision loss.
- Success is `{"ok":true,"data":<object>,"error":null}`. Failure is `{"ok":false,"data":null,"error":{"code":<SCREAMING_SNAKE_CASE>,"message":<string>,"retryable":<bool>,"details":<object>}}`. Every success `data` requires a literal `operation` string matching the qualified command (`instance.init`, `block.publish`, etc.). For `status`, `operation="status"`. No private seed/ciphertext/AES key appears in any response.
- An output file, backup member, or signed `.BLK` is acknowledged as `durable:true` **only after complete content and its final destination-directory entry have met the platform's documented durability procedure**; a short write, failed flush, or uncertain rename returns an I/O failure/uncertain-result diagnostic, never a false durable acknowledgment. Use unique temporary paths and **no-overwrite** final publication. Crash-recovery must never delete the only surviving signed bytes or identity record. If a platform cannot provide the required acknowledgment, fail closed with `DURABILITY_UNCERTAIN` (exit 6). Exact fsync/FlushFileBuffers behavior is subject to Windows 11 QA qualification.
- A healthy instance holds an exclusive same-host identity lock for mutating and ordinary ledger commands; `DUPLICATE_INSTANCE` (exit 4) names the instance GUID, not a secret. Diagnostic `instance status`/`status` remain available in recovery. Identity-recovery mode blocks `ledger init/join`, `block publish/import/get/export`, `master countersign-revocation`, key backup, normal config operations, and all ordinary SQL/replay/synchronization until recovery succeeds; only `instance status`, diagnostic `status`, `instance recover`, `key restore` and `ledger recover-genesis` **when the surviving original identity and genesis can be validated** are admissible. `ledger recover-genesis` cannot bypass a missing/corrupted signing key.

### 13.2 Stable Phase 1 operation arguments and result fields

Types: `uuid` = canonical lowercase UUID string; `hex32` = exactly 64 lowercase hex chars; `hex64` = exactly 128 lowercase hex chars; `path` = normalized absolute path string; `count`/`bytes` = nonnegative JSON integer up to int64 maximum; `bool` = JSON boolean; `state` and `reason` = enumerations documented below; `?` means nullable, **not omitted**. Fields in each row are **all required**, unless an input is explicitly marked optional. The common `operation` field is required in every `data` object. Unexpected flags and incompatible combinations are `INVALID_ARGUMENT` (exit 2).

| Command | Additional exact inputs | Required `data` fields, besides `operation` |
| --- | --- | --- |
| `instance init` | none | `instance_guid:uuid`, `public_key_hex:hex32`, `instance_root:path`, `durable:bool` (true on success) |

### 13.3 Publication, genesis and identity recovery

- `block publish` is available through both the CLI and an equivalent database-independent managed ledger-library operation. The library accepts the exact Version 1.01 **uncompressed** event payload bytes, optional explicit UUID and signed-int64 millisecond timestamp, and returns a structured outcome equivalent to CLI `data`; it does not require a `.DLDB`, SQL parser, projector or peer service. It generates missing block GUID/time, uses the **persisted local** Ed25519 key, constructs the standard signed `0x0101` envelope and checks the known canonical authorization state at the chosen position **before** durable `.BLK` publication. Only a presently authorized master may publish; a replica key alone confers no publication rights. Invalid events (including REAL NaN), unavailable keys, unmet revocation signatures, limits, and missing authorization fail **without publishing** a new authenticated block. No import-only test escape hatch bypasses verification.
- `REVOKE_MASTER` countersignature covers `block_guid` and `timestamp_utc_ms` among its 149-byte signed-intent fields. Therefore **both** `--block-guid` and `--timestamp-utc-ms` are required for `block publish` of `REVOKE_MASTER`; the caller constructs the `event_kind 0x21` payload and obtains the valid countersignature using the exact existing §6.3 message before publication. The library exposes the same explicit-ID/time arguments. It must not regenerate these values after the countersignature. QA may alternatively independently construct full authenticated signed blocks and submit them using `block import`. This adds no new event kind, wire format, or key authority.
- `ledger init` uses the existing persisted key to create a **single Version 1.01 self-signed empty-payload 211-byte genesis block**, flushed to `.BLK` before atomically pinning `{ledger_guid, genesis_sha512}` in the manifest. On durable genesis plus interrupted manifest binding, subsequent `ledger init` must return `RECOVERY_REQUIRED`/`GENESIS_BINDING_INCOMPLETE` and must **not create another genesis**. Evidence includes the valid local-signed genesis and initialization artifacts; no assumption that absence of the manifest binding equals a fresh attempt. Multiple conflicting locally authored genesis candidates trigger `GENESIS_CONFLICT`, never automatic selection.
- `ledger recover-genesis` is the **Owner-approved explicit idempotent recovery interface**. It requires a healthy or recoverable **original** instance key and manifest, searches retained local `.BLK` records (including `OUTOFRANGE`) for the **exact provided SHA-512** and GUID, verifies the 211-byte `0x0101` genesis structure, payload hash, self-signature, ledger GUID, full-block hash, and signer=original instance public key. It must reject mismatched/multiple locally authored genesis candidates, a different preexisting manifest binding, or a missing/invalid original identity, without replacing any original bytes. If manifest is already pinned to the same identity, return idempotent success; if unbound with a single matching previously durable genesis, atomically publish the binding. A repeat crash/retry yields the same result or remains safely recoverable. Never infer trust from ledger GUID alone. An unbound replica joining externally authored genesis uses `ledger join`, **not** `recover-genesis`.
- `instance recover --from` and `key restore --directory` recover from the **original identity** only: verify AES-GCM authentication with the approved 88-byte AAD and rederive the same Ed25519 public key; reject a different instance GUID, identity, pinned genesis, or overwrite of live unrelated records. **ARCH-011 explicit exception:** when the canonical original signing-key file survived **but manifest and genesis were never durably created**, `instance recover --from <signing-key.v1.json> --confirm-unbound-initialization` may restore a **matching unbound** manifest after checking all local evidence and the operator's explicit assertion of interrupted setup. Without that confirmation, or if durable binding/genesis/contradictory remnants exist, remain in recovery. No key is generated or replaced. Idempotent retried recovery must not erase the original key. Residual temp files are diagnosis/recovery evidence, never permission to run `instance init` automatically. No `.DLID` is created. Exact acceptance in §14.4.

### 13.4 Import, variants, get/export, and error selection

- The `DDLB` container remains **Version 1**: magic `DDLB`, `uint16_BE(1)`, `uint64_BE(count)`, repeated `uint64_BE(length) || exact_block_bytes`. Parse and bound each length before allocation; reject trailing/unaccounted bytes, truncation and arithmetic overflow. Imported signed `0x0101` blocks must pass framing, payload SHA-512, signature, event/REAL validation and ledger-identity checks before durable retention. Valid independently authenticated blocks with missing earlier grant/schema context may be durably **pending** rather than rejected. Unknown signed-protocol versions return `UNSUPPORTED_VERSION` (exit 2), are **not durably retained in Phase 1**, and do not affect counters; `opaque` and its retention are reserved for a later separately approved phase. Import into a bound instance of a different ledger fails `LEDGER_IDENTITY_MISMATCH`.
- For each import item, always return an object with: `index:count` (zero-based), `ledger_guid:uuid?`, `block_guid:uuid?`, `sha512:hex64?` (full signed block), `status:{retained,pending,quarantined,rejected}`, `reason:string`, `authorization:{authorized,unauthorized,pending,not_evaluated}`, `duplicate:bool`, `durable:bool`. Fully valid presently authorized active `.BLK` uses `status="retained"`, `authorization="authorized"`, `reason="AUTHORIZED_RETAINED"`; it is **not** SQLite-applied and does not increment `pending_count`. Missing historical authorization evidence uses `status="pending"`, `reason="PENDING_AUTHORITY"` and local-only `.XBLK`. Currently unauthorized evidence uses `status="quarantined"`, `reason="UNAUTHORIZED_AT_POSITION"`, also `.XBLK`. Authenticated same-identity variants use `status="quarantined"`, `reason="BLOCK_ID_DISPUTED"` and local-only `.XBLK`, regardless of their secondary authorization assessment. Dispute classification takes precedence. No `opaque` status is emitted in Phase 1. Rejected/unsupported bytes have `durable:false` absent a separately specified diagnostic quarantine. `duplicate:true` only for byte-identical already-retained signed data, is idempotent success, and does not increment `durable_count`; `sha512` identifies exact signed bytes, never the DDLB wrapper.
- On a `block import` **fully successful** command, `data.total_count` equals input item count, `data.durable_count` equals **newly persisted** complete signed files, `data.duplicate_count` counts byte-identical repeats, and `data.rejected_count=0`. If some input items were already committed and others fail, return exit `3`, `PARTIAL_IMPORT`, `data:null`, and **put the complete ordered item-results array and all four counts in `error.details`**. If none succeeded, return the first error by input order with its usual exit group and include the same results/counts; never roll back previously durable items to fabricate all-or-nothing behavior. Any pending/quarantined item whose authenticated bytes were retained counts as success for this batch accounting, even if its projection eligibility is unresolved.
- `block get`: return the **unchanged signed bytes of one active `.BLK`**. If authenticated variants of `(ledger_guid,block_guid)` are disputed, classify/archive both and return `BLOCK_ID_DISPUTED` (exit 4) for the identity, without selecting a winner. `--sha512` identifies a variant but **does not grant permission to read archived `.XBLK`**; for an exact digest present only in archive, return `BLOCK_NOT_FOUND` with `error.details.reason="ARCHIVED_NOT_EXPORTABLE"`. A nonexistent variant also returns `BLOCK_NOT_FOUND`. For unbound roots with blocks from multiple ledgers, require `--ledger-guid` when the query would otherwise be ambiguous. Path output is atomic/no-overwrite; no local `.XBLK` is exported by this normal command.
- `block export`: produce `DDLB` bytes containing exact active **`.BLK`** signed blocks of one ledger (never local `.XBLK`). With no filter, select all such blocks of the pinned ledger; if unbound and exactly one ledger is represented, select that ledger; if unbound with multiple ledger GUIDs, require `--ledger-guid` or return `AMBIGUOUS_LEDGER` (exit 4). `--id` selects a single block GUID; `--sha512` is allowed only together with `--id` and selects one exact authenticated variant. Inclusive `--from-timestamp-ms`/`--to-timestamp-ms` filters may appear singly or together but not with `--id`; when both are supplied lower must be ≤ upper. Export **only active `.BLK` variants**, never pending, unauthorized or disputed `.XBLK` files; archived signed bytes are kept for local reconsideration and included in inclusive retention counters, not ordinary export. If several active authorized variants match an identity before a dispute has been fully quarantined, fail closed with `BLOCK_ID_DISPUTED` rather than silently export a winner. Sort selected items by `(signed_timestamp_utc_ms, raw_block_guid, raw_signer_public_key, full_block_sha512)`; this final SHA-512 tie only orders byte-distinct disputed variants. Return an empty valid DDLB with count 0 for a valid ledger with no matching blocks. Missing-hash peer inventory filters are **Phase 4** and not mandatory in Phase 1.
- Any get/export where no ledger can be inferred because the unbound store is empty must use `--ledger-guid` or return `AMBIGUOUS_LEDGER`. A bound instance never silently switches ledger; an explicit conflicting `--ledger-guid` returns `LEDGER_IDENTITY_MISMATCH`. Existing output path collisions are `OUTPUT_EXISTS` (exit 4) and must not overwrite. Retained block existence and successful export do not imply canonical authorization or projection application.

### 13.5 Exact Phase 1 status fields and recovery diagnostics

`instance.status` fields are defined in §13.2. `status` returns the following **required** nested objects:

```json
{
  "ok": true,
  "data": {
    "operation": "status",
    "instance": {"state": "uninitialized", "instance_guid": null, "public_key_hex": null, "recovery_codes": []},
    "binding": {"ledger_guid": null, "genesis_sha512": null, "state": "unbound"},
    "signing": {"available": false, "authorized": false},
    "blocks": {"retained_count": 0, "pending_count": 0, "quarantined_count": 0, "disputed_count": 0, "opaque_count": 0},
    "projection": {"state": "not_installed", "applied_count": null},
    "peers": {"state": "not_installed", "connected_count": null}
  },
  "error": null

```

The example deliberately uses null identity fields for a **newly uninitialized** instance with `instance.state="uninitialized"` and `binding.state="unbound"`; a genuinely **unbound** initialized instance instead reports its known instance GUID, public key and `signing.available=true`. `signing.authorized` reflects local verified master status at the current canonical position, not possession of any private key. No Phase 1 operation reports a projected record as `applied`; `projection.state="not_installed"` and `applied_count:null` are mandatory until Phase 3 exists. The status snapshot distinguishes **durable block retention** (`blocks.retained_count`) from evaluated authorization (per import item or ledger verification) and **projected** status (absent). `pending_count` counts **only** cryptographically authenticated `.XBLK` variants whose historical authority is unresolved for lack of evidence, **not** blocks waiting for a Phase 3 projector. Counts do not claim any unknown remote block completeness. `retained_count` includes both active `.BLK` and local archived `.XBLK` variants (including the verifiable genesis) identified by complete signed-block SHA-512; `quarantined_count` includes currently unauthorized and disputed `.XBLK`; `disputed_count` is a **subset** of `quarantined_count` (never add them together). Pending and quarantined are disjoint. `opaque_count` is always zero in Phase 1. An archived `.XBLK` is never an export candidate or active inventory entry, even though it is included in inclusive retained totals.

When config exists but fails strict parsing or instance-GUID matching, `status` and `instance status` remain diagnostic-only available, with `instance.recovery_codes` including `CONFIG_CORRUPT` or `CONFIG_IDENTITY_MISMATCH`, **without claiming loss of the signing identity**; `instance.state` remains `bound` or `unbound` if the original key/manifest are healthy. `config get/set` and ordinary operations that depend on those settings fail until explicit operator recovery; never report effective limits from invalid input. If original identity verification fails, `status` remains callable as a **diagnostic-only** operation: `instance.state="recovery_required"`, `instance.recovery_codes` contains sorted error identifiers (such as `SIGNING_IDENTITY_UNAVAILABLE`, `IDENTITY_MISMATCH`, `GENESIS_BINDING_INCOMPLETE`), `binding` contains only safely readable manifest fields or nulls, `signing.available=false`, `signing.authorized=false`, `blocks=null`, `projection.state="not_installed"`, `peers=null`. Do not scan/process ledger blocks to compute fake counts while recovery gate is active. Recovery codes are stable symbolic values even though diagnostic `message` text may vary.

### 13.6 Phase 1 `config` contract and resource limits

`config get` has no Phase 1 filters. `config set --name NAME --value DECIMAL_UINT` changes **exactly one** supported parameter, durably persisting it in the **Owner-approved separate** `instance.config.json` file under the existing instance support root, without modifying immutable identity or pinned genesis binding. Missing file selects the defaults below; malformed or mismatched file fails with a diagnostic and blocks ordinary config-dependent operations until explicit operator repair (see §14.5). The only **Phase 1** accepted setting names are:

| Name | Units | Default | Valid values |
| --- | --- | ---: | --- |
| `max_raw_block_bytes` | bytes | `16777216` (16 MiB) | integer `211..9223372036854775807` |
| `max_decompressed_event_bytes` | bytes | `67108864` (64 MiB) | integer `1..9223372036854775807` |
| `max_inflight_import_bytes` | bytes | `134217728` (128 MiB) | integer `211..9223372036854775807` |
| `per_block_timeout_seconds` | seconds | `60` | integer `1..9223372036854775807` |

These are local operational limits, **not signed-wire maxima**. They may be lowered below the size of previously retained immutable blocks without deleting history; a subsequent command that cannot safely process required data returns a structured `RESOURCE_LIMIT`. Streaming implementation may allow in-flight memory smaller than permitted raw block size; do not require a complete block allocation. Values too large for a supported platform to enforce safely fail `RESOURCE_LIMIT` with a platform capability reason, **without storing the change**. Unsupported names, malformed numbers, zero, negative limits and overflows fail `INVALID_ARGUMENT`; no silent rounding, clamping or partial update. Return the entire `limits` object in stable order with all four exact keys. A `projection_delay_seconds` setting is Owner-approved in principle with default 0 but is **Phase 3** scope; do not silently treat it as a working Phase 1 projector setting.

### 13.7 Phase 1 error precedence and conformance handoff

The error envelope/exit groups from §3 remain authoritative. Add the following exact symbolic errors as needed: `GENESIS_BINDING_INCOMPLETE`, `GENESIS_CONFLICT`, `AMBIGUOUS_LEDGER`, `OUTPUT_EXISTS` (exit 4), `DURABILITY_UNCERTAIN` (exit 6). Unknown inputs always yield `INVALID_ARGUMENT` (2) before touching state. When several **state** gates apply, report the first in this fixed sequence: missing/mismatched identity → `RECOVERY_REQUIRED` (4); duplicate same-host identity → `DUPLICATE_INSTANCE` (4); missing trusted ledger/ambiguous selection → `ALREADY_BOUND`/`AMBIGUOUS_LEDGER`/`GENESIS_BINDING_INCOMPLETE` as applicable (4); unauthorized signer → `NOT_AUTHORIZED` (4); unsupported/invalid signed/event payload → `BAD_FRAME`/`UNSUPPORTED_VERSION`/`BAD_SIGNATURE`/`BAD_EVENT` (2); configured bounds → `RESOURCE_LIMIT`/`PROCESSING_TIMEOUT` (5); I/O failures → `IO_ERROR`/`DURABILITY_UNCERTAIN` (6). If argument syntax is malformed, use `INVALID_ARGUMENT` before any such gate. Do not leak key material or perform speculative mutation simply to choose an error.

## 14. ARCH-011 — Approved countersigning, counts, archive, identity and configuration contracts

**Normative precedence:** This section supersedes any earlier example in §§3–13 that calls an authorized-but-unprojected block `pending`, omits locally archived `.XBLK` from inclusive `retained_count`, permits Phase 1 opaque retention, describes ordinary `block export` as raw, or requires already existing genesis/binding evidence for the **explicit key-only unbound-initialization recovery**. §13 is otherwise preserved. No existing signed protocol 1.01, key-format Version 1, or DDLB transport Version 1 bytes change.

### 14.1 Exact Phase 1 status and counter matrix

All classes below require a complete authenticated signed Version 1.01 block (valid frame, payload hash, signature and applicable event validation). Counts operate on **distinct full signed-block SHA-512 variants** in the selected support root and include the verifiable 211-byte genesis; the same byte-identical imported block is counted once. A bound instance counts its pinned ledger. A healthy unbound support root counts all locally retained ledgers unless the operation has an explicit ledger filter; counting does not authorize mixing different ledgers for `get/export`. A count is a coherent classification snapshot, not a measure of other peers' inventory or SQL application.

| Block class | Initial/active storage | Per-item `status` | `authorization` | `reason` | Count membership |
| --- | --- | --- | --- | --- | --- |
| Verified genesis with consistent pinned or discoverable ledger identity | `.BLK` | `retained` | `authorized` (self-signed genesis rule) | `AUTHORIZED_RETAINED` | retained |
| Verified currently authorized, undisputed non-genesis | `.BLK` | `retained` | `authorized` | `AUTHORIZED_RETAINED` | retained |
| Cryptographically valid non-genesis, required earlier historical authority evidence unavailable | local `.XBLK` | `pending` | `pending` | `PENDING_AUTHORITY` | retained + pending |
| Cryptographically valid, known inapplicable/unauthorized at canonical position under available history | local `.XBLK` | `quarantined` | `unauthorized` | `UNAUTHORIZED_AT_POSITION` | retained + quarantined |
| Two or more authenticated variants of one `(ledger_guid, block_guid)` | each archived locally as `.XBLK` where no-overwrite permits | `quarantined` | independent assessment `authorized`, `unauthorized` or `pending` | `BLOCK_ID_DISPUTED` | retained + quarantined + disputed **per variant** |
| Byte-identical duplicate import | Existing storage unchanged | Current classification above | Current classification | Current reason | no increment |
| Invalid signature/event/frame or unsupported signed version | no durable ledger retention | `rejected` | `not_evaluated` | matching symbolic validation reason | no count |

`retained_count` is **inclusive**: `active_authorized_count + pending_count + quarantined_count` in a fully classified healthy snapshot, where `disputed_count <= quarantined_count` is **not** added again. `pending_count` and `quarantined_count` never overlap; disputed variants are counted separately **within** quarantine even when their historical authorization is `pending` or `authorized`. `opaque_count` is **zero** in Phase 1, and no import status `opaque` is emitted. `AWAITING_PROJECTOR` is **not** a Phase 1 block classification or import reason; `projection={"state":"not_installed","applied_count":null}` is reported independently. A late historical grant/revocation can change classification and counters without rewriting the signed data; every transition is idempotent and recoverable from crashes. No local `.XBLK` is served by normal get/export or later advertised to peers.

Physical `.XBLK` names use the approved same-date-path compact stem `YYYYMMDD-HHMMSSssss-<block-guid>-<signer-public-key>.XBLK`; for `OUTOFRANGE` retain `T<biased-int64-hex>-<block-guid>-<signer-public-key>.XBLK`, alongside the approved matching active `.BLK` layout. The file extension does **not** encode the pending/unauthorized/disputed classification: recalculate from verified bytes plus current known history; never trust stale status caches. Do not silently overwrite an existing `.XBLK` (including a compact-name conflict), delete the only surviving signed variant, select a disputed winner, or advertise an incomplete transition. If no-overwrite conflicts prevent normal archival, return a deterministic state/I/O diagnostic and retry/recover safely, without inventing an alternate file layout. Phase 1 has no `.STAT` replay obligations.

**Per-item import payload:** Retain §13.4 required keys exactly: `index`, nullable `ledger_guid`, nullable `block_guid`, nullable `sha512`, `status` (`retained|pending|quarantined|rejected`), `reason`, `authorization` (`authorized|unauthorized|pending|not_evaluated`), `duplicate`, and `durable`. When import causes reclassification of previously stored variants, the command reports the final classification of each input variant after evaluating the entire durable accepted prefix; the next `status` reflects the same coherent snapshot. The existing `PARTIAL_IMPORT` ordered `error.details.results` contract remains. For rejected unknown versions use `UNSUPPORTED_VERSION` (exit 2) and never durably retain them. `opaque` is reserved for later design only.

### 14.2 `block get` and `block export` — unambiguous byte outputs

`block get --id UUID --output ABS [--ledger-guid UUID] [--sha512 HEX]` publishes exactly one **raw, unchanged** signed-block byte sequence from active `.BLK`, not a `DDLB` wrapper. `block export --output ABS [filters]` publishes **one Version 1 DDLB container** for every selection, including zero or one matching block. Inside the wrapper, each signed block's bytes are unchanged and never re-signed. No normal get/export accesses archived `.XBLK`. Earlier generic references to "single-block export" mean raw single-block **retrieval via `block get`**, not a special one-block mode of `block export`. Output-file durability and no-overwrite remain as §13.1. Active inventory variants in unresolved same-GUID dispute cannot be exported by choosing an arrival-order winner.

### 14.3 `master countersign-revocation` — supported CLI and library API

```text
ledgerctl --instance-root ABS master countersign-revocation \
  --block-guid UUID --timestamp-utc-ms INT64 \
  --outer-signer-public-key HEX32 --revoked-public-key HEX32 \
  --output ABS
```

Required inputs are exact canonical UUID, signed-int64 ASCII decimal timestamp, two 64-character lowercase Ed25519 public-key hex values, and nonexisting absolute output path. `ledger_guid` is obtained **only** from the verified bound `instance.identity.json`; `countersigner_public_key` comes **only** from the surviving validated local Ed25519 key. The command requires a healthy, bound, locally authorized second master at the proposed canonical signed position, distinct from the outer signer. The outer signer must also be authorized there, and `revoked_public_key` must equal **one** of these two signer keys. If applicable earlier authority is missing, fail closed with `AUTHORITY_UNRESOLVED` (exit 4) rather than signing speculative consent; known unauthorized or bad signer-role relationships use `NOT_AUTHORIZED` (exit 4). No new private-key export is permitted. Construct §6.3's exact 149 bytes by concatenating ASCII `DDL-REVOKE-v1` (13), ledger GUID (16), block GUID (16), timestamp int64 BE (8), outer public key (32), revoked key (32), countersigner public key (32). Sign exactly those bytes with the local Ed25519 seed, output exactly **64 raw signature bytes** to the destination using durable no-overwrite publication, then return:

```json
{"ok":true,"data":{"operation":"master.countersign-revocation","ledger_guid":"<uuid>","block_guid":"<uuid>","timestamp_utc_ms":"<signed decimal string>","outer_signer_public_key":"<64 lowercase hex>","revoked_public_key":"<64 lowercase hex>","countersigner_public_key":"<64 lowercase hex>","consent_sha512":"<128 lowercase hex>","signature_hex":"<128 lowercase hex>","path":"<absolute path>","bytes":64,"durable":true},"error":null}
```

An equivalent **database-independent library API** accepts the same intent fields (with ledger ID and local countersigner identity derived from the bound instance), returns the exact 64-byte signature and SHA-512 of the 149-byte intent, and applies the same checks; it cannot expose the seed. The initiating master's subsequent `block publish` must use the exact same block GUID, timestamp, keys and countersignature already in event kind `0x21`, then verify the full revocation at that position before signing the enclosing block. If signers are unauthorized/pending, key unavailable, intent malformed, consent invalid, or output already exists, fail without publishing another block or leaking a private key. `OUTPUT_EXISTS` (exit 4), `BAD_SIGNATURE`/`BAD_EVENT` (exit 2) and `DURABILITY_UNCERTAIN` (exit 6) follow existing groups. Repeated successful invocation may produce the same deterministic Ed25519 signature, but must not overwrite an existing output file.

### 14.4 Explicit key-only, never-bound initialization recovery

```text
ledgerctl --instance-root ABS instance recover \
  --from ABS/signing-key.v1.json --confirm-unbound-initialization
```

This is an **exception solely for interrupted initial `instance init`** where original `signing-key.v1.json` already durably exists at the canonical path but no manifest or original genesis was ever durably published. The flag is a literal boolean assertion by the operator; no value accepted. Verify the complete signed-key JSON Version 1, approved **88-byte AES-GCM AAD**, tag, derived Ed25519 public key and original instance GUID before using the key. Confirm that the supplied path resolves to the canonical key for this support root and all available durable local evidence is consistent with a never-bound identity; no `.DLDB`, pinned-genesis, `.BLK`/`.XBLK` genesis, identity manifest with different key, contradictory backup, or conflicting initialization remnants may be silently ignored. Mere absence of evidence is **not cryptographic proof** of no former binding, hence the explicit operator assertion. If valid, atomically create the exact approved Version 1 manifest with the **same** instance GUID/public key, key_file `signing-key.v1.json`, `ledger_binding:null`, no `.DLID`, and return the §13.2 `instance.recover` data with `recovery_kind:"key_only_unbound"`, `state:"unbound"` and `recovered:true`. Repeating against an already identical complete, unbound manifest must return idempotent success; never create a second identity. If a crash leaves a temp manifest, verify it and safely finish/clean recovery without replacing existing records. Any conflicting or possibly bound evidence returns `RECOVERY_REQUIRED` (exit 4) with `error.details.reason="BOUND_OR_CONFLICTING_EVIDENCE"`; missing flag is `INVALID_ARGUMENT` (exit 2), bad key authentication or different instance identity is `IDENTITY_MISMATCH` (exit 4), I/O failure is `IO_ERROR`/`DURABILITY_UNCERTAIN` (exit 6). A **bound** original identity with a missing manifest instead uses existing verified original-backup or original-genesis evidence, never this flag.

### 14.5 `instance.config.json` — persistent resource limits

In the **existing** instance support root, create no new directory. Version 1 file uses UTF-8 without BOM; compact JSON writer in the field order shown with final LF; strict reader accepts arbitrary property order/whitespace but rejects invalid UTF-8, duplicate or unknown fields at any level, unsupported versions, wrong JSON types, oversized (>4096 bytes) or trailing content. Its exact approved initial form (the four numeric settings already defined in §13.6) is:

```json
{
  "format": "UDDL-INSTANCE-CONFIG",
  "version": 1,
  "instance_guid": "11111111-2222-4333-8444-555555555555",
  "limits": {
    "max_raw_block_bytes": 16777216,
    "max_decompressed_event_bytes": 67108864,
    "max_inflight_import_bytes": 134217728,
    "per_block_timeout_seconds": 60
  }
}
```

`instance_guid` must match the verified manifest and signing key. All limit values are **positive JSON integers** in the ranges stated in §13.6; booleans, floats, quoted numeric strings, negative, zero, and out-of-range/platform-unsupportable values fail. Unknown/duplicate fields fail. Missing config is **not corruption** and selects the documented four defaults; no file need be created until first successful `config set`. `config get` returns every effective limit and retains the existing response envelope. `config set --name NAME --value DECIMAL_UINT` validates entire existing config and the proposed limits; write a complete replacement to a unique temp in the same folder, flush contents, and atomically publish/swap with crash-safe directory durability, so after interruption either the complete old set or the complete new set remains, never a truncated/mixed set. Only acknowledge set after durable replacement; never change `instance.identity.json`, signing key, ledger binding, `.BLK`, or `.XBLK` as a side effect.

For a present corrupt config, `config get/set` returns `CONFIG_CORRUPT` (exit 4), or `CONFIG_IDENTITY_MISMATCH` (exit 4) if its instance GUID conflicts; diagnostics identify location/reason without exposing secrets. **Ordinary config-dependent ledger operations** fail closed while config is corrupted; diagnostic `instance status`/`status` and original-identity recovery remain accessible. The operator may explicitly restore a known-good configuration file or intentionally remove the invalid file to select defaults; do not silently reset corrupted settings. On a present, valid config, `config get` and `set` return all four effective limits; setting updates retain unrelated limits. If a platform cannot safely enforce a requested limit, return `RESOURCE_LIMIT` (exit 5) without writing it. Windows 11 durable atomic replacement must be qualified by Developer/QA; `DURABILITY_UNCERTAIN` (exit 6) applies when the required durability acknowledgment cannot be proven.
