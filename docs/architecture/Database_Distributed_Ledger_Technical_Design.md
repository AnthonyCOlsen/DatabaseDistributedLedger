## 1. Purpose and layer boundaries — CONFIRMED

Build a public-data, disaster-resilient, cryptographically authenticated distributed event ledger supporting an eventually consistent relational database on top. **The immutable ledger, not a relational database, is the authoritative data history.** The ledger may exist without a database. Only an **empty** database can initially adopt an existing ledger; it derives schema and data solely by consuming ledger events. Existing supported SQLite SQL interfaces and SELECT/query facilities must be retained, including the SQLite native C API where applicable, but there must be no supported direct SQL-to-official-storage mutation path: ordinary INSERT/UPDATE/DELETE or other supported user-managed data/schema changes submitted through any normal client connection must first produce authenticated ledger events; official storage changes only by ingesting ledger events. The implementation may use different internal components, but bypassing this invariant through an alternative SQL client, administrator-accessible supported interface, or unwrapped server endpoint is nonconforming.

An authorized master receives SQL write requests, evaluates them against the relational state it currently knows (or provisional transactional state), and publishes the resulting **concrete atomic changes** to the ledger before they are ever applied to official materialized storage. The same ledger consumer then applies locally produced blocks as it does remotely received blocks. A successful write acknowledgment can precede local SELECT visibility; client developers must accommodate stale reads. The database and application layers may implement stronger transactional protocols, but the underlying ledger neither promises global synchronous agreement nor interprets a client's business transaction as an atomic group.

**Every block is independent. No block references any predecessor, previous block, head, fork, or chain link.** “Blockchain” is a descriptive term for the authenticated historical collection and must not be interpreted as a hash-linked chain. There is no fork-choice election or dropping otherwise valid blocks to choose a preferred branch. A single logical order is calculated over the accepted blocks presently known to a participant.

## 2. Participation, identity, and authority — CONFIRMED

- **Ledger ID (Owner-approved ARCH-012):** immutable **exact 32 raw bytes** of the original genesis signer Ed25519 public key, not an independently generated 16-byte UUID. Remains unchanged if that signer is subsequently revoked or reauthorized. In JSON/CLI it is `ledger_id_hex` (exactly 64 lowercase hexadecimal characters).
- **Block GUID:** immutable 16-byte UUID identifier of an individual block, independent of its 32-byte ledger ID.
- **Master:** participant holding an authorized Ed25519 private signing key and permitted to publish blocks and delegate master authority.
- **Read-only replica:** anyone may join, verify, retain, exchange, and materialize blocks without signing authorization. **Every newly initialized local instance nevertheless has its own persistent Ed25519 keypair** under SEC-002. The replica's key does not confer authority without a valid grant; a node with an unavailable private key enters a recovery state that blocks ordinary SQL and ledger processing, including read-only replay, until the original identity is restored. Public-key verification does not cryptographically require a private key, but ordinary processing is intentionally paused under ARCH-003. A replica may relay blocks between disconnected masters.
- **Entity GUIDs:** every table, column, and row has its own immutable GUID, independent of SQL-visible names or declared keys. Names may change without changing identity. A deleted GUID cannot be reused; recreating a same-name entity uses a new GUID.
- **Genesis master:** initial sole signing authority established by the special genesis block; other masters are added with ledger events.

**Grant — CONFIRMED:** Any currently authorized master may issue a `GRANT_MASTER` event identifying a public key. A valid grant sets that key's authorization state to **authorized** at the grant's canonical position. Grants do not stack into separately surviving permissions: a redundant grant to an already authorized key is permitted but does not protect it from a subsequent valid revocation. A later valid grant can re-authorize a previously revoked key; no grant retroactively validates earlier blocks.

**Revocation — CONFIRMED:** A `REVOKE_MASTER` event must have approval from **the master being revoked and one other distinct currently authorized master**. Under active Protocol 1.03, Master A signs the exact time-bounded consent and Master B signs the final block, as specified in §6.3; the revoked target may be **either A or B** (B is the target in the Owner's motivating example); the original grantor has no special role. At the final block’s canonical position a valid revocation sets the **entire target public key** to unauthorized, rather than revoking a single grant. **Previously accepted** history may later be found inapplicable and must be retained/reclassified according to §22; **new incoming blocks** with unproven or false authority never enter durable storage. A later valid grant may reauthorize the key prospectively, not retroactively. Distinct-authorized-signers rule prevents revoking the sole remaining master; loss of the last signing key remains an operational catastrophe.

**Canonical authorization replay — CONFIRMED:** Process grants, revocations, and other events in the total block order defined in Section 4, irrespective of receipt order. A block is applicable only when its signer is authorized at that canonical position. Late-arriving earlier history can invalidate or revalidate dependent grants and projected effects; re-evaluate those consequences without erasing retained block bytes. A previously accepted block is not guaranteed permanently applicable when missing earlier history later arrives. No separate independent grant-lineage model or grant-block-specific revocation is used.

**CONFIRMED (ARCH-014 controlling):** `REVOKE_MASTER` payload field order is fixed in §6.3. Block identity is `(ledger_id[32], block_guid[16])`; `ledger_id_hex` is its JSON/CLI form. Byte-identical signed blocks are idempotent duplicates. A new incoming block whose historical signing authority is unproven or false is rejected entirely in memory. At Owner direction, accidental same-GUID conflicts are outside Phase 1 specialized dispute handling; reusing a retained GUID with different bytes returns `BLOCK_GUID_CONFLICT` without writing or overwriting any signed bytes. Previously accepted `.BLK` later invalidated by newly arrived historical authorization evidence is retained locally as `.XBLK` and reconsidered. No special incoming conflict-to-`.XBLK` archival or winner arbitration is required. Phase 1 `pending` and `quarantined` refer only to formerly accepted archived history; `disputed_count` is reserved/zero. Previous archival/dispute language is historical and superseded by this rule and §25. The proposal to sign only the reusable fixed phrase `I AGREE` remains unapproved.

## 3. Genesis and database initialization — CONFIRMED

On creation, each **empty** database must choose one of two paths:

- **Create a new ledger:** derive the permanent 32-byte ledger ID from the **verified persisted Ed25519 public key of the already initialized local instance** to publish a valid self-signed genesis block. The first master receives authority from authenticated genesis and binding, not from installing/selecting a key. The private key must already have been durably saved outside the projection and ledger files before this succeeds.
- **Join an existing ledger:** select an **existing ledger** by supplying its exact raw signed genesis block with `--genesis-file` and confirming its genesis signer’s full 32-byte Ed25519 public key (ledger ID), together with an explicitly verified full-genesis SHA-512 pin. Adopt its already-established genesis authority and reconstruct the database solely by replaying authenticated ledger events. The joining instance keeps **its own persistent signing identity** even when it joins as a replica; that public key has no master authority until authorized by canonical grant history. A populated unrelated database cannot join.

**CONFIRMED:** A genesis block uses the same fixed binary envelope as other blocks but **requires raw `ledger_id[32] == signer_public_key[32]` exactly** and has an **empty payload** (`payload_size=0`, compression `0x00`, SHA-512 of the empty bytes). Its outer Ed25519 signature is verified against the public key in the header, which is also the permanent ledger ID and initial authorized master key. Ordinary non-genesis blocks may not claim genesis status merely by being self-signed.

**CONFIRMED trust safeguard:** Joining pins both the trusted `ledger_id_hex` and SHA-512 of the full signed genesis block. Persist the binding in `ABC/instance.identity.json` outside rebuildable `ABC.DLDB`; there is **no `.DLID`**. The support directory is deterministically the resolved database basename (`ABC/`), and the manifest records the stable instance GUID/public key and pinned ledger identity. A different signed genesis cannot become trusted by matching ledger ID alone: verify its self-signature, require ledger ID = signer key, and require the exact **already pinned SHA-512 of the complete signed genesis bytes**. A different validly signed genesis with the same ledger ID is `GENESIS_CONFLICT`, rejected without quarantining/invalidation of the pinned authentic genesis or altering its authorized history.

**ARCH-012 Owner-approved version transition:** The approved 32-byte ledger ID cannot fit the former 1.01 (`0x0101`) 16-byte ledger GUID field. **The active signed protocol is 1.03 (`0x0103`, bytes `01 03`)**, with a 163-byte header, 227-byte empty genesis, and `DDL-REVOKE-v3` domain-separated 165-byte revocation consent. Historical 1.02 used a different revocation format. The former 1.01 (`0x0101`, 147-byte header/211-byte genesis) and historical 1.00 (`0x0001`) are distinct incompatible signed formats and MUST NOT be silently reinterpreted, truncated, upgraded, or re-signed. Unknown signed versions are rejected without durable retention in Phase 1. **`DDLB` container `0x0001` and signing-key JSON Version 1/AAD 88 bytes are independent and unchanged.**

**Owner-approved onboarding:** A genuinely new, demonstrably empty and unconfigured `.DLDB` with no evidence of earlier instance state may explicitly offer new-ledger creation or join-existing-ledger. The operator must invoke initialization; ordinary startup never creates a signing identity. `instance init` first durably saves the key and instance manifest; `ledger init` signs genesis with that existing key. `ledger join` requires the ledger ID plus discovery/validation and explicit confirmation of the complete signed-genesis SHA-512. Missing trusted genesis or identity evidence blocks binding. The mere absence of the `ABC/` folder is **not proof** of a new instance.

A nonempty or previously initialized `.DLDB`, remaining identity/key/ledger remnants, or mismatched metadata is **not** a fresh instance. Enter `recovery_required`, pause all ordinary SQL and ledger operations, keep diagnostics and original-identity recovery available, and never silently create replacement identity/genesis. A deliberate new identity is a different instance.

## 4. Canonical chronological order and clocks — CONFIRMED

**OWNER-APPROVED 2026-11-09 AMENDMENT TO VERSION 1 CANONICAL ORDER:** Accepted blocks are ordered by the tuple **`(timestamp_utc_ms, block_guid, signer_public_key)` ascending**. Timestamps are signed 64-bit integers representing **milliseconds since 1970-01-01T00:00:00Z**. Compare block GUIDs using their canonical 16-byte RFC 9562 binary representation; then compare signer public keys using raw 32-byte Ed25519 unsigned lexicographic bytes, not Base64 or locale-dependent text. The block GUID is the **secondary** tie-break and signer key the **tertiary** tie-break. Masters should synchronize clocks frequently against an agreed trustworthy UTC reference, preferably atomic-clock-backed. Two local publications may share a millisecond; the UUID and signer public key provide the approved deterministic tie-breaks. Never advance a timestamp into the future merely to avoid ties. This rule is authoritative for authorization replay, conflicts, field precedence, recovery and event-derived state.

**Owner-accepted historical signing-key compromise risk (unchanged in 1.03):** A stolen authorized master signing key can create backdated blocks, including grants, and cause canonical historical authorization and projection to be recomputed retroactively, potentially compromising the whole ledger. This is knowingly accepted. No timestamp cutoff, unilateral revocation exception, or new finality protocol is added.

**Separate creation from reception (ARCH-013 Owner approval):** Every locally authored block—including genesis, grants, data and the final revocation—takes its **official header timestamp from the instance's current UTC clock at creation**, using `DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()` or the equivalent OS UTC clock. Neither `block publish` nor any normal public signing API accepts a user-supplied official timestamp or a historical timestamp override. The revocation's *separate consent timestamp* is generated earlier by A, as specified in §6.3; B's final header timestamp is independently current UTC. These are operational authoring requirements, not a cryptographic timestamp authority. A malicious master key-holder may still forge times; the Owner accepts that risk.

**Incoming signed history:** Do not overwrite or restamp signed timestamps when forwarding, importing or replaying old/out-of-order blocks. No block is rejected *solely* for a past/future timestamp; verify the active version, signature, ledger identity, historical authority and applicable event rules (including the two-timestamp 15-minute revocation interval) at its canonical signed position. Arrival order never determines canonical order. Missing history means incoming acceptance is deferred **without durable retention**, not treated as authorization.

**CONFIRMED updated tie behavior (Owner 2026-11-09):** Equal-millisecond timestamps, including grants and revocations, are resolved by raw block GUID **before** raw signer public key, never arrival order. This expressly replaces the October 23 v7 **signer-before-block-GUID** rule and can produce a different canonical result if two signed blocks share a timestamp. **Historical chronology:** The canonical-order amendment did not alter block bytes; the Owner subsequently approved **1.01 (`0x0101`)** to replace historical `0x0001` value/column encoding. ARCH-012 adopts the subsequently Owner-approved **1.02 (`0x0102`)** signed wire with the full 32-byte ledger identity. Do not mix implementations using the former signer-before-block-GUID order or historical wire grammar; no released ledger migration is required. **CONFIRMED 2026-10-22:** SQL leap-second literals with seconds field `:60` are rejected, not normalized by local clock rules. Operational time synchronization methods remain implementation choices. No clock-skew quarantine is required.

## 5. Custom binary block wire format — OWNER-APPROVED PROTOCOL 1.03

Blocks are raw binary, not JSON, Base64, CBOR, or serialized SQL. The layout is packed, with no alignment padding. Multibyte integers use **big-endian** byte order and GUIDs use canonical RFC 9562 byte ordering. Fields are laid out sequentially:

| Field | Encoding | Bytes | Zero-based offset |
|---|---|---:|---|
| `version` | unsigned 16-bit big-endian, `0x0103` | 2 | 0–1 |
| `ledger_id` | **original genesis Ed25519 public key, raw bytes** | **32** | **2–33** |
| `block_guid` | raw RFC 9562 UUID bytes | 16 | 34–49 |
| `timestamp_utc_ms` | signed 64-bit epoch milliseconds, big-endian | 8 | 50–57 |
| `signer_public_key` | Ed25519 raw public key | 32 | 58–89 |
| `payload_sha512` | raw SHA-512 digest | 64 | 90–153 |
| `payload_size` | unsigned 64-bit byte count, big-endian | 8 | 154–161 |
| `payload_compression_type` | unsigned 8-bit | 1 | 162 |
| `payload` | exact transmitted bytes | N | 163 through 162+N |
| `signature` | Ed25519 signature | 64 | 163+N through 226+N |

The header length is **163 bytes**; the signature is **64 bytes**; each entire block is **227 + N bytes**, with `N = payload_size`. **For the approved 1.03 protocol, the first two bytes are `01 03` (hex), including genesis. Historical 1.02 (`01 02`), 1.01 (`01 01`), and 1.00 (`00 01`) are incompatible signed protocol versions and must not be silently interpreted with this grammar.** `version` uses 2 bytes, and `payload_size` uses 8 bytes, permitting values beyond 4 GiB subject to practical resource restrictions. The payload field is not Base64 encoded. 

**Hash:** `payload_sha512 = SHA-512(exact transmitted payload bytes)`; this includes any internal compression properties within those bytes. **Signature:** Ed25519 signs the complete exact serialized block bytes from `version` through the last byte of `payload`, excluding the trailing 64-byte signature. The verified signature authenticates header, timestamp, signer's public key, compression method, payload length, hash, and payload. Ed25519 is a signature scheme, **not symmetric encryption**; the data are public. AES-256-CBC is not used to authenticate blocks.

**Compression type — CONFIRMED:** `0x00` = uncompressed raw event payload; `0x01` = **raw LZMA2** compressed event payload, not a `.7z` archive or Base64. For `0x01`, the first byte **inside `payload`** is the LZMA2 decoder-property byte `p`, followed by the raw compressed stream; the property byte is included in `payload_size` and in the transmitted-payload SHA-512. Version 1 encoding uses **`p=20`, a 4 MiB dictionary**. Other dictionary properties are reserved for future protocol versions. Decoding must require the LZMA2 end-of-stream marker and reject trailing garbage. The signature and SHA-512 digest are checked over transmitted bytes before decompression. Other compression type IDs are reserved. Compression is optional for small events.

**CONFIRMED resource and pre-persistence validation policy (ARCH-014 controls):** Configure limits for raw input, decoded payload, CPU/processing time, memory, decompression, and peer resource use. The 64-bit outer payload length is a wire capacity, not permission for unbounded allocation. Validate framing/version, event type, payload hash, Ed25519 signature, ledger/genesis binding and historical signing authority using bounded **volatile memory before any new input is written to a temporary file, `.BLK`, or `.XBLK`**. Invalid, unauthorized, or authorization-unresolved incoming bytes must not affect official materialization or durable history; missing historical authority returns `AUTHORITY_UNRESOLVED` (retryable after relevant evidence arrives), known false authority returns `NOT_AUTHORIZED`, and unknown signed versions return `UNSUPPORTED_VERSION` without retention (`opaque_count=0`). **Never create an incoming pending/quarantined `.XBLK`.** Only a **previously accepted** `.BLK` that later becomes inapplicable may transition to local `.XBLK` (§22). Oversize or resource-exhausted input fails with bounded structured diagnostics, without uncontrolled CPU/memory growth. **Default configurable Phase 1 limits:** maximum raw received block **16 MiB**, maximum decompressed event **64 MiB**, maximum in-flight import memory **128 MiB**, per-block processing timeout **60 seconds**. Preserve other practical CPU, memory and peer/network bounds; exact setting names and supported ranges are in Management API §13.6.

## 6. Binary event payloads — OWNER-APPROVED PROTOCOL 1.03 ENVELOPE AND FIVE-CLASS PAYLOAD GRAMMAR

**Active 1.03 wire:** The signed-block envelope retains the 32-byte ledger identifier and 163-byte layout first introduced in historical 1.02; compared with 1.01, fields after the ledger identifier moved 16 bytes. The active version field is `0x0103`. The **five-class value and column-definition payload grammar** is inherited unchanged from 1.01 (and remains incompatible with historical 1.00 `0x0001`). Each non-genesis block contains one binary typed event (`event_kind:uint8` first), never source SQL. For DML, each changed row is one independent signed block; a statement affecting multiple rows is not a ledger-atomic group. Tables, columns and rows retain immutable 16-byte GUID identities. Updates transmit only changed column GUIDs and resulting values.

### 6.1 Event kinds — protocol 1.03

| Code | Event | Uncompressed body following `event_kind` |
|---|---|---|
| `0x01` | `INSERT_ROW` | `table_guid[16] || row_guid[16] || column_count[varuint] || repeated(column_guid[16] || typed_value)` |
| `0x02` | `UPDATE_ROW` | Same structure as INSERT; **only changed columns** |
| `0x03` | `DELETE_ROW` | `table_guid[16] || row_guid[16]` |
| `0x10` | `CREATE_TABLE` | `table_guid[16] || table_name[text] || column_count[varuint] || complete column definitions in declared order` |
| `0x11` | `DROP_TABLE` | `table_guid[16]` |
| `0x12` | `RENAME_TABLE` | `table_guid[16] || new_name[text]` |
| `0x13` | `ADD_COLUMN` | `table_guid[16] || complete column definition` |
| `0x14` | `DROP_COLUMN` | `table_guid[16] || column_guid[16]` |
| `0x15` | `RENAME_COLUMN` | `table_guid[16] || column_guid[16] || new_name[text]` |
| `0x16` | `ALTER_COLUMN` | `table_guid[16] || complete resulting column definition with same GUID` |
| `0x20` | `GRANT_MASTER` | `grantee_public_key[32]` |
| `0x21` | `REVOKE_MASTER` | `revoked_public_key[32] || countersigner_public_key[32] || consent_timestamp_utc_ms[8] || countersignature[64]` (137-byte uncompressed event including kind; §6.3) |

All GUIDs are RFC 9562 network-byte-order; `varuint` is minimal unsigned ULEB128, and `text` is minimal ULEB128 UTF-8 byte length followed by those exact bytes (no terminator). DML entries are sorted by raw column GUID, with duplicates rejected. A zero-count UPDATE is a no-effect shape; actual SQL writes with no changed values need not create blocks.

### 6.2 Value and schema grammar — SQLite-native Version 1.03 (same five-class encoding as 1.02)

| Tag | SQLite storage class | Bytes after tag |
|---|---|---|
| `0x00` | `NULL` | None |
| `0x01` | `INTEGER` | Signed int64 using ZigZag and minimal unsigned ULEB128 (1–10 bytes) |
| `0x02` | `REAL` | IEEE-754 binary64, exactly 8 bytes big-endian; see approved NaN/∞/−0 rules below |
| `0x03` | `TEXT` | Minimal ULEB128 byte count followed by UTF-8 text bytes |
| `0x04` | `BLOB` | Minimal ULEB128 byte count followed by arbitrary bytes |

**IEEE-754 REAL rules (approved under ARCH-010 and unchanged in active 1.03):** A `0x02` value carries exactly eight IEEE-754 binary64 bytes in network/big-endian bit order. Accept all finite numbers, signed subnormals, **positive and negative infinity**, and both zero sign-bit patterns. Preserve the exact eight signed bytes on decoding, retention, forwarding, and re-export: positive zero `0000000000000000` and negative zero `8000000000000000` are distinct *wire encodings*, even where SQLite treats them as numerically equivalent or normalizes the sign through storage/affinity. Infinity examples: `7ff0000000000000` and `fff0000000000000`. **Reject every NaN encoding** (all sign bits, exponent bits all one, nonzero fraction, whether quiet or signaling) as `BAD_EVENT`; do not rewrite incoming signed bytes to SQL NULL. An originating *SQLite* SQL expression/bind that SQLite converts from NaN to SQL NULL is encoded as the `0x00` NULL tag, never as an illegal REAL NaN. Independent `block publish` likewise rejects a REAL NaN rather than normalizing a supplied event file. Never claim projected SQLite will round-trip the sign of negative zero; the signed ledger retains its exact originating bytes. The same signed-byte rules apply on all platforms. Reject a REAL payload shorter/longer than eight bytes and never silently cast incoming wire values to a different storage class.**

All other value tags are invalid for `0x0103`. There is **no** separate wire `DECIMAL`, `DATETIME`, `BOOLEAN`, or `GUID` value type; application values use the storage class actually produced by SQLite. Internal row/table/column and block GUID identities remain unchanged; the former ledger GUID is replaced with the approved 32-byte genesis-key ledger ID. Column declarations such as `VARCHAR(100)`, `DECIMAL(10,2)`, or `BOOLEAN` are retained as declared SQL type **text** and interpreted by SQLite affinity rules, not translated into extra value tags. The ledger promises SQLite-native precision, **not** arbitrary-precision decimal arithmetic. Preserve the actual SQLite storage-class result after affinity and expression evaluation rather than coercing to an invented type. For supported TEXT, transfer exact UTF-8 bytes without Unicode normalization; unsupported conversion of invalid text bytes must fail explicitly, or applications may store arbitrary bytes as BLOB. Resource limits apply.

**Row NULL/omission:** An UPDATE omitting a column leaves it unchanged, whereas an entry with `0x00` assigns NULL. INSERT omits NULL-valued fields, including explicit SQL NULL; a missing field is NULL unless the supported typed-constant schema default was evaluated at the originating master and included as a concrete value. `UPDATE ... SET column=DEFAULT` similarly captures the evaluated result. A zero-column INSERT is valid. On replay, defaults are **not** re-evaluated; no arbitrary fallback value is synthesized.

**Complete column definition (exact ordered bytes, no padding):**

```text
column_guid[16]
name_length[varuint] || name_utf8

declared_type_length[varuint] || declared_type_utf8
column_flags[1]
default_presence[1]
optional_typed_default
```

`column_flags` bit 0 is 1 for nullable, 0 for NOT NULL; all other bits must be zero. `default_presence` is `0x00` (none) or `0x01` (followed by one typed value, including NULL). `name_utf8` and `declared_type_utf8` preserve the originating supported SQL identifiers/declaration text exactly in UTF-8; an empty declared type is allowed where supported by SQLite. The type text, not a numeric declared-type tag, controls native SQLite affinity. `CREATE_TABLE` includes full definitions in declared order, while row change entries are sorted by GUID. Unsupported SQLite schema features or expressions that cannot be represented and replayed deterministically (such as unrepresented generated columns, triggers, virtual tables, collations, constraints or expression defaults) must be **rejected before publication**, never silently dropped. The supported SQL surface must be explicitly qualified by Developer/QA; no claim of full SQLite syntax support is made by this grammar.

**Version separation:** The historical `0x0001` wire grammar with nine value tags and tagged declared types, and the incompatible 1.01 signed envelope with its 16-byte ledger GUID, are not accepted as active protocol `0x0103`. The Owner accepted the standalone signed-ledger Step 1 at Protocol 1.03 on 2026-11-18; any independently generated 1.01 trial data must still be handled explicitly rather than silently reinterpreted or re-signed. The approved 1.02 envelope uses a 227-byte empty genesis and versioned countersigned revocation intent; Ed25519 full-block signing, event-kind codes and `DDLB` outer batch framing retain their existing semantics. Canonical replay still sorts `(timestamp_utc_ms, block_guid, signer_public_key)`.

### 6.3 Second signature on revocation — OWNER-APPROVED protocol 1.03, two timestamps

**Roles and public authorization:** The first master (**A**, the countersigner) creates signed consent. A second distinct master (**B**, outer block signer) validates it and publishes the final `REVOKE_MASTER` block using B's **current UTC clock**. The revoked target must equal either A or B; in the Owner's motivating workflow, B revokes itself. Both A and B must be historically authorized at the **final block's canonical position** before the revocation is accepted. A also checks known current authority before issuing consent; neither signature alone authorizes revocation. The original genesis signer public key remains the immutable 32-byte ledger ID even if later revoked. Revocation takes effect through ordinary canonical event processing, after its own signed position. The target's original grantor has no special role.

**A's consent message (`DDL-REVOKE-v3`; exact 165 bytes):** A independently generates the intended `block_guid` (new random UUID) and `consent_timestamp_utc_ms = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()`; neither time nor GUID is supplied by the command caller. Concatenate bytes exactly (no NUL, framing, separators or padding):

| Field | Bytes | Offsets (zero-based) |
|---|---:|---:|
| ASCII `DDL-REVOKE-v3` (13 bytes) | 13 | 0–12 |
| `ledger_id[32]` — verified bound genesis signing key | 32 | 13–44 |
| `block_guid[16]` — A-generated | 16 | 45–60 |
| `consent_timestamp_utc_ms` — signed int64 BE | 8 | 61–68 |
| `outer_signer_public_key[32]` — B | 32 | 69–100 |
| `revoked_public_key[32]` — revocation target | 32 | 101–132 |
| `countersigner_public_key[32]` — A | 32 | 133–164 |

A signs these exact 165 bytes with its own Ed25519 identity, producing a 64-byte signature. The CLI/library produces an exact **229-byte portable consent package**: `consent_message[165] || consent_signature[64]`. The public-key and ledger-binding fields inside this package are independently verified by B; never trust them merely because they parse. No private signing seed is exported.

**B's final signed block:** B reads and authenticates A's complete 229-byte consent package in memory, verifies all identities/roles, then reads its **own current UTC milliseconds** and constructs a protocol `0x0103` block with the **same A-generated block GUID**. The **official** `timestamp_utc_ms` is B's current UTC timestamp, *not* A's consent timestamp. The exact **137-byte uncompressed `REVOKE_MASTER` event** (including kind) is:

| Field | Bytes | Offsets (zero-based within uncompressed event) |
|---|---:|---:|
| kind `0x21` | 1 | 0 |
| `revoked_public_key[32]` | 32 | 1–32 |
| `countersigner_public_key[32]` — A | 32 | 33–64 |
| `consent_timestamp_utc_ms` — signed int64 BE | 8 | 65–72 |
| `countersignature[64]` — A | 64 | 73–136 |

B signs the entire 163-byte header and transmitted payload with B's persisted Ed25519 key (64-byte outer signature). All receiving verifiers reconstruct the exact 165-byte `DDL-REVOKE-v3` message from the signed **block** fields (ledger ID, block GUID, B's public key, revoked target, A's public key) plus the payload's signed **A consent timestamp**, and verify A's signature. The block's signature authenticates both timestamps and the consent signature; A's signature authenticates its own timestamp and the precise revocation intent, but **does not** purport to authenticate B's later official timestamp.

**Deterministic 15-minute consent validity:** `delta_ms = block.timestamp_utc_ms - consent_timestamp_utc_ms` must satisfy **`0 <= delta_ms <= 900000`**, with checked integer arithmetic; 900001 ms, negative deltas, malformed consent or mismatched fields fail. Apply the rule on both local publication and every later import/replay, using only the **two immutable signed timestamps**, not receipt time or the verifier's local clock. When expired before a durable final block was published, obtain a new A consent package with a newly generated block GUID. If the exact original block was durably published before a crash, retry is idempotent and must not publish a different variant reusing its GUID. Validate historical authorization of both signers at the final block position; new earlier grants/revocations can still cause subsequent re-evaluation. A malicious holder of an authorized master's key can forge signed timestamps outside the official implementation; this accepted threat is not solved by this operational clock rule.

**Version separation:** The 1.02 `DDL-REVOKE-v2` 165-byte message and 129-byte event are **historical**. Protocol 1.03 MUST reject 1.02 signed blocks, 1.02 consent messages, and any 1.02-style event payload under an `0x0103` header; no implicit translation or re-signing. Signed header length **163**, empty signed genesis length **227**, and DDLB Version 1 are unchanged from 1.02. The unrelated signing-key JSON Version 1 / 88-byte AES-GCM AAD, manifest Version 2, and instance-config Version 1 are likewise unchanged.

### 6.4 Protocol specification boundaries

For the active signed-wire `0x0103`, §6.1–§6.2 fully specify the five value tags and column-definition byte order. SQLite native type affinities and actual storage classes determine authored values. Unsupported expression/schema surfaces fail without ledger publication or official storage effects. Exact Phase 1 CLI and timestamp fallback rules are in the current SQLite management specification; subsequent SQL gateway implementation must publish concrete results and never bypass authenticated blocks. Earlier PostgreSQL-specific type/cast documents and the `0x0001` nine-type grammar are historical, not controlling.

## 7. Deterministic reconciliation and conflict semantics — CONFIRMED

A node durably retains only newly received blocks fully validated *in memory*, including the signer **against canonical authorization history**, then derives the current schema and rows from applicable events in canonical order. **Later modifications win over earlier modifications to the same affected field** unless a deletion applies; **deletions always win for the same immutable entity GUID**, including after earlier or later updates. The same rule applies to rows, columns, and tables. A deleted row/table/column cannot be recreated with the same GUID.

A delayed update to a GUID for which its earlier INSERT has not yet arrived is retained and logged as temporarily inapplicable; it has no visible effect until the missing earlier INSERT is received and the entity can be reprojected. Operations that cannot yet be interpreted because schema blocks are missing are similarly logged and reconsidered after recovery of dependencies. **A valid block is never ignored or permanently excluded solely because it arrives late or has an earlier timestamp.** When an earlier block changes the canonical interpretation of materialized history, the node **must correct the official projection**: it may roll back/recompute affected rows, schema and dependencies, or rebuild its materialized database **from genesis and the retained relevant full ledger history**. Rebuilding from scratch is conforming, even if slower. Any partial/recovery representation must not pretend the late valid block never existed. An **incoming** block lacking established historical signing authority is rejected in volatile memory **without persistence**, even if its timestamp is old; it may be reimported when missing signed authority history becomes available. In contrast, a cryptographically valid and **authorized** block with missing schema/entity dependencies may be durably retained for later Phase 3 projection without becoming `pending_count` for signing authority. A **previously accepted** block later made authorization-unresolved by earlier arriving signed history may be preserved as local `.XBLK` under the approved archive rules. Unrelated rows need not be rolled back when selective replay is proven safe. Immutable event history itself never rolls back; only the derived materialized database state can be corrected. A raw block may remain retained even where later validation makes it unauthorized/inapplicable; it must not affect the projection.

**No secondary events from normal replay; all logical corrections are ledger-first — CONFIRMED:** Applying or replaying an ordinary block does not publish another block merely as an echo. Only an authorized master may originate a separate signed corrective event for any ledger-derived logical inconsistency, including a name collision, disallowed NULL, incompatible value, datatype or schema inconsistency, or any other automatic logical data/schema repair. Every such correction, including one proposed by the local master, must first become authenticated ledger history and then be ingested and applied through the same normal ledger pipeline used for remotely received events. No automatic correction may directly alter official database data or schema. A proposed or durably retained correction is not yet official materialization: the affected state remains unresolved until its applicable authenticated correction is ingested and applied. A read-only replica may recognize, retain and diagnose an inconsistency and apply a master's authenticated corrective history; it must not independently originate corrective blocks, generate replacement identities/names/values for official state, or mask a problem with an unsigned change. This prohibition does not prevent required local replay or reconstruction that derives a projection from already-authenticated events. Physical storage maintenance and ordinary supported lossless interpretation of recorded values are not permission to invent a new logical repair. The ledger does not distinguish human-proposed from automatically proposed signed changes.

## 8. Schema identity, name collisions, and conversion — CONFIRMED

Every table and every column has an immutable GUID. RENAME_TABLE and RENAME_COLUMN preserve that GUID. Concurrent rename events targeting the same GUID settle by the latest valid canonical event, unless deletion applies. A dropped column supersedes updates targeting it. Recreating a same-name table or column uses a new GUID; deleted GUIDs cannot be reused.

If distinct entities are created under the same SQL-visible table name, or the same column name within one table, both entities survive. The entity introduced first in canonical **creation-block order** retains the original name. Entity-GUID numerical order and receipt order do not determine priority. An authorized master proposes a separate signed corrective rename for a later-created conflicting entity. The ordinary first correction spelling is exactly `original-name-entityGUIDwithoutdashes`, using the complete dashless entity GUID. Neither ordinary replay nor a read-only replica independently invents this rename.

**Identifier-length fallback — latest owner decision:** For the PostgreSQL adapter's 63-byte SQL identifier limit, measure the proposed corrected SQL-visible name in UTF-8 bytes. If the required corrected name would exceed 63 bytes, the authorized master generates a fresh random UUIDv4 unrelated to the entity GUID, ledger ID and block GUID. Use that UUID's lowercase canonical hyphenated textual representation as the entire replacement name, rather than truncating the required name or its GUID suffix. The random replacement is a name value, not a replacement entity identity, ledger identity or block identity. Carry that exact name in a separate signed RENAME_TABLE or RENAME_COLUMN event identifying the original target entity GUID. SQL quoting does not change the byte limit. Other database adapters' identifier limits belong in their own public adapter contracts; this paragraph does not silently impose a new protocol-wide wire-name length or truncate received names.

The originating master must ingest and apply its own signed correction through normal authenticated ledger processing before that name becomes official. Proposing a rename, publishing it or durably retaining its block alone leaves the affected official name unresolved. The same rule applies to all automatic logical value/NULL/schema corrections. Until application, name resolution must not arbitrarily choose one GUID or discard either entity; the visible ambiguity or error is deterministic for the applied history. Replicas may apply authenticated corrective history but never independently originate a correction or substitute an unsigned name/value.

Signed automatic and user-initiated renames are ordinary rename events under the same canonical ordering, authorization, identity and delete-wins rules. Preserve all valid independently signed corrections. If masters propose different random replacement names for one entity, each event carries its own literal chosen name; the latest applicable canonical rename determines the resulting name for that GUID. Consumers and reconstruction never rerun random name generation. Participants with different known history may temporarily differ; participants with the same complete applicable history derive the same result. No requirement makes independent masters choose the same random UUID.

If a corrected name conflicts again, an authorized master must resolve the remaining conflict through another distinct signed rename, adding another newly generated GUID-based suffix as needed under the ordinary rule. If that proposed corrected name exceeds the PostgreSQL limit, apply the random-UUID fallback again. Random UUIDs do not guarantee a name is collision-free; a remaining collision is diagnosed and resolved by further valid signed history, not by an unsigned local edit or arbitrary winner. Canonical first-creator precedence and the latest valid explicit rename rules remain in force. Do not suppress earlier signed history, repeatedly emit identical corrections for unchanged known state, or create an uncontrolled replay-triggered correction cascade. Convergence describes replay of the same history, not a bound on the number of future independently proposed corrections.

On a column datatype change, apply only declared supported lossless conversions automatically. An incompatible value is retained/diagnosed unresolved, not silently replaced. If a nullable column may be corrected to NULL, a master may publish that explicit value in a separately signed row correction. Otherwise an authorized master explicitly selects a valid corrective value or applicable typed constant default and publishes it in a new signed UPDATE_ROW block. Never invent zero, empty text, epoch minimum or another arbitrary fallback. Every receiving node, including the origin, changes the official logical value only by authenticating, ingesting and applying that correction. Replicas wait for such signed history. Operational progress/diagnostics and failed reconstruction follow Section 10; exact interim SQL error conventions remain in the adapter contract.

For the PostgreSQL adapter, newly submitted SQL identifiers longer than 63 UTF-8 bytes are rejected rather than silently truncated. Authenticated historical names outside the adapter's representable range are retained and diagnosed without inventing an alternate name or changing identity. This input rule is distinct from the automatic-correction overflow fallback above.

## 9. SQL semantics, constraints, and transactions — CONFIRMED

**Current SQLite SQL adapter (Owner-approved 2026-11-07):** Preserve the normal SQLite SQL client interface and C API for **supported** queries and mutations. SQL writes on a master are evaluated provisionally and converted to authenticated ledger events; the official `.DLDB` database is changed **only** by the authenticated projector, which operates independently of publication. Replicas reject user SQL mutation attempts. Historical PostgreSQL-only `COPY`, `MERGE` spelling, command tags and `ZL001`/`ZL002`/`ZL003` SQLSTATE conventions in this section document the prior adapter and are **not mandatory SQLite syntax or error fields**. The SQLite SQL subset, precise error mapping, DECIMAL expression semantics and full API interception boundary must be specified and tested; unsupported mutation paths fail safely rather than writing directly. The existing portable effective-transaction and honest partial-publication guarantees still apply.


The signed-ledger model **does not automatically enforce ordinary relational application constraints** such as primary-key uniqueness or foreign-key referential integrity when deriving authoritative changes. Two rows with different row GUIDs may contain identical business primary keys. Ledger deletions are not vetoed by referencing rows or application locks. Internal storage integrity and synchronization cannot be disabled merely to bypass these application-level rules. User-defined triggers, stored procedures, user-defined functions with effects, and comparable user-defined implicit write facilities are **not supported in Version 1**. This excludes their use as alternate mutation paths; it does **not** require removing SQL built-ins or internal database functions necessary for parsing, expression evaluation, data conversion, indexing, recovery, or supported SELECT/DML. The previously discussed PostgreSQL support matrix below is retained only as historical context; the active SQLite SQL subset remains a later Phase 2 native-interception qualification gate. No PostgreSQL-only command or error contract automatically applies to SQLite. Indexes and SELECT/query support may be used for efficient materialization and reads.

**HISTORICAL PostgreSQL-only SQL scope (not the current SQLite support matrix):** The earlier adapter required ordinary `SELECT`, `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `INSERT`, `UPDATE`, and `DELETE`, with `BEGIN`, `COMMIT`, `ROLLBACK`, and savepoints for provisional local staging. **Additional approved entry paths:** `COPY FROM STDIN` (bulk inserts), `COPY TO STDOUT` (read-only export), `MERGE` (its per-row insert/update/delete effects), and `RETURNING` (reports values from locally evaluated changes). Every resulting row change from `COPY` or `MERGE` must publish its own authenticated ledger block **before official materialization**; none may bypass the same authority rules. `RETURNING` reports locally calculated result values, which are **provisional with respect to later block publication and local projection visibility**. The caller may receive `RETURNING` rows before the corresponding signed block is durably published and before the official SELECT-visible projection catches up. This is an accepted application-design responsibility, not a requirement that the engine make RETURNING synchronously visible. `RETURNING` must not be represented as proof that a multi-block COMMIT is atomic or entirely durable, and statement results may precede later publication failures. `COPY FREEZE`, `COPY PROGRAM`, unsupported user-defined triggers, stored procedures, user-defined functions **with side effects**, and other unapproved mutation paths must be rejected or made unavailable rather than allowed to bypass ledger-authoritative changes. PostgreSQL internal built-ins necessary for supported SQL remain available. This is a baseline feature subset, not a promise to preserve unsupported SQL extensions or direct writes. The accompanying PostgreSQL SQL/execution contracts define required MERGE branches, expression/join/CTE forms, lossless type mappings, utility restrictions and result/error conventions; genuinely unspecified advanced SQL forms are identified there, without narrowing the approved command categories.

SQL clients can use provisional transactions. `BEGIN` starts uncommitted isolated changes; `ROLLBACK` and savepoint rollback discard staged work without emitting blocks. No publication occurs before COMMIT. At COMMIT publish final effective provisional row changes (Option A): an existing row changed 1 → 2 → 3 produces one UPDATE_ROW carrying 3; a row restored 1 → 2 → 1 needs no effective row-change block; INSERT then UPDATE produces one final INSERT_ROW; INSERT then DELETE has no surviving row event; UPDATE then DELETE produces one DELETE_ROW. Preserve appropriately qualified provisional RETURNING values and statement counts for the supported SQLite SQL surface; PostgreSQL-specific command-tag rules are historical. Every independently effective changed row still requires its own signed block. DDL must preserve immutable entity identities, valid dependencies and reconstructible final state, without an arbitrary schema-event count or publication order; unpublished DDL folding is permitted rather than a mandated representation.

Publication is **not group-atomic**. If a crash leaves only 60 of 100 intended blocks durably published, those 60 are permanent ledger history; remaining blocks may never exist. The materialized official database is updated only by authenticated ledger ingestion, including at origin, not by the provisional transaction directly. If the origin can determine that COMMIT stopped after publishing only some intended blocks, it must report failure or explicit partial completion accurately, never claim atomic rollback of already durable blocks. Network disconnects may leave the client uncertain; they do not annul independently durable blocks. Resumable publication is optional, not a fundamental ledger requirement. Applications must handle missing/partial outcomes and stronger business atomicity at a higher layer; compensating operations create new blocks and do not erase history.

Ordinary offline master writes do not wait for cross-master acknowledgment. A higher-assurance application may implement independent locks/reservations and require all masters' confirmation, recognizing that such applications can block during partitions and still need a true protocol to prevent simultaneous conflicting reservations.

**HISTORICAL PostgreSQL SQLSTATE outcome mapping (not an active SQLite requirement):** Preserve normal PostgreSQL command tags/affected-row counts for supported SQL, including matched-but-unchanged rows where applicable. A failed partial `COMMIT` must not return ordinary full success. When the origin can determine partial publication, report a distinct SQLSTATE `ZL001`, an explicit partially-published status, and the known durable block count and GUIDs; durable blocks remain ledger history. When the outcome cannot be determined due to connection loss, do not imply rollback; `08007` can be used where the server can report uncertain transaction resolution, otherwise the client must inspect durable ledger history. Previously emitted `RETURNING` values remain locally evaluated provisional information and do not imply publication or immediate SELECT visibility. Application software, not the ledger database, is responsible for business workflows that require immediate read-after-write visibility or all-or-nothing multi-block results. The accompanying execution/management/SQL contracts define PostgreSQL error fields, JSON DETAIL and supported expression/CTE/cast/error conventions. Request resumption remains optional; it is not required as an implicit retry guarantee. Explicit NULL-versus-omission semantics are now specified in Section 6.2. The initial system makes no promise that ordinary SQL semantics imply global transaction finality.

## 10. Materialization priority, durability, and recovery — CONFIRMED

**Previously accepted signed-history integrity and phase boundaries (QA-013 / Owner clarification):** Phase 1 must detect corrupted formerly accepted `.BLK` bytes whenever that history is checked for use (including verification for ordinary retrieval/export, authorization and recovery). Detection includes invalid framing, a mismatch to the signed block's known exact-byte SHA-512 identity, failed payload integrity or failed Ed25519 signature; a filename or cached `.STAT` is never proof of authenticity. An expected local block known to be missing is likewise an incomplete-history condition; Phase 1 does **not** claim to discover unknown remote blocks or provide automatic peer retrieval. Never authenticate, export, propagate or, in later phases, project damaged bytes as valid history. Preserve unchanged signed blocks, the existing instance key/manifest and pinned genesis, and available diagnostic evidence; do not silently delete, rewrite, re-sign, replace or hide corrupted history. A detected defect that prevents confidence in accepted local history places the **affected ledger** into diagnostic/recovery restrictions: allow status/diagnostics and original-identity protection, but do not acknowledge new authority-dependent publication/import, complete-history export or any derived state as healthy until the integrity problem is explicitly resolved. The existing `RECOVERY_REQUIRED` error is used for blocked ordinary ledger operations, with `error.details.reason="LEDGER_HISTORY_CORRUPT"` (or `LEDGER_HISTORY_INCOMPLETE` when an expected block is demonstrably missing); signing-key corruption remains independently identified as `SIGNING_IDENTITY_UNAVAILABLE`/`IDENTITY_MISMATCH`, not mislabeled as ledger corruption. No automatic block repair or peer discovery is a Phase 1 acceptance requirement; an operator may investigate or provide an independently verified original copy through a separate explicit recovery workflow, without altering the original identity or automatically overwriting retained signed files.

**Phase 3/4 boundary:** If unavailable or corrupt historical blocks are later restored, the Phase 3 SQLite projector must correct the derived database by a full authenticated deterministic replay when necessary; focused rollback/replay is only a possible future equivalent optimization. Phase 4 networking will discover/request missing or damaged history from participating peers, and will validate the exact recovered bytes, ledger ID, pinned genesis and historical authority **before** accepting any replacement as ledger history. If a valid replacement is unavailable, retain diagnostics and do not represent incomplete history as authoritative. Details of peer retry/transport and safe replacement remain Phase 4 work, not Step 1 completion criteria.

A newly received block must pass bounded in-memory framing, hash, signature, ledger/genesis binding and **historical authorization** checks before any persistence; a block whose authority is unresolved or false is rejected without temporary or permanent disk files. A validated authorized block must become durable in ledger storage before it can alter the official database. Master-originated blocks follow the same durable-ledger-before-projection rule. Phase 3 materializes only eligible ordinary data/schema blocks in canonical order, subject to the Owner-approved configurable projection-age delay (§20). During actual local reconciliation/rebuild, pause affected ordinary processing and protect SELECT consistency; prioritizing eligible local projection remains intentional. This never implies certainty that no missing blocks exist on the wider network. A master can operate while other masters are offline, apart from local synchronization needed to apply known blocks.

Crash-safe progress tracking and idempotent replay or reconstruction must ensure a crash between block durability and materialization can be recovered without permanently omitting or double-applying effects. **CONFIRMED 2026-10-22:** Late valid historical blocks and later-revealed earlier authority history must cause the projection to be corrected through safe rollback/replay of affected materialization **or a complete rebuild from authenticated ledger history**; no timestamp-age cutoff may permanently suppress those corrections. Master/replica outage, out-of-order delivery, partitions, and late authority changes may all require selective re-projection. The ledger itself is immutable; the projection is replaceable. Acknowledgment of successful ledger append implies local durable storage; a block lost with all copies is unrecoverable.

**CONFIRMED 2026-10-22 — local read barrier versus remote catch-up:** An ordinary `SELECT` must **not wait merely because peers may still hold unknown blocks**, because network completeness cannot generally be established. A node may serve a consistent, locally materialized but network-stale state until more blocks become known. Once a node undertakes a local projection modification, selective rollback/replay, or full rebuild to incorporate **blocks it already knows**, ordinary `SELECT` operations requiring that projection must wait until the current local reconciliation produces a consistent result; they must not observe an intermediate or partially rebuilt official state. A complete rebuild **must create a persistent diagnostic/error-log entry** explaining why the rebuild was necessary, the affected ledger/database, its outcome, and information sufficient for an operator to investigate. The entry is operational evidence, not an authenticated ledger block. Implementers may choose locking/projection-swap mechanisms, but must not indefinitely block `SELECT` solely to await hypothetical unseen network blocks. **CONFIRMED operational projection reporting:** Expose projection states `ready`, `reconciling`, `rebuilding`, and `failed`. A full rebuild must persistently log ledger ID, database identity, UTC start/end timestamps, reason, outcome, and error details when unsuccessful. If reconstruction fails, an affected SELECT must return a clear error rather than stale/inconsistent projected data. Under continuous block arrivals, a node must not starve SELECT indefinitely: it may reconcile a finite known batch to a consistent point, admit reads, and then incorporate later blocks. Implementation-specific WAL/cursor/checkpoint details remain free; exposed status must not claim an inconsistent projection is ready. Exact log encoding and error codes belong to operational API documentation. Rollback/replay versus full rebuild is an implementation choice; neither may ignore applicable earlier blocks.

## 11. Peer-to-peer propagation and offline exchange — CONFIRMED behavior and management interface

Every node may **receive and verify** an intact signed block regardless of whether it may originate blocks, but **new inbound blocks are stored/served/relayed/exported only after historical signing authority is established in memory**. Existing local `.XBLK` archives are excluded from normal propagation. Signed-block verification is transport-independent. Permit direct peer connections (TCP/QUIC or suitable supported protocols), decentralized peer discovery with configurable bootstraps, BitTorrent-inspired DHT, peer exchange, LAN service discovery, NAT traversal and relaying, HTTP(S), multipeer downloads, and real-time announcements. Nodes normally advertise new validated blocks to peers with resource/bandwidth controls. **No peer discovery or master quorum is necessary for an ordinary local write**.

Combine rapid announcements with periodic cryptographic **inventory reconciliation**, including Merkle-style summaries or equivalent, and comparisons by block ID/hash that do not depend exclusively on timestamps. Export and import must include individual blocks, timestamp ranges, a full ledger, and incremental missing-block batches; large whole-ledger archives can be imported as offline batch jobs, from arbitrary media. The ledger does not require a database to exist; a returning master can catch up through a read-only replica.

**HISTORICAL PostgreSQL v0.4 management context (superseded by SQLite Management API §§3, 13–17):** Earlier work used `--pgdata`/engine-specific instance selectors, proposed standalone CLI JSON and peer commands, and assumed an offline/localhost peer exercise. Those old command spellings, verifier artifact hashes, and same-GUID dispute/quarantine instructions are **not current UDDL Phase 1 requirements**. The authoritative SQLite management interface now supplies complete command flags, status, import/export, signing/recovery and error contracts; Phase 4 peer discovery/transport remains an engineering choice, subject to bounded resources, cryptographic authority and local-network acceptance. Legacy detail is preserved in Git history, not duplicated as active rules here.

**Current Phase 1 export and transport (ARCH-014):** `block get` emits the **exact original raw signed block bytes**; `block export` always emits a Version 1 `DDLB` container, including zero- and one-block selections. **DDLB Version 1 exact framing:** ASCII `DDLB` (4 bytes) || `uint16_BE(0x0001)` || `uint64_BE(block_count)` || `block_count` repetitions of (`uint64_BE(signed_block_length)` || exact signed-block bytes). No footer/trailing bytes; reject truncated/overlong/overflowing framing. The wrapper is unsigned transport framing and never modifies, re-encodes, re-signs, aggregates or vouches for a block; original headers, transmitted payload, SHA-512 digest and 64-byte Ed25519 signature remain byte-for-byte unchanged. Export active authorized `.BLK` only, in deterministic canonical order `(timestamp_utc_ms, block_guid, signer_public_key)`; no `.XBLK` or unsupported opaque version is exported or advertised. Exact identical blocks are idempotent duplicates. A **different** incoming signed variant reusing any retained `(ledger_id, block_guid)` fails `BLOCK_GUID_CONFLICT` (exit 4, nonretryable), with no write, overwriting, archival or identity-dispute arbitration. An invalid or authority-unresolved **new input is not retained**; archived `.XBLK` is restricted to formerly accepted history later invalidated. A partial DDLB import may retain independently accepted/durable items and must report other items individually; there is no all-or-nothing batch guarantee. Bounded resource constraints are in §5 and the Management API.


**Archived publication retry (Owner-approved ARCH-014 clarification):** Retrying the same explicit GUID and exact event/consent after the originally durable block has transitioned to `.XBLK` does **not** restore or re-sign it. Instead return `BLOCK_ARCHIVED` (exit 4, nonretryable), report original signed-publication metadata distinctly from current archived state, and leave all signed files and counters unchanged. A still-active exact match remains an idempotent success; different bytes return `BLOCK_GUID_CONFLICT`. The normative JSON/error details are in Management API §13.3.1.

**Current Phase 1 status vocabulary:** `retained` means cryptographically valid, currently authorized active `.BLK`, whether or not SQLite projection exists; `pending` and `quarantined` apply **only to previously durable `.BLK` history later reclassified into `.XBLK`** after late earlier historical authority evidence. No new unauthorized/unresolved input is written; return `rejected`/`AUTHORITY_UNRESOLVED` (retryable) or `rejected`/`NOT_AUTHORIZED` (currently nonretryable). Same-GUID nonidentical new inputs return `BLOCK_GUID_CONFLICT` without modifying retained history. Inclusive `retained_count` includes active `.BLK` and historically archived `.XBLK`; `disputed_count=0` and `opaque_count=0` in Phase 1. Projection backlog never increments `pending_count`. See Management API §§13.5, 14.1.

**Flood resistance / inbound validation — OWNER APPROVED IN-MEMORY GATE:** Every node must inspect every received block for framing, protocol version, well-formedness, hash/signature integrity, ledger identity, and signer authorization before it has any database effect. A hostile actor may flood arbitrary invalid blocks. Reject invalid inputs safely and limit untrusted resource consumption (including decoding, disk, CPU, memory and networking) without treating plausible timestamps alone as grounds for rejecting otherwise valid authorized blocks. An out-of-order block whose missing authorization evidence has not arrived must not be materialized before its authority is established. Exact inventory, caching and DoS budgets remain implementation choices.

## 12. Intended guarantees and deliberate non-guarantees

**Intended:** Public cryptographic origin/integrity verification, signed historical authorization, deterministic canonical replay on the same accepted history, append-before-apply, one-row-per-block updates, delete-wins identity semantics, eventual convergence for participants that ultimately receive equivalent relevant events, permissionless block redistribution, complete reconstruction from validated genesis and all ledger history, independent progress during network partitions, and crash recovery for durably accepted events.

**Not promised:** Simultaneous SELECT visibility, knowledge of an objectively complete history at an arbitrary instant, automatic rollback of **ledger blocks**, all-or-nothing execution of multi-block SQL transactions, preservation of foreign-key/unique constraints, instant failover without surviving block copies, globally irreversible application business outcomes, and successful application-level strong locking when required masters are unreachable. **Required despite these non-guarantees:** correcting/rebuilding the derived database projection when an earlier valid block changes canonical materialization; retaining history and never suppressing an applicable block simply because it arrived late.

## 13. Acceptance scenarios (conceptual, not hidden verification details)

1. A new ledger initializes a genesis signer; an empty replica adopts the ledger and derives an identical state when fed the same history.
2. A grants B; B grants C; a late invalidation of B's grant invalidates C's dependent authority and relevant projected effects.
3. A signer key has no authority at a block position before its own grant; a later revocation invalidates subsequent blocks, not prior ones.
4. A and B publish independently while disconnected; a replica relays blocks to a disconnected master when peer links permit.
5. A block arrives late with an earlier timestamp; the node corrects affected materialization by selective rollback/replay **or complete rebuild from the validated ledger**, without treating the block as too old to apply.
6. Partial-column updates on the same row preserve separately modified columns; deletion of the row, table, or column GUID wins over modifications.
7. Same-name columns/tables with distinct GUIDs both survive; corrective naming blocks are produced by an authorized master, not by direct projection writes.
8. Duplicate primary-key values across distinct row GUIDs survive in Version 1.
9. `BEGIN`+`ROLLBACK` emits no blocks; partial failure during `COMMIT` can preserve only a published prefix of independently durable row blocks.
10. Crashes between ledger persistence and projection recover idempotently; replicas converge once their accepted block sets and authority histories agree.
11. Newly received unsupported-protocol, malformed or signing-authority-unresolved blocks are rejected without persistence; historically authorized blocks that cannot yet be projected because schema/entity dependencies are missing can be retained and diagnosed without bypassing official storage; previously accepted blocks later made authorization-unresolved may be archived locally as `.XBLK`.

## 20. Compact local block names, local-only invalidation and approved projection delay — Owner direction (2026-11-09)

**Approved local filename compacting (independent of signed protocol version):** Under each database-basename support directory, use `BLK/YYYY/YYYYMM/YYYYMMDD/` and matching `STAT/YYYY/YYYYMM/YYYYMMDD/`. The standard filename stem is `YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>`, with `.BLK` or `.STAT` extension. A four-digit fractional field encodes millisecond timestamp as `sss0`; all date/time fields are UTC and zero-padded. This changes *local file organization only*, not the signed-block wire bytes, timestamps, GUIDs, signatures or canonical replay order. Sort inventory filename stems by canonical ASCII order; the sorted inventory is not required to reproduce the order of all signed events in every disputed-variant case. Handle valid signed timestamps outside supported calendar ranges with an explicitly designed non-calendar fallback.

**Owner-directed historical invalidation and local-only archival (2026-11-09; ARCH-013 restricts this to *previously accepted* history):** A block that was once historically authorized may become unauthorized when an earlier signed grant/revocation arrives. Its original signed bytes remain intact and are retained locally. Invalidate/remove its advisory `.STAT` through the sole STAT manager; move/rename the corresponding `.BLK` into the compact `.XBLK` form `YYYYMMDD-HHMMSSssss-<block-guid>-<signer-public-key>.XBLK` (full public key: 64 lowercase hex characters); then reconcile official state by full replay or a future equivalent selective replay. While a file is `.XBLK`, **never announce, push, serve, export or relay it**, and exclude it from peer `TREE.HASH` inventories. Recheck archived `.XBLK` when newly received canonical historical authority changes; if its signer becomes authorized again at its signed block position, verify its bytes, restore its canonical `.BLK` name using SHA-512 of the unchanged full signed bytes, reinstate it in the active inventory, and allow ordinary best-effort push/periodic pull. No archived bytes become official effects until normal authenticated projection has applied them. This is a new owner-directed operational exception to the prior generic serve/relay-all-history language; it does not alter block wire bytes or erase archive history.

**Limits and deliberate tradeoff:** The Owner accepts ignoring the extraordinarily unlikely collision of `.XBLK` filenames for equal timestamp, block GUID and signer; never overwrite existing destination files or silently delete previously accepted signed bytes on unexpected conflict. New inbound unauthorized/unresolved variants are rejected from memory without disk persistence. Since `.XBLK` is **local-only and absent from peer inventories**, two nodes can match active inventory roots while privately retaining different archived histories, and temporarily differing authorization knowledge can prevent a peer from obtaining a block until a holder revalidates and restores it to `.BLK`. This is accepted as the simpler Version 1 synchronization policy; it is not a guarantee of complete historical inventory equivalence. The exact peer/cache binary serialization and safe rename/scan/restart transaction mechanics still require implementation review.

**Projection delay — OWNER APPROVED:** A configurable `projection_delay_seconds >= 0`, default **0 seconds**, buffers only ordinary data/schema materialization: signed blocks are received, verified, durably retained, and evaluated for current historical authorization immediately. Relational projection waits until the signed timestamp is at or before local UTC time minus the configured delay, subject to all other dependencies. Report age-deferred work separately. The delay reduces some avoidable replay but creates intentional, consistent local SELECT staleness, is no guarantee of global completeness, and never prevents arbitrarily late blocks from requiring correction. Critically, a newly known earlier revocation may trigger immediate re-evaluation of current signing authority and already projected effects despite the delay. Test using deterministic projection status/checkpoints, not arbitrary sleeps.

## 22. ARCH-011 — Owner-approved Phase 1 authority classification, recovery, countersigning and configuration

**Authority and variant states (ARCH-013 supersedes incoming archival rules in ARCH-011):** Canonical order and full signature checks remain unchanged. For any *newly received or externally constructed* signed block, complete protocol/frame/signature/event checks, ledger/genesis binding, and historical authorization in bounded **volatile memory before any filesystem writes**. Return deterministic non-durable retryable `AUTHORITY_UNRESOLVED` or non-durable `NOT_AUTHORIZED`. Missing earlier authority evidence can be supplied and the source block reimported later; Phase 4 may rediscover it from peers that possess it. The signed bytes stay unchanged when retried. **Previously persisted history and disputes:** A signed block *already accepted as active `.BLK`* may later become unauthorized or authority-unresolved if earlier signed history arrives. New unauthorized/unresolved variants never persist. An exact GUID already used by different bytes is rejected as `BLOCK_GUID_CONFLICT` without overwriting retained signed bytes. Random GUID collisions are negligible; deliberate GUID reuse is possible but special adversarial resolution remains out of scope. Existing valid pinned genesis cannot be displaced by a conflicting candidate genesis. `block get/export` and peer inventory never include `.XBLK`.

**Phase 1 counts (Management API §14.1 controls):** Count fully authenticated durable signed-byte variants by their full SHA-512, including genesis and historically archived `.XBLK`. `retained_count = active_authorized_count + pending_count + quarantined_count`; `pending_count` is formerly accepted history whose authority later becomes unresolved; `quarantined_count` is formerly accepted history now proven unauthorized/inapplicable. `disputed_count=0` and `opaque_count=0` for the active Phase 1 contract. Pending and quarantined never overlap; duplicates, newly rejected input, absent SQLite schema, and projection backlog never inflate counts. Re-evaluate after pertinent earlier history arrives.

**Current UTC authorship and revocation:** All new local publication uses the clock at signing/publication; the CLI no longer accepts `--timestamp-utc-ms` for block publishing and the revocation consent CLI generates A's timestamp and GUID internally. B completes the block at B's own current UTC time after validating A's exact 229-byte signed consent bundle; the 15-minute signed timestamp interval and Protocol 1.03 message are specified in §6.3. Older received blocks preserve their original signed times.

**Interrupted initial identity recovery:** When the original `signing-key.v1.json` survived but no manifest or genesis was ever durably created, a deliberately requested `instance recover --from <original-signing-key-path> --confirm-unbound-initialization` can reconstruct only the **original unbound** manifest after verifying the complete signed-key JSON/AES-GCM AAD/seed/public key/instance GUID and absence of contradictory binding/history evidence. This exception to the normal requirement for existing binding evidence does **not** authorize replacing an earlier identity or recovering an actually bound instance as new. Repeated exact recovery is idempotent; partial/crashed recovery remains recoverable. See Management API §14.4.

## 25. ARCH-014 — Owner-approved bootstrap and publication safety (active Phase 1)

**Verified join and recovery:** `ledger join --ledger-id HEX64 --genesis-sha512 HEX128 --genesis-file ABS` requires an exact raw protocol 1.03 227-byte genesis. A healthy initialized unbound instance validates its empty payload, `genesis.ledger_id == genesis.signer_public_key == supplied ledger ID`, Ed25519 self-signature, and whole-signed-block SHA-512 against the independently supplied trust pin completely in bounded volatile memory **before any persistence**. The joining replica’s own Ed25519 public key is **not** the genesis signer and must be preserved independently. Then durably save the exact genesis `.BLK` before atomically binding the Version 2 instance manifest. A crash between persistence and binding is handled by explicit idempotent `ledger recover-genesis --ledger-id HEX64 --genesis-sha512 HEX128`, which revalidates the already durable genesis and completes the same replica binding without replacing its key. For locally created ledgers only, `ledger init` and its recovery also require the genesis signer to equal the local instance public key. Conflicting identity or fingerprint fails without adopting a different genesis. `ledger join` must not require that the genesis was previously imported.

**Ordinary publish retries:** For an explicit `--block-guid`, check for a durably retained, fully verified original block *before* generating a fresh UTC timestamp. If ledger ID, local signer, GUID, and exact event payload match **and the original is active `.BLK`**, return its original complete successful metadata (including its timestamp, SHA-512 and active path) without re-signing. If that same original was subsequently archived as `.XBLK`, return `BLOCK_ARCHIVED` (exit 4, nonretryable), original publication metadata and current archive classification in the error details; never restore or alter its counts (Management API §13.3.1). Otherwise, existing GUID with different content returns `BLOCK_GUID_CONFLICT` exit 4 with no change. A publish call without an explicit GUID is always a new publication attempt. Preserve no-overwrite storage guarantees.

**No special GUID dispute subsystem:** Owner explicitly declines direct incoming `.XBLK` archival or elaborate arbitration for accidental same-GUID collisions. Random collisions are negligible; deliberately copied GUIDs remain possible but no special adversarial collision resolution is part of Phase 1. Never overwrite existing signed bytes. `.XBLK` is used solely when **previously accepted** `.BLK` history later becomes unauthorized or inapplicable after earlier signed history arrives. The status field `disputed_count` remains reserved and zero for Phase 1.

**Revocation timing and retry:** The 15-minute consent validity test is `0 <= B_signed_UTC_ms - A_signed_UTC_ms <= 900000`; filesystem flush/completion time does not affect that validity. When retrying B's publication with A's signed consent GUID, verify any matching durable revocation before generating a timestamp: return original success only if it remains active `.BLK`, or `BLOCK_ARCHIVED` (exit 4) if it is now `.XBLK`; never re-sign into a second GUID variant. If no existing publication, form B's current-UTC block and apply the signed 15-minute interval.

**Owner-approved bounded batch import sequence (Step 1; normative CLI details in Management API §13.4):**

1. Read the complete import batch into **bounded volatile memory** under the approved size, allocation and time limits; if it cannot be evaluated safely within those limits, reject it with the applicable resource error and do not spool unvalidated inputs to disk.
2. Validate each candidate's container framing, signed protocol version, payload hash, Ed25519 signature, event shape, ledger ID and trusted genesis binding **without making it durable**. Record invalid items for per-input diagnostics; they cannot supply authority to another item.
3. Sort valid candidates **before historical authorization evaluation or publication**, ascending by the approved canonical tuple `(timestamp_utc_ms, block_guid, signer_public_key)`, **not** DDLB transport order, filename or timestamp alone.
4. Evaluate signing authority in that canonical order using already accepted history and applicable validated authorization events in the batch. A dependent signer cannot gain authority from a grant placed later in canonical order. Any new item lacking proven historical authority is rejected **in memory**, with no filesystem write.
5. Durably persist individually accepted blocks in dependency-safe canonical order. A necessary new `GRANT_MASTER` (or other authority prerequisite) must be crash-durable **before** any dependent block becomes durable or is acknowledged; if prerequisite persistence fails, do not persist or acknowledge its dependents. Independent valid items may succeed; the batch is **not group-atomic**.
6. Return the final per-item disposition, actual durability, duplicates, error reason and `retryable` in the **original input order**, with truthful `PARTIAL_IMPORT` counts and no retained rejected inputs.

Sorting a known batch before persistence also enables the future Step 3 SQLite projector to apply it chronologically and avoids avoidable full replays. Blocks arriving in **later** batches can still predate known history and require reconciliation or a full replay. This batching policy does not implement the Step 3 projector or Step 4 networking.

**Acceptance:** Developer must implement and QA must independently verify Protocol 1.03 join bootstrap, wrong genesis pin, **interrupted local-creation and replica-join recovery with distinct local/genesis public keys**, preservation of original instance GUID/key and pinned trust, ordinary/revocation retry, signed-time boundaries and delayed flush, inverted batch authorization dependencies, no-disk reject of unresolved/unauthorized input, no-overwrite collision errors, and retroactive `.BLK→.XBLK` transitions. Prior 1.01/1.02 passing tests are not 1.03 acceptance.

## 26. Owner directive — cross-platform portability (2026-11-17; controlling)

**CONFIRMED architectural requirement:** The new ledger implementation and modifications to the internal SQLite 3.54.1 fork MUST preserve upstream SQLite's cross-platform capability wherever reasonably possible. Protocol encoding, Ed25519/SHA-512/AES-GCM semantics, block validation, historical authorization, canonical ordering, SQLite-native value handling, SQL interception logic and all signed formats MUST be specified and implemented independently of operating-system conventions. Platform-specific code MUST NOT change canonical bytes, signatures, authority outcomes, or logical database semantics.

**OS boundary:** Isolate filesystem publication/atomic replacement, directory-entry durability, locking, path handling, file sharing, process termination and related OS behavior behind narrow portable interfaces or adapters. An initial Windows NTFS implementation is acceptable, but Windows-specific calls or assumptions MUST NOT leak into portable ledger/SQLite core logic. Keep the architecture viable for Linux, macOS and other feasible platforms; do not claim their support without platform-specific qualification.

**Developer change-control obligation:** For each unavoidable platform-specific implementation, identify affected source files and functionality, the reason, currently qualified OS/filesystem combinations, the proposed portability strategy, and remaining reliability/testing limitations. Correct avoidable portability regressions as part of normal development. Do not introduce a permanent platform restriction without Owner review.

**Testing and acceptance:** Prefer portable functional, protocol, crypto and deterministic fault-injection tests; isolate genuinely OS-specific filesystem/durability qualification. Windows 11 is the initial required Step 1 qualification platform. Linux/macOS qualification is a later goal, not a prerequisite to Windows Step 1 acceptance. QA owns independent tests and evidence; Security reviews portability-sensitive reliability boundaries; PM/Owner decide acceptance. Existing Windows 11 results must not be represented as Linux/macOS certification. This directive changes no signed-wire bytes or existing Owner-approved Phase 1 behavior.
