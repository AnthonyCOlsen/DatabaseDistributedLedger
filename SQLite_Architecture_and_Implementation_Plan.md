## 1. Scope and controlling documents

This document specifies the **current SQLite implementation direction** for [Database_Distributed_Ledger_Technical_Design.md](Database_Distributed_Ledger_Technical_Design.md). The October 23, 2026 integrated v7 design is **historical** for the `0x0001` value/column grammar. The current Technical Design specifies signed **1.01 (`0x0101`)** with five SQLite storage-class values and text-preserving column declarations. The previously approved 147-byte envelope, Ed25519 signatures, genesis fingerprinting, grant/revoke event grammar, GUID identities and immutable replay principles remain applicable; canonical order is `(timestamp_utc_ms, block_guid, signer_public_key)` as approved November 9. This document supersedes **PostgreSQL-specific implementation choices**; the explicitly Owner-approved 1.01 value/schema revision is the only new signed-wire change described here. The former PostgreSQL v0.4 management contract is retired as a live adapter specification; a SQLite-oriented replacement is [Distributed_Ledger_Management_API_Specification.md](Distributed_Ledger_Management_API_Specification.md).

**Non-negotiable guarantees:** ledger history is authoritative; signed blocks remain immutable and independent (not hash-linked); multiple authorized masters publish while disconnected; replicas verify and relay; all supported user modifications create durable authenticated block history *before* official relational changes; official state is a reconstructible deterministic projection; missing earlier blocks can change that projection; ordinary SQL reads need not await unknown remote history.

**Accepted initial threat boundary:** Changing SQLite's file header and extension deters ordinary external SQLite tools from accidentally opening or modifying the official database. It is **not** encryption, authentication, or protection against administrators or deliberately hostile local processes. The Project Owner explicitly does **not** require full ledger-versus-projection verification before each new block is signed. SQL mutation-path closure inside the supported fork remains mandatory.

## 3. Logical components and trust boundaries

| Component | Responsibility | May update official `.DLDB`? |
| --- | --- | --- |
| Ledger codec / verifier | Strict signed protocol 1.01 parsing, SHA-512, Ed25519 signatures, canonical event encoding, resource limits | No |
| Ledger block store | Durable, exact-byte `.BLK` files; duplicates, variants and export | No |
| Authorization / canonical replay | Genesis binding, grant/revoke validation, ordering and event applicability | No |
| SQL publisher | Accept normal SQLite SQL writes on an authorized master; evaluate provisional effects, sign and durably publish independently meaningful blocks | **No** |
| Ledger projector | Ingest applicable signed blocks; build/repair schema and rows; transactionally record projection progress | **Yes, exclusively** |
| SQL reader | Ordinary SQLite SELECT/query interface against consistent local projection | No |
| Peer exchange | Announce, request, transmit and receive **exact signed bytes**; relay without becoming a master | No |
| Management | Initialization, joining, keys, status, import/export, rebuild and configuration | Only by invoking the trusted projector path |

The **publisher and projector are independent workers** connected by durable ledger history, not an in-memory queue as their only recovery source. Implementers may use dedicated threads, scheduling loops, or separate processes provided these guarantees hold. Locally published blocks pass through the **same verification and projector ingestion** path as remotely received blocks. Merely selecting a private key never grants authority; an instance must be authorized by canonical ledger history.

## 4. Native SQLite client behavior and SQL boundaries

**Owner-approved public behavior:** Keep ordinary SQLite API and SQL submission, including native `sqlite3_prepare*` / `sqlite3_step` client workflows. For **supported** `INSERT`, `UPDATE`, `DELETE`, `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, transaction commands, and other supported mutations, the native library must cause the concrete effects to become signed ledger events **without directly changing official materialization**. A replica rejects writes. A master may publish blocks even while its projector is catching up or peers are disconnected, subject to local state/authority preconditions. **ARCH-003 delivery order:** native write interception is implemented in Phase 2, *before* the official projector in Phase 3. At that stage, supported SQL writes either produce valid durably stored signed blocks while leaving official `.DLDB` unchanged, or fail safely.

A managed C# gateway alone is **not** transparent to arbitrary native SQLite API clients; the Developer must establish a **native interception and official-write authorization boundary**, or obtain an explicitly approved revision to the compatibility guarantee. Ordinary clients must not gain projector write authority through a PRAGMA, special SQL statement, callback, alternate API, `ATTACH`, incremental BLOB write, backup destination, extension, trigger, or other supported path. Reject unsupported mutation paths rather than silently performing an unlogged change.

Reuse SQLite's native parser, planner, expressions, and transaction execution wherever safe. Provisional mutation evaluation is separate from official projection. `BEGIN`, savepoints, `ROLLBACK`, and `COMMIT` preserve the earlier ledger contract: rollback emits no blocks; final effective changed rows are emitted at COMMIT; multi-block publication **is not group-atomic**. If publication is partially durable, report partial or uncertain outcome honestly; never claim already durable blocks were rolled back. `RETURNING` and command counts are provisional and do not guarantee immediate `SELECT` visibility. PostgreSQL-specific `COPY` and `MERGE` syntax and SQLSTATE codes are not required SQLite features solely because the old adapter described them.

**Read behavior:** With a valid available instance identity and a completed consistent projector, SELECT may serve consistent, locally projected but network-stale data. Do **not** block awaiting unknown blocks on remote nodes. Once a locally known block starts reconciliation/replay that could expose inconsistent intermediate state, gate affected SELECTs until a consistent generation is available; an unsuccessful rebuild yields a clear error. Under sustained arrivals, reconcile finite batches and admit reads between consistent batches to prevent starvation. Handle active read transactions/prepared statements across projection generation changes explicitly.

**No additional historical-state auditing before signing:** The publisher may trust the application-controlled local `.DLDB` projection under the accepted threat model. This waiver does **not** remove signature validation, historical authorization replay, ledger-first publication, or the ban on supported direct SQLite write bypasses.

## 5. SQLite-native value semantics — OWNER APPROVED PROTOCOL 1.01

The active signed block header is `0x0101`, with the **five SQLite storage classes** as the only value tags: `0x00=NULL` (no bytes), `0x01=INTEGER` (signed int64 ZigZag minimal ULEB128), `0x02=REAL` (binary64 big-endian), `0x03=TEXT` (length-prefixed UTF-8), and `0x04=BLOB` (length-prefixed bytes). **No DECIMAL, DATETIME, BOOLEAN or GUID value tags**; immutable internal entity GUIDs remain 16-byte identities. SQLite's own affinity/conversion rules apply to actual stored values. No arbitrary-precision decimal guarantee or exact decimal arithmetic extension is implied. A SQL declaration such as `DECIMAL(10,2)` may still be preserved as declared type text, but its stored numeric values use native SQLite INTEGER/REAL and their native precision.

The Version 1.01 column-definition byte grammar is specified in Technical Design §6.2: `column_guid`, length-prefixed name UTF-8, length-prefixed **declared type UTF-8**, flags, default-presence byte and optional typed-constant default. Preserve the actual text declaration and corresponding SQLite affinity for **supported** schema operations. Unsupported constructs that cannot be faithfully replayed must be rejected *before* ledger publication. Do not fall back to the nine-value historical `0x0001` grammar; that version is incompatible. The `DDLB` container frame remains independently versioned at `0x0001`.

Existing native SQL support is the target; Phase 2 interception and Phase 3 projection still require QA qualification of supported SQLite bindings, expressions, and byte-preserving values. The ledger does not add independent exact DECIMAL semantics to SQLite.

## 6. Filesystem block store: `.BLK` and `.STAT`

**Owner-approved compact naming (2026-11-09):** One exact signed block per immutable `.BLK` file, with a separate advisory `.STAT` tree **using the same relative UTC-date path and basename** (per-instance roots in §8.4 and §12):

```text
<database-basename>/BLK/YYYY/YYYYMM/YYYYMMDD/
    YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.BLK
<database-basename>/STAT/YYYY/YYYYMM/YYYYMMDD/
    YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.STAT
```

`HHMMSSssss` uses six UTC hour/minute/second digits followed by four fractional digits; the fourth fraction digit is **0** for Version 1 millisecond timestamps (for example, 12:34:56.123 UTC becomes `1234561230`). Use UTC, zero-padding, lowercase canonical GUIDs and SHA-512 hex, and filesystem-safe names. For signed int64 timestamps outside UTC calendar years **0001–9999**, use the already approved deterministic `OUTOFRANGE/T<sign-biased-16-lowercase-hex>-<block-guid>-<full-block-sha512>.BLK` fallback specified exactly in §11; it is **not pending specification**, and valid signed timestamps must not be rejected solely because they cannot be rendered as calendar dates. Do not trust a filename as proof of block identity, signature, or timestamp; verify block bytes. The full-block SHA-512 suffix allows both authenticated variants of a disputed block GUID to remain retained.

**Durable publish sequence:** Create a unique temporary file on the destination filesystem; write complete original bytes; validate safely; flush file data; publish without overwrite using a same-filesystem atomic rename; ensure the directory entry is durable by a platform-appropriate mechanism; *then* acknowledge durable retention. Never expose partially written files as accepted `.BLK` entries. Duplicate identical bytes are idempotent. Different authenticated variants claiming one `(ledger_guid, block_guid)` are quarantined, never chosen by filename or arrival order. Paths and metadata are indexes, not signed protocol data.

`.STAT` is **replaceable diagnostic/cache metadata** with the same filename stem, never an input to block authenticity or the source of truth for current applicability. It may be absent, stale, or deleted. Its statuses may change after late history. Persistent projection generation and progress metadata must be committed **inside the same SQLite transaction as the corresponding official state change**. On recovery, derive statuses from signed blocks and current projection metadata and regenerate `.STAT` as necessary. Deleting all `.STAT` files does not itself roll back official state.

**Active signed-wire header and REAL:** The block header `version` changed from historical `0x0001` to Owner-approved `0x0101`. The **147-byte field layout and 211-byte empty-genesis size are retained**, not the old version field value or nine-type event grammar. For REAL, reject incoming NaN bit patterns, accept ±infinity, and preserve signed negative-zero block bits even where SQLite projection normalizes them (Technical Design §6.2).

## 7. Reconciliation, crash recovery, and rebuilding

The ledger is immutable and can exist without SQLite. The initial projector may use **complete deterministic replay** from the pinned genesis and all retained relevant blocks; a later optimizer may use selective rollback/replay only if it yields the same state as a full replay. Canonical order is **`(timestamp_utc_ms, raw block_guid, raw signer_public_key)` ascending** (Owner-approved amendment 2026-11-09); it replaces the older signer-before-GUID interpretation. This canonical ordering change is semantically significant; the separate Owner-approved signed-block version also changed the first two header bytes to **`0x0101`**, although the envelope field widths and offsets remain unchanged. Authentication and authorization are evaluated at each block's canonical position, independent of import order. A late earlier block, including a grant or revocation, may require rebuilding and invalidating effects previously considered applicable.

**Crash boundary:** (1) durable `.BLK` publication; (2) SQLite transaction committing projection changes **and** progress metadata together; (3) optional `.STAT` update. Crashes before (2) cause safe replay; crashes after (2) do not justify blind duplicate application merely because `.STAT` was not updated. All startup/recovery paths must account for late-block invalidation and current projection generation, not merely a per-file applied flag.

**Full rebuild:** Stop/guard projector writes and affected reads; recover or close SQLite correctly; reconstruct into a clean `.DLDB` from authenticated block history; commit consistent projection/progress; regenerate `.STAT`; reopen reads only after a consistent projection is established. If rebuild fails, remain unavailable for affected reads and persist diagnostics. Do not merely delete `.DLDB` while it has active handles or associated WAL/journal recovery state. A staged rebuild followed by atomic activation may be added later.

## 8. Persistent signing identities and key storage — SEC-002 (OWNER APPROVED 2026-11-08)

### 8.1 Identity, lifecycle and authorization (approved requirements)

- **Every explicitly initialized instance, including a replica, generates its own Ed25519 keypair** with a cryptographically secure random generator. Its expected public key and private signing seed are durably persisted **before** initialization reports success. A new ledger uses the existing instance identity for self-signed genesis; a new replica joining an existing ledger keeps its independent identity, initially unauthorized to sign ledger changes. An authenticated `GRANT_MASTER` can authorize that existing identity later.
- Store the identity separately from `.DLDB`, `.BLK`, `.STAT`, the Git repository, and routine projection/ledger backups. **Never delete, regenerate, overwrite, or silently replace the identity during startup or rebuilding**. A database can be deleted or rebuilt without changing its signing identity. Normal startup/replay/rebuild are unattended, without a required phrase, PIN, password, manual approval, cloud service, or OS secure-store unlock.
- **Use Ed25519 signing and public verification.** A public key alone cannot sign; the ledger GUID is not a signing key. Possessing a private key does **not** grant master authority; canonical genesis/grant/revocation history exclusively determines it. Public-key verification/replay is cryptographically possible without a private key, **but ARCH-003 requires ordinary SQLite and ledger processing to pause in recovery state whenever the existing instance's private key is unavailable**. Do not continue normal read-only replica activity in that condition.
- Keep an instance-scoped `ISigningKeyStore`-style abstraction providing creation during explicit first-time initialization, load, public-key lookup, signing, backup/restore and diagnostic operations. Normal callers use an opaque instance/key handle and never receive private seed bytes. Separate non-destructive signing availability/selection from immutable instance identity.

### 8.2 Baseline confidentiality model (approved requirements)

The Version 1 default is a **portable encrypted key file**, not an OS-specific secret store. Encrypt Ed25519 seed bytes with **AES-256-GCM** using a **fresh cryptographically random nonce per encryption**, authenticated ciphertext/tag, and a **versioned application-wide 256-bit symmetric key embedded in publicly released source and binaries**. The key is publicly recoverable; this is **obfuscation against casual file inspection, not meaningful secrecy against a determined actor** who has the encrypted file and open-source application. Apply filesystem permissions where available and trust the host OS under the accepted Version 1 threat model.

**No mandatory** Windows DPAPI, Apple Keychain/Secure Enclave, Android Keystore, Linux Secret Service, TPM/HSM, cloud key management or interactive startup. These are optional future hardening. A hardware-specific provider is not required for portable Ed25519 support. The application must not misrepresent this file encryption as protecting against privileged host compromise or a holder of the encrypted file plus published wrapping key.

### 8.3 Portable signing-key JSON representation — OWNER-APPROVED VERSION 1 FORMAT (2026-11-09)

**Authority boundary.** SEC-002 *already approves* an independently persisted Ed25519 identity for every initialized instance, AES-256-GCM obfuscation using a publicly embedded versioned 256-bit application-wide key, fresh nonces, unattended operation, and no silent replacement. The Owner **approved the exact Version 1 key-file JSON fields and the 88-byte AAD byte encoding** in §8.3 on 2026-11-09. The `.DLID` descriptor has been **removed** by Owner approval. The **exact Version 1 `instance.identity.json` format in §8.4 is approved**, not provisional; its fields and strict validation are mandatory. The separate `instance.config.json` Version 1 format is now approved under ARCH-011 in §20 and Management API §14.5. Optional future recovery phrases and detailed future key migrations remain outside Phase 1 and require separate review. These local operational JSON formats never change signed ledger-event bytes.

**File:** `<database-basename>/signing-key.v1.json`. UTF-8 without BOM, exactly one top-level JSON object. Whitespace and property order have no semantic effect; duplicate property names, missing required fields, unknown fields for this version, invalid UTF-8, invalid JSON types, or extra trailing nonwhitespace data are errors. Names are case-sensitive; `version` is JSON integer `1` (not a string). Decode hexadecimal and Base64 strictly, with the exact decoded lengths below; use standard RFC 4648 Base64 with canonical padding and no whitespace. UUIDs use lowercase canonical hyphenated spelling, never the all-zero UUID, and are decoded into the 16 RFC 9562 network-order bytes. Bound input size to a documented safe limit; do not allocate unbounded memory for malicious JSON.

```json
{
  "format": "UDDL-ED25519-KEY",
  "version": 1,
  "instance_guid": "11111111-2222-4333-8444-555555555555",
  "public_key_hex": "<exactly 64 lowercase hex characters>",
  "wrap_key_id": "application-wide-v1",
  "encryption": "AES-256-GCM",
  "nonce_b64": "<standard Base64 encoding of 12 random bytes>",
  "ciphertext_b64": "<standard Base64 encoding of 32 ciphertext bytes>",
  "tag_b64": "<standard Base64 encoding of 16 authentication-tag bytes>"
}
```

The GUID in this example is **illustrative and must never be used as a fixed real instance ID**. The Ed25519 private signing material is exactly a 32-byte seed. Derive its 32-byte public key using the selected interoperable Ed25519 implementation and compare the exact raw public-key bytes with the expected values in **both** persistent identity records (`instance.identity.json` and `signing-key.v1.json`) before permitting signing. Never encrypt a variable-length PEM representation in this format. Key encryption uses one 32-byte wrapping key resolved by `wrap_key_id`, one freshly generated, cryptographically random **12-byte nonce per encryption**, 32-byte ciphertext, and a **16-byte GCM tag**. Never reuse a `(wrapping key, nonce)` pair; migrations and backups that re-encrypt must obtain a new nonce. The embedded key is available publicly, so GCM detects accidental corruption but does **not** establish tamper resistance against a deliberate holder of both the file and the published application key.

**Wrap-key selection:** The exact ASCII identifier `application-wide-v1` names a single, versioned 32-byte application-wide AES key compiled into the published application. Its actual 32-byte value belongs in the documented application source/build provenance, not in the private-key JSON. Unknown identifiers are **unavailable-key** errors, never reasons to substitute the latest key. All supported historical wrapping-key versions must remain decodable until their migration is safely completed. Do not claim that the publicly embedded key is secret.

**Exact Version 1 AES-GCM authenticated additional data (AAD), independent of JSON presentation:**

```text
ASCII("UDDL-ED25519-KEY-v1")             # 19 bytes; no NUL terminator
instance_guid                             # 16 raw UUID bytes, RFC 9562 network order
public_key                                # 32 raw Ed25519 public-key bytes
wrap_id_length                            # unsigned 16-bit integer, big-endian
wrap_id_utf8                              # exactly wrap_id_length UTF-8 bytes
```

Concatenate these fields **in exactly this order without padding or separators**. The `wrap_key_id` for Version 1 is the exact case-sensitive ASCII string `application-wide-v1` (encode those ASCII bytes as UTF-8). `wrap_id_length` counts its UTF-8 bytes, not characters. Do **not** hash the JSON, serialize a canonical JSON object as AAD, include `.DLDB` paths, or incorporate the ledger GUID/genesis binding into AAD: ledger binding is established *after* the instance key is persisted and must not require re-encrypting the key. The fixed AAD prefix binds the Version 1 format/encryption semantics; `instance_guid`, public key and wrapping-key identifier are also bound to the ciphertext. Verify the tag with this exact AAD **before** interpreting decrypted seed material; then rederive and compare the public key. Use a constant-time byte comparison where a library primitive is available; do not log plaintext seed bytes, recovered key material, or cryptographic buffers.

**Wire independence:** This private-key JSON/AAD format is not the ledger's Version 1 signed-block binary format and does not itself modify Ed25519 signing/verification or grant/revoke rules. **The Owner separately amended canonical event order** on 2026-11-09 as stated in Technical Design §4. A key-file copy does not establish master authorization; that remains a property of valid signed history.

### 8.4 Persistent instance identity (no `.DLID`), binding and crash recovery

**Owner-approved storage:** For the resolved file-backed target `ABC.DLDB`, `ABC/` is its same-basename support folder, even when `.DLDB` is not yet present in ledger-only Phase 1. The earlier `.DLID` descriptor is **removed**, and `ABC/instance.identity.json` is the sole nonsecret identity/binding descriptor.

```text
ABC.DLDB                         # derived SQLite projection; optional in Phase 1
ABC/
    instance.identity.json       # immutable instance identity; nullable trusted genesis binding
    signing-key.v1.json          # separately encrypted Ed25519 seed (approved §8.3)
    instance.config.json         # optional versioned persistent Phase 1 resource limits (ARCH-011)
    BLK/                         # exact signed blocks and OUTOFRANGE fallback
    STAT/                        # disposable status cache; rebuilt/rotated independently
    DEL1/                        # optional retired STAT directory pending cleanup
```

**Manifest JSON Version 1 (Owner-approved exact local representation, ARCH-010; no change to signed wire):** UTF-8 without BOM, one JSON object, field names shown, strict types and duplicate-field rejection; writer uses compact deterministic field ordering and final LF, reader accepts independent whitespace/property order. Unknown required fields or unknown versions are not interpreted silently. Example of a new unbound instance:

```json
{
  "format": "UDDL-INSTANCE-IDENTITY",
  "version": 1,
  "instance_guid": "11111111-2222-4333-8444-555555555555",
  "public_key_hex": "<64 lowercase hex digits>",
  "key_file": "signing-key.v1.json",
  "ledger_binding": null
}
```

**Exact manifest validation (approved fields; Architect-specified parser limits for QA review):** The complete set of top-level fields is exactly `format`, `version`, `instance_guid`, `public_key_hex`, `key_file`, `ledger_binding`. `format` equals the case-sensitive literal `UDDL-INSTANCE-IDENTITY`; `version` is JSON integer **1** (not a string or floating-point value); `instance_guid` is canonical lowercase hyphenated RFC 9562 UUID; `public_key_hex` is exactly 64 lowercase ASCII hex characters; `key_file` is exactly the relative basename `signing-key.v1.json` (no separators, absolute path, `..`, or alternative location). `ledger_binding` is either JSON null or an object with **exactly** `ledger_guid` (canonical UUID) and `genesis_sha512` (exactly 128 lowercase ASCII hex characters). Reject duplicate or unknown keys at every level, malformed UTF-8, BOM, invalid JSON/trailing data, wrong types, case mismatches, unsupported versions, zero-length/truncated values and files larger than **4096 bytes**. Writer emits these six fields in the listed order, compact UTF-8 JSON (no BOM, final LF), and if bound uses `ledger_guid` then `genesis_sha512`; reader accepts any object-key order and legal JSON whitespace. Do **not** authenticate the manifest by its JSON byte formatting: validate semantics and verify the 88-byte-AAD-protected original key's instance GUID/derived public key, then verify the exact pinned signed genesis separately. No `.DLID` is used.**

After successful `ledger init` or explicitly fingerprint-confirmed `ledger join`, replace `ledger_binding` with `{ "ledger_guid": "<canonical UUID>", "genesis_sha512": "<128 lowercase hex digits>" }`. Example GUIDs are not fixed identity constants. An instance GUID and public key must match the decrypted `signing-key.v1.json` and expected identity, even for a read-only replica. The trusted genesis/ledger binding survives deletion/recreation of `.DLDB` and must never silently change. The key-file's own `version:1` and 88-byte AAD remain already approved and **unaffected** by signed protocol 1.01. The manifest name and basename folder association must be verified at open; moving/renaming a database requires checked relocation of the matching support directory, not new identity generation.

**Crash-safe first-time initialization and Owner-approved explicit genesis repair:** Explicit `instance init` only after preflight (paths/permissions, name collisions, remnants, existing main-db state). Generate a fresh GUID and Ed25519 seed, write the Version 1 encrypted key file to a unique temporary file and ensure its bytes and directory entry become durable. Then write the manifest in a new temporary file, fsync/flush it and publish with no overwrite. Do not report success until both final records exist, parse, authenticate and agree. Partial temp files remain diagnostic evidence, not a fresh-start signal. No automatic replacement key generation during ordinary startup. If a key exists without manifest, or manifest exists without matching key, report `RECOVERY_REQUIRED`/`SIGNING_IDENTITY_UNAVAILABLE` and permit **explicit** recovery, never silent regeneration; preserve all surviving bytes. **ARCH-011 approved exception:** If the surviving original key is verified and there is no genesis, binding or contradictory initialization evidence, the user may explicitly assert never-bound interrupted initialization using `instance recover --from <original-signing-key.v1.json> --confirm-unbound-initialization` to reconstruct the original unbound manifest. This operation is idempotent and crash-safe, and is never an automatic creation of a new identity. See Management API §14.4. Incomplete genesis/binding update likewise requires explicit recovery against the retained authenticated genesis and original manifest, rather than silently publishing a new genesis.

`ledger recover-genesis --ledger-guid UUID --genesis-sha512 HEX` is the approved way to finish a crash-interrupted publication of **the original instance's own genesis**: scan existing exact durable `.BLK` bytes, verify the signed Version 1.01 211-byte genesis and original matching identity, refuse competing candidate geneses, then durably pin exactly the provided ledger GUID/full genesis hash using atomic manifest publication; repeating the command is idempotent for an already identical binding. An absent/invalid original key or conflicting pinned genesis remains recovery-required; do not start another genesis. See Management API §13 for the deterministic result/error contract and library/CLI `block publish` interface required in Phase 1.

**Normal state gate and restore:** Missing, corrupt, unsupported, undecryptable, mismatched key/manifest or ambiguous copied identity: stop **all** ordinary instance SQL, ledger, replication and replay until recovery. Only status, diagnostics and original-identity restore are callable. `instance recover --from` / `key restore --directory` must verify the expected same GUID/public key, check the original AES-GCM tag/AAD, restore without overwriting another identity, and preserve pinned genesis binding. Backup `instance.identity.json` and encrypted seed together separately from routine `.DLDB` or ledger backups; under the public wrapping-key SEC-002 model it is obfuscated, not confidential. No automatic recovery-phrase entry in normal operation.

**Duplicate detection:** Prevent concurrent opens with the same instance identity on the supported **same host** (OS lock/lease scoped to the manifest/instance); reject conflict with diagnostics. Copied entire identities on different hosts are an accepted detectable-only-where-practical risk within the initial threat model. Moving/renaming must not automatically change identity. Unrelated preexisting `ABC/` content must never be overwritten.

**Explicit first opening:** Only an intentionally new, empty, unconfigured target with no evidence of earlier identity is eligible for `instance init`. Then `ledger init` or `ledger join` establishes authenticated binding. A nonempty/orphaned `.DLDB` and any surviving identity/ledger evidence require recovery instead of a new-instance prompt. Discovery by ledger GUID is not binding; require full signed-genesis SHA-512 confirmation.

**Future migrations:** Old supported key versions can be decoded and upgraded with a fresh AES-GCM nonce only after verifying the original identity; a crash during upgrade must leave at least one complete recoverable version. Unsupported versions fail in recovery mode. No migration may replace the Ed25519 public identity or trusted ledger binding.

### 8.5 SEC-002 test obligations

QA and Security shall require **deterministic Owner-approved Version 1 key-file/AAD conformance vectors** using a nonproduction test wrapping key and seed. The AAD for `wrap_key_id=application-wide-v1` must be exactly **88 bytes** (19-byte domain prefix + 16-byte instance GUID + 32-byte expected public key + 2-byte big-endian string length + 19 identifier bytes), independent of JSON property order and whitespace. Changing any authenticated identity field must fail decryption; changing the nonce, tag or ciphertext must fail GCM authentication. Different nonce inputs must create distinguishable valid files with the **same expected public key**. Test invalid Base64, duplicate properties, wrong byte lengths, unknown format/version/wrapping key, truncated or corrupted writes and repeated initialization attempts.

Additional acceptance gates: (1) initial key creation on both master and replica survives restart and `.DLDB` deletion; (2) the identity record and key file are verified before routine activity; (3) persisted ledger GUID and full genesis fingerprint survive reconstruction, and a mismatched genesis cannot silently bind; (4) crashes after each initialization file publication yield either a complete *same identity* or an explicit recoverable incomplete state, never a new identity; (5) missing/unavailable key **blocks every ordinary SQL and ledger operation**, while diagnosis and original-key recovery remain available; (6) restoration reproduces the exact original Ed25519 public key and does not change the pinned ledger; (7) replica promotion follows an authenticated `GRANT_MASTER` without key replacement; (8) migration after interrupted rewrapping preserves at least one recoverable original key and changes neither identity nor authorization; (9) Windows/Linux/macOS/Android/iOS-supported format decoding is byte-identical where implementable, with unattended operation and no mandatory platform secret provider; (10) private seed/plaintext never appears in diagnostics or normal backups. The original revoked/uncooperative/lost-master limitation remains unchanged. **QA execution and actual supported-platform coverage are not claimed by this design.**

## 12. Separate `BLK` and `STAT` trees and full-replay rotation — OWNER APPROVED

The two sibling roots under the database-basename support directory (for example `ABC/`) are **`BLK/`** and **`STAT/`**, each with the approved matching UTC date hierarchy when applicable. `.BLK` files remain immutable signed source history. `.STAT` files are disposable, potentially stale, and never authoritative; SQLite transaction-coupled projection progress controls state. Every `.STAT` file stem corresponds to its `.BLK` variant. No additional `status/generations` hierarchy or `status/current` pointer is approved.

A single instance **STAT manager** is the exclusive owner of writes, creation, rotation and removal of the *active* `STAT` folder. For **full replay**, freeze ordinary database/ledger activity before touching the status tree. **Before replay starts**, rotate the existing `STAT` directory to the first available `DEL1`, `DEL2`, etc., under the same instance root, using a collision-safe rename. If another application holds a handle/lock that prevents rename, show an actionable error naming the obstructed file/directory when reported by the OS, **remain fully paused**, and retry until the lock is released. Never begin replay while that rename remains blocked. After successful rotation, create a new `STAT` (also create it when missing in safe startup conditions), run authenticated deterministic replay, and schedule **asynchronous cleanup** of the old `DELn` tree. The STAT manager coordinates cleanup; background deleters may only operate on verified retired `DELn` trees, never the active `STAT` or `BLK`. Resume cleanup of safe remnants on restart. A cleanup lock on a retired tree need not block current replay after the initial rename has succeeded.

**Crash rules:** A crash before renaming leaves old `STAT` requiring rotation; a crash after renaming but before creating `STAT` allows the manager to create a fresh one while replay remains controlled. A crash during replay must never expose incomplete official `.DLDB` state; regenerated `.STAT` is not proof of projection application. Retry and error formatting, Windows handle diagnostics, durable directory rename/creation, and cross-process exclusive STAT-manager enforcement must be validated by Developer/QA/Security; do not invent a locked filename when the OS only supplies a directory-level error.

## 15. Persistent ledger trust, accepted compromise risk, and proposed recovery

## 16. Hierarchical block-inventory reconciliation — OWNER-APPROVED APPROACH (2026-11-09); EXACT BYTE GRAMMAR UNDER REVIEW

**Approved architecture:** Each instance's `ABC/BLK/YYYY/YYYYMM/YYYYMMDD/` tree supports regenerable SHA-256 inventory summaries at the **day, month, year, and `BLK` root** levels. Cache files are called `TREE.HASH` at each level. An instance immediately pushes/announces newly created, durably retained **active `.BLK`** blocks best-effort to known configured peers and periodically descends into mismatching inventories to request missing active blocks. This inventory is **not** a complete history of local `.XBLK` archives: those are deliberately private, never announced/served, and reenter active reconciliation only on validated `.XBLK`-to-`.BLK` restoration. Block classification never alters original signed bytes. Exact cache/wire grammar remains under review.

**Approved leaf membership and ordering (active `.BLK` only):** For each dated `BLK` leaf directory, inventory all durably retained, independently cryptographically verified, active `.BLK` filenames. A daily record contains the complete canonical stem (timestamp, block GUID, full-block SHA-512) with only `.BLK` removed, sorted by ordinal ASCII bytes. Authenticated same-identity variants retain distinct SHA-512 filenames. Local `.XBLK` archives are **excluded** from these advertised peer inventories; they remain immutable historical bytes in local storage and are reconsidered for reauthorization. A signed block's cryptographic integrity is distinct from its historical authority. Before and after classification changes, no `.BLK` / `.XBLK` bytes are rewritten. Invalidation removes the `.BLK` entry from active inventory; revalidation and `.XBLK`-to-`.BLK` restoration add it back. Malformed/unauthenticated diagnostic bytes are not advertised as verified blocks.

**Exact inventory input concept (approved at the algorithmic level):** In a daily leaf, take each entire canonical filename **without only the trailing `.BLK` extension**; it includes the signed UTC timestamp, block GUID, and **full signed-block SHA-512**. Sort stems by **ordinal ASCII byte order** (not a locale-sensitive sort), and feed a **binary length-delimited list**, not CSV or platform-default text, to SHA-256. At a month, year, or root level, sort each child directory name by ordinal ASCII bytes and hash a binary length-delimited sequence of child **name plus 32-byte raw SHA-256 digest**. Use a level-specific version/domain separator to prevent interpreting a different level as equivalent. Sorting filename stems yields timestamp-first ordering; it is **not in every case the canonical ledger replay order** `(timestamp_utc_ms, block_guid, signer_public_key)`, particularly for disputed same-GUID block variants. This distinction is harmless for inventory set comparison.

**Candidate deterministic binary grammar — PROPOSED, NOT BYTE-FROZEN:** For a day: `ASCII("UDDL-INV-DAY-v1") || uint64_BE(record_count) || repeated { uint16_BE(stem_ascii_byte_length) || stem_ascii_bytes }`. At each parent level: `ASCII("UDDL-INV-{MONTH|YEAR|ROOT}-v1") || uint64_BE(child_count) || repeated {uint16_BE(child_name_ascii_byte_length) || child_name_ascii_bytes || child_sha256[32]}`. A candidate `TREE.HASH` cache contains the 32-byte raw digest. Filename validation, case, maximum record lengths, out-of-calendar-range timestamp fallback, empty-directory rules, and wire exchange envelopes must be finalized consistently with these conventions before an interoperability contract is frozen. File naming and canonical byte framing are independent of the signed `.BLK` wire format.

**Cache correctness:** Produce active `.BLK` comparisons from a consistent snapshot/generation. Durable publication, `.BLK`-to-`.XBLK` invalidation, and `.XBLK`-to-`.BLK` restoration each invalidate/recompute the affected day and ancestors through the root (or a safe batched equivalent). Never report a mixture of old and new subtree generations as settled. After crash/uncertainty, rebuild stale `TREE.HASH` caches from the durable verified **active `.BLK` set**; local `.XBLK` files are intentionally excluded and not transmitted. Cache contents never override block bytes. Previously verified filename metadata is sufficient for routine inventory recomputation; a sender may recheck raw bytes prior to sending and a recipient independently verifies before accepting. Historical authorization changes must be evaluated promptly, including for retained `.XBLK` archives that might regain authorization.

**Ledger scoping and limits:** Compare inventories only for the **same trusted ledger GUID and pinned full-genesis SHA-512** and matching inventory algorithm/inclusion-policy version. A replica may relay signed blocks despite having no signing authority. Matching root hashes mean equivalent **advertised retained inventories**, never proof of complete worldwide history. Bound peer memory, bandwidth, CPU, file traversal, announcements and retries; deduplicate repeated bytes. This policy does not authorize trust in an arbitrary peer or removal of retained history.

**Still to review with Developer/QA/Security:** Freeze the byte-exact hash grammar, `TREE.HASH` cache representation, inclusion of opaque future-version records, empty-directory and out-of-calendar timestamp representation, consistent-generation algorithm, per-platform filesystem guarantees, and default synchronization interval. These are implementation/interoperability details, **not** a reason to revert the now-approved hierarchical SHA-256 push/pull approach. No specific new transport protocol is approved by this section.

## 18. Local-only `.XBLK` historical-invalidation archive — OWNER DIRECTION (2026-11-09)

**Purpose and distinction:** A signed block previously considered authorized may become **historically invalidated** when missing earlier authority history arrives. Its original bytes and signature are still cryptographically valid; only authorization at its canonical position has changed. The Owner directs local retention without propagation: invalidate/remove the companion `.STAT` through the STAT manager, rename `.BLK` to `.XBLK` without rewriting signed bytes, and trigger consistent full replay (or future equivalent selective replay). **ARCH-011 Phase 1 policy:** Newly imported cryptographically valid blocks lacking historical authority evidence must be durably retained locally as **pending `.XBLK`**. Known unauthorized/inapplicable blocks and authenticated same-identity disputed variants are **quarantined `.XBLK`**. The classification is derived from signed bytes and known history, not from the filename. All are excluded from normal exports/peer inventories until an authorized undisputed variant becomes an active `.BLK`; the original signed bytes are never rewritten. These Phase 1 ledger rules need no SQLite projector, `.STAT` or peer network. The local historical archive must be scanned/reconsidered whenever newly available authority evidence could change an archived block's applicability.

**Owner-selected compact local names (2026-11-09):**

```text
<database-basename>/BLK/YYYY/YYYYMM/YYYYMMDD/
  YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.BLK
  YYYYMMDD-HHMMSSssss-<block-guid>-<signer-public-key>.XBLK
<database-basename>/STAT/YYYY/YYYYMM/YYYYMMDD/
  YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.STAT
```

The `.XBLK` public key is the **full 32-byte Ed25519 signer key encoded as 64 lowercase hexadecimal characters**, not Base64, and can be cross-checked against the signed header. Compact `.BLK`, `.STAT`, and `.XBLK` file components are approximately **189, 190, and 126 ASCII characters** respectively, below the common 255-character component limit; the complete path, directory-entry durability, and temporary-name limits still require preflight testing. All folder names and the sortable timestamp use canonical UTC digits with no punctuation inside date/time components. `HHMMSSssss` includes exactly one padded zero as the fourth fractional digit for millisecond timestamps. The filename format is an **on-disk index**, never the signed wire representation or an authorization proof. A signed int64 timestamp outside supported calendar dates requires a documented deterministic fallback, not rejection.

**Owner-directed Version 1 simplification:** The compact `.XBLK` name intentionally omits the full-block SHA-512; no special handling or further design approval is required for mathematically implausible accidental reuse of a block GUID at the same timestamp by the same signer. Filesystem renames must remain no-overwrite: if a destination unexpectedly already exists, report an error and preserve the source bytes. The separately approved signed-block identity-dispute rule still requires retaining authenticated variants without choosing a winner.

**Approved local-only propagation exception:** `.XBLK` files never participate in `TREE.HASH` peer inventories, peer announcements, push, pull serving, ordinary block exports or relaying. Do not create a second full-history peer inventory to discover `.XBLK` files. This deliberately means matching root hashes compare **active `.BLK` sets only** and cannot prove identical local archived histories. If new authenticated authority evidence restores an archived signer's authorization at the block's canonical position, verify the retained `.XBLK` bytes, compute full-block SHA-512, reconstruct the original canonical `YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.BLK` name, and **rename without overwrite** back into active `.BLK` storage. Update the daily and ancestor `TREE.HASH` summaries and permit normal best-effort push and periodic pull. Reclassification and crash recovery must be idempotent; don't erase the original signed history, and never use `.STAT` as an authorization source. A node holding only archived `.XBLK` and another lacking it may differ until the former revalidates and republishes; this is an explicit accepted limitation of the simplified policy. Exact transition/rename crash mechanics and peer frame format still require engineering review.

## 19. Configurable projection-age buffer — OWNER APPROVED (2026-11-09)

**Approved scope and default:** Provide a nonnegative per-instance `projection_delay_seconds` setting, with **0 seconds as the default**, to intentionally delay **only relational SQL materialization** of row/schema events. Receipt, strict format/hash/signature verification, durable block storage, and evaluation of currently known historical authorization (including changes to whether a local key may sign) remain prompt and are **not postponed**. The precise maximum/config API spelling beyond this documented candidate awaits the management-contract freeze.

**Eligibility:** A locally known ordinary data/schema block is eligible for projection when `signed_timestamp_utc_ms <= current_UTC_ms - delay_seconds*1000`, evaluated without integer overflow. Otherwise report a distinct, observable pending-by-age condition. A consistent local SELECT may be intentionally stale while eligible blocks are pending; it must still obey the existing local reconciliation/read barriers and missing-key recovery gate. Do not publish SQL effects merely because the age threshold passed if signature, authority, schema, or dispute dependencies remain unresolved. Changes to the configured delay require safe re-evaluation of pending work without losing ledger history.

**Safety:** This buffer is neither finality nor protection against arbitrarily late/backdated blocks, skewed clocks, future timestamps, or retroactive revocation. Newly received earlier authorization evidence can immediately invalidate a previously published projection and require a consistent replay regardless of age. The projection delay must not allow continued signing after presently known authorization revocation. Full replay remains available; future selective replay must be equivalent. QA must use explicit status/checkpoints rather than arbitrary sleeps to test delayed visibility. Behavior during clock jumps and precise numerical limits require Developer/QA qualification, not a signed-protocol change.
