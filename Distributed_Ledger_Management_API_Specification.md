## 1. Scope and supersession

This document replaces the **PostgreSQL 18.6-specific v0.4 management adapter** as the current working interface specification. The previous `--pgdata`, `initdb`, PostgreSQL socket/process, populated-cluster adoption and AI-verifier-specific provisions are **retired**; they are not required of the SQLite implementation. Retiring those adapter-specific obligations does not change Ed25519 signing, authenticated authority, `.BLK` exact-byte retention, `DDLB` transport, current no-overwrite/GUID-conflict policy or recovery guarantees defined in [Database_Distributed_Ledger_Technical_Design.md](Database_Distributed_Ledger_Technical_Design.md). **Historical approvals:** 1.01 introduced the five-class grammar, and 1.02 widened the ledger ID. **Current** signed protocol 1.03 (`0x0103`) retains that header layout and changes the revocation payload/consent workflow (§14.3; Technical Design §6.3).

[SQLite_Architecture_and_Implementation_Plan.md](SQLite_Architecture_and_Implementation_Plan.md) controls SQLite file format, SQL boundary, signing-key storage and incremental delivery. The ledger operates **independently of a relational database**. Commands must report which components are available rather than imply a projection exists in Phase 1.

## 2. General CLI behavior — Owner-approved Phase 1 conventions

**Approved Phase 1 CLI syntax:** `ledgerctl --instance-root ABS COMMAND ...`, with an explicitly selected local support root. The name `ledgerctl` and the command structure reflect the Owner-approved direction; command-specific extensions remain subject to later QA schema review. On any platform, paths must be validated and contained within intended configured storage roots when appropriate. No PostgreSQL executable, daemon, port, user, or cluster is assumed.

Finite CLI commands should produce exactly one UTF-8 JSON object terminated by a newline on stdout; errors/diagnostics go to stderr. Approved JSON envelopes:

```json
{"ok":true,"data":{},"error":null}
```

```json
{"ok":false,"data":null,"error":{"code":"CODE","message":"Human-readable text","retryable":false,"details":{}}}
```

The raw signed bytes are **always transferred by files or binary peer streams**, not JSON reserialization. Canonical UUID strings are lowercase hyphenated; SHA-512 hashes and Ed25519 public keys are lowercase hex in JSON. Private signing material never appears in status, logs, or successful responses. Exit-code groups and command response field types are specified in §§3 and 13. QA/Tester independently checks that contract and develops conformance vectors; the document does not claim test execution.

## 3. Phase 1 approved commands and lifecycle

**Global selector:** `ledgerctl --instance-root ABS COMMAND ...`; ABS identifies the intended same-basename support directory (`ABC/`), which can exist before `ABC.DLDB` is constructed. On CLI errors print one JSON failure object to stdout, details to stderr, and never fabricate successful durable outcomes. Unknown flags, out-of-range integers, invalid UUID/digest syntax and incompatible options fail `INVALID_ARGUMENT` without changing state. The approved command families and flags are:

| Command | Required / optional inputs | Expected `data.operation` and essential success output |
| --- | --- | --- |
| `instance init` | No required extras | `instance.init`: `instance_guid`, `public_key_hex`, `instance_root`; durably persists key and manifest before success |
| `instance status` | None | `instance.status`: `state`, nullable `instance_guid`/`public_key_hex`, `signing_available`, `recovery_codes` (including config errors when applicable) |
| `instance recover --from ABS [--confirm-unbound-initialization]` | Original backed-up identity directory; **or**, only with confirmation flag, canonical surviving original `signing-key.v1.json` path from an interrupted never-bound initialization | `instance.recover`: original `instance_guid`, `public_key_hex`, `recovered`; strict original-identity checks |
| `ledger init` | None | `ledger.init`: `ledger_id_hex`, `genesis_sha512`, `genesis_block_guid`; use existing instance key, never create another |
| `ledger recover-genesis --ledger-id HEX64 --genesis-sha512 HEX128` | Exact previously durable signed genesis and original local instance identity required; recovers interrupted `ledger init` **or** `ledger join` | `ledger.recover-genesis`: `ledger_id_hex`, `genesis_sha512`, `genesis_block_guid`, `recovered`; idempotent only for same pin |
| `ledger join --ledger-id HEX64 --genesis-sha512 HEX128 --genesis-file ABS` | All three required; complete raw genesis verified in memory before any disk write | `ledger.join`: `ledger_id_hex`, `genesis_sha512`; specified digest is explicit trust confirmation |
| `key backup --directory ABS` | Destination | `key.backup`: `directory`, `instance_guid`; identity records preserved together |
| `key restore --directory ABS` | Source | `key.restore`: `instance_guid`, `public_key_hex`, `restored`; strict original-identity match |
| `block publish --event-file ABS [--block-guid UUID]` | Raw Version 1.03 nonrevocation event body; caller may retain approved optional GUID control, while current UTC timestamp is always generated internally; no caller time override | `block.publish`: `ledger_id_hex`, `block_guid`, `sha512`, `durable`, `authorization`; signs with persisted local authorized key |
| `master countersign-revocation --outer-signer-public-key HEX --revoked-public-key HEX --output ABS` | Healthy bound authorized first consenting master A; generates GUID/current consent UTC internally; output is exact 229-byte signed consent bundle per Technical Design §6.3 | `master.countersign-revocation`: consent SHA-512, signature hex, output path, countersigner public key; never private seed |
| `block publish --revocation-consent-file ABS` | B (bound authorized outer signer); existing archived matching consent GUID uses §13.3.1; validates exact A-signed 229-byte consent bundle, generates B current UTC header timestamp, publishes 1.03 137-byte revocation event | `block.publish`: same fields as ordinary publish including required `path`, plus `consent_timestamp_utc_ms` and `consent_age_ms`; never accepts caller-supplied timestamps |
| `block import --input ABS` | Raw `.BLK` or `DDLB` | `block.import`: `results`, `durable_count`; per-item result contains `ledger_id_hex`, `block_guid`, `sha512`, `status`, `reason`, `duplicate`, `durable` |
| `block get --id UUID --output ABS` | optional `--sha512 HEX` identifies an exact active signed block | `block.get`: `path`, `bytes`, `sha512` |
| `block export --output ABS` | Optional `--ledger-id`, `--id UUID`/`--sha512`, or inclusive timestamp bounds; peer missing-hash filter deferred to Phase 4 | `block.export`: `path`, `bytes`, `sha512`, `block_count` |
| `config get` / `config set` | `set` requires nonempty documented resource-limit subset | `config.get` / `config.set`: `limits` |
| `status` | None | `status`: `instance`, `binding`, `signing`, nullable `blocks`, required `projection` (Phase 1 `not_installed`), nullable `peers` |

**Approved outcome conventions:** Exit `0` success; `2` invalid arguments/frames/signatures/events and expired signed consent; `3` truthful `PARTIAL_IMPORT`; `4` state/authorization/identity/recovery errors; `5` resource/time limits; `6` I/O/uncertain-durability/internal failure. JSON success is `{"ok":true,"data":{},"error":null}` and error is `{"ok":false,"data":null,"error":{"code":"CODE","message":"TEXT","retryable":false,"details":{}}}` with command-specific `data`. **Current codes:** exit 2 `INVALID_ARGUMENT`, `BAD_FRAME`, `HASH_MISMATCH`, `BAD_SIGNATURE`, `BAD_EVENT`, `UNSUPPORTED_VERSION`, `CONSENT_EXPIRED`; exit 3 `PARTIAL_IMPORT`; exit 4 `RECOVERY_REQUIRED`, `SIGNING_IDENTITY_UNAVAILABLE`, `IDENTITY_MISMATCH`, `DUPLICATE_INSTANCE`, `NOT_AUTHORIZED`, `AUTHORITY_UNRESOLVED`, `ALREADY_BOUND`, `GENESIS_MISMATCH`, `BLOCK_NOT_FOUND`, `BLOCK_GUID_CONFLICT` (nonretryable), `BLOCK_ARCHIVED` (nonretryable), `LEDGER_IDENTITY_MISMATCH`, `OUTPUT_EXISTS`, `CONFIG_CORRUPT`, `CONFIG_IDENTITY_MISMATCH`; exit 5 `RESOURCE_LIMIT`, `PROCESSING_TIMEOUT`; exit 6 `IO_ERROR`, `DURABILITY_UNCERTAIN`, `INTERNAL_ERROR`. `BLOCK_ID_DISPUTED` is **not** an active Phase 1 outcome under ARCH-014; it is historical. `error.details` includes relevant paths/reasons/instance identity/fingerprints and ordered import results without exposing secrets. `retryable` describes potential recovery of the **same operation**, not a safe automatic SQL replay. Exact per-item import results follow the single §13.4 contract below; QA vectors may add validation detail but not change mandatory fields.

**Initialization:** `instance init` succeeds only for a genuinely new, explicitly initialized target after path/identity preflight. Write/flush/publish the encrypted key record first, then the nonsecret instance manifest; no automatic startup initialization. Any detected partial temporary/key/manifest remnants require explicit recovery. The key must be durably persisted before acknowledging initialization. `ledger init` then creates one durable **Version 1.03** self-signed 227-byte genesis signed by that saved identity. A crash after durable genesis but before manifest binding requires explicit reconciliation and binding recovery; never silently create a second genesis. `ledger join --ledger-id HEX64 --genesis-sha512 HEX128 --genesis-file ABS` validates the supplied raw signed genesis entirely in memory before persistence; the independently supplied ledger ID and full signed-genesis SHA-512 establish the trust pin, never the local replica key. A crash after durable genesis but before manifest binding is recoverable through `ledger recover-genesis` with the same two trusted identifiers. `instance.identity.json` persists the pinned ledger ID and genesis fingerprint outside future `.DLDB` projection.

**Identity gate:** Missing, corrupted, mismatched or undecryptable key/manifest suspends all ordinary SQL and ledger processing, including reads, replay, imports, export and peer synchronization. Only `instance status`, `status` (diagnostic subset), `instance recover`, `key restore`, and safe read-only diagnostics are allowed (plus verified `ledger recover-genesis` when original identity is usable). Restore must reproduce the original expected Ed25519 public key; duplicate active identity is rejected on the same host. Removing `.DLDB` must never remove the manifest/key. No `.DLID` exists. `key backup` is an explicit operation, not permission for ordinary processing while key is unavailable.

## 4. Signed-block import, storage, status and export

### Storage organization

The source of truth is the set of independently authenticated **exact-byte** `.BLK` files. **Approved:** keep them under `<database-basename>/BLK/` where `<database-basename>` is the name (without `.DLDB`) of the database file; matching advisory status resides under a separate sibling `<database-basename>/STAT/`, with identical relative UTC-date paths and filename stems:

```text
<database-basename>/BLK/YYYY/YYYYMM/YYYYMMDD/
  YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.BLK
<database-basename>/STAT/YYYY/YYYYMM/YYYYMMDD/
  YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.STAT
```

This filename layout is not a protocol encoding. Verify actual bytes even if the name appears valid. `HHMMSSssss` consists of UTC `HHMMSS` plus four fractional digits with the last digit `0` at millisecond resolution. Support a documented non-calendar fallback for valid signed int64 timestamps outside host calendar range. The SHA-512 suffix is over the **entire raw signed block**, including the signature, and distinguishes disputing variants of one block GUID.

**Owner-approved inventory approach (exact peer/cache byte grammar under review):** Daily leaf inventory hashing sorts exact `.BLK` filename stems (remove only the `.BLK` extension) by ordinal ASCII bytes and hashes a versioned, binary, length-delimited serialization with SHA-256. Parent folders hash sorted child-folder names together with raw child digests. Filenames include full-block SHA-512 for exact-byte identity and auditing; cache files are rebuildable and never authoritative. Hash comparisons are meaningful only for the same pinned ledger ID and full genesis SHA-512, not merely the same local folder name.

### Retention and durability

- Parse, bound, hash, and verify received blocks before official projection effects. In Phase 1 an unknown signed protocol version is rejected with `UNSUPPORTED_VERSION` **without durable retention** (`opaque_count=0`). A *new incoming* cryptographically valid block whose historical authority cannot be proven is **not written to disk or retained as `.XBLK`**; return retryable `AUTHORITY_UNRESOLVED`. Only previously durably accepted `.BLK` files may later be archived as `.XBLK` when newly received earlier history invalidates them. See the controlling §14.1.
- Write a unique temporary file in the target filesystem; flush exact bytes; publish with a safe atomic no-overwrite rename; ensure directory-entry persistence as supported on the host; only then report acknowledged durable receipt. Partial `.BLK` files must never be treated as accepted.
- Identical exact-byte blocks are idempotent duplicates. Under ARCH-014, an incoming block reusing a retained GUID with different signed bytes is rejected non-destructively as `BLOCK_GUID_CONFLICT`; no specialized identity-dispute arbitration or direct-to-`.XBLK` publication is required. Newly received unauthorized/unresolved variants are not stored; previously accepted blocks later invalidated by earlier historical authority may be archived as `.XBLK`.
- `.STAT` sidecars are **advisory, replaceable and potentially stale**. Rebuild them as needed; they never authorize materialization or override current canonical history. Projection generation/checkpoint records are committed in SQLite **with** official state changes.

A Phase 1 block's reported disposition uses `retained`, `pending`, `quarantined`, or `rejected` with a machine-readable reason; `applied` requires the future Phase 3 projector and `opaque` is reserved. **Retained**, **durable**, and **projected** are distinct. An authenticated authorized block is `retained`, even with no `.DLDB`; `pending` describes only previously accepted history that later becomes authorization-unresolved and is archived as `.XBLK`. New unresolved imports are `rejected` without durability, with retryable reason `AUTHORITY_UNRESOLVED`. A full replay or late earlier block can change statuses without changing original `.BLK` bytes.

### Import/export behavior

- Import exact single-block bytes or the existing `DDLB` container; validate framing, hash, signature and ledger identity safely. A partially completed batch retains independently durable preceding blocks; never claim all-or-nothing batch import.
- `block get` retrieves only **active `.BLK`** bytes. A conflicting incoming GUID never displaces an existing verified active block; `--sha512` never bypasses `.XBLK` exclusion. If a requested exact digest exists only in `.XBLK`, return `BLOCK_NOT_FOUND` with reason `ARCHIVED_NOT_EXPORTABLE`.
- `block get` returns the **exact original raw signed-block bytes**. **Every `block export`** (including zero- or one-block selection) returns the existing Version 1 `DDLB` framing: `DDLB` magic (4 bytes), version uint16 big-endian, count uint64 big-endian, then count repetitions of `(length uint64 big-endian, original full signed block bytes)`; no re-signing or reserialization.
- Deterministic batch ordering uses canonical event order with full-block digest as tie-breaker when needed. Incremental missing-set exchange compares hashes/IDs of **active `.BLK` files**, not only timestamps; local-only `.XBLK` files are not exported or included in peer reconciliation.
- Limits on raw bytes, decoded bytes, import memory, CPU/time and peer resources remain required and configurable. Earlier PostgreSQL adapter exact min/max validation tuples and test-harness timing conventions are **not automatically inherited**.

## 5. SQL behavior, read barriers, and errors

Except in identity-recovery state, this CLI is an operational surface **alongside** ordinary SQLite C API/SQL access; it is **not a substitute** for standard supported SQL mutation submission. An authorized master's supported SQL mutation path publishes authenticated blocks first. Only the trusted projector changes official `.DLDB`. Unsupported SQL commands or alternate mutation interfaces must fail safely rather than bypass the ledger. A replica refuses user mutations.

Supported SQL reads observe a consistent locally projected state and may be network-stale. Affected SELECTs pause while an already-known reconciliation/rebuild would expose intermediate inconsistent state; they never wait for hypothetical unreceived remote blocks. A successful write publication acknowledgment need not make the value immediately SELECT-visible. `RETURNING`, transaction result tags, and partial-publication reports must describe what actually happened, without promising group-atomic multi-block commits.

**Important distinction:** The original PostgreSQL-specific SQLSTATE codes `ZL001`, `ZL002`, `ZL003`, `08007`, server error fields, `COPY FROM STDIN`, `COPY TO STDOUT`, and PostgreSQL `MERGE` requirements do not automatically apply to SQLite clients. The SQLite implementation needs an explicit, separately reviewed mapping to SQLite's result/extended-error APIs and normal SQLite transaction behavior. This specification **does not claim that mapping has been finalized**.

## 6. Private signing keys and recovery

**SEC-002 approved baseline (2026-11-08):** Every explicitly initialized instance, master or replica, generates an Ed25519 keypair using secure randomness and durably persists it before initialization succeeds. Private material resides in a separate **versioned key file**, encrypted at rest with **AES-256-GCM**, a **fresh random nonce for each encryption**, and a **versioned application-wide symmetric key embedded in the public source**. The embedded wrapping key is recoverable by anyone reading the source: this is **obfuscation against casual inspection, not protection against determined file holders**. Use a portable `ISigningKeyStore` abstraction and appropriate best-effort OS file permissions; no mandatory DPAPI, Keychain, Keystore, hardware service, cloud provider or startup password/PIN. Keep the key and nonsecret instance identity record outside `.DLDB`, `.BLK`, `.STAT`, repository and normal projection backups. The identity survives projection deletion/rebuild. Verification/replay are unattended and require only public keys; loss of the original private key triggers **recovery-required suspension of ordinary SQLite and ledger operations** (including read-only replay), never silent regeneration; status/diagnostics/original-identity restoration alone remain available. Optional disaster recovery must restore **the identical Ed25519 public key**. The **Owner-approved exact** signing-key Version 1 JSON fields, AES-256-GCM nonce/tag/AAD and identity-manifest Version 2 fields are specified in [SQLite_Architecture_and_Implementation_Plan.md](SQLite_Architecture_and_Implementation_Plan.md) §§8.3–8.4; the approved 88-byte AAD remains unchanged.

This project uses **digital signatures**, not private-key encryption of public ledger bytes. The ledger ID is the original genesis signer public key and a permanent identity; mere possession of that key is not permanent master authorization. A private key's mere possession is not canonical master authorization. Normal startup, replay and reconstruction **must not prompt** for a phrase, PIN, password or key-unlock action. Existing keys whose file is missing, malformed, undecryptable or whose derived public key differs from the persistent instance-identity record put the instance in recovery-required state; do not silently replace them or serve ordinary read-only SQL/ledger operations. Key rotation, restore and version upgrades must preserve identity unless the Owner separately approves an identity replacement operation.

## 7. Replay, status, and diagnostics

Once identity availability is verified (or the original identity has been restored), the projector must reproduce state from signed retained history including genesis, authority history, schema events and row changes. Full deterministic replay is an acceptable first implementation. Without the expected private key, ordinary replay is paused by Owner operational policy even though signature verification itself needs only public keys. It should guard affected reads and official writers, use SQLite-supported recovery lifecycle, and atomically persist projection progress alongside projected changes. Reconciliation/failure states must be visible through management commands and persistent diagnostics; a failed rebuild must never silently expose half-reconstructed state. Selective replay and zero-downtime projection swaps are future optimizations, not exceptions to full-replay correctness.

A status report should distinguish current canonical applied work from unapplied retained variants, pending authority (distinct from schema/projector dependencies), GUID-conflict error diagnostics, and missing projection. The status is a local snapshot and **cannot prove global network completeness**.

## 8. Incremental implementation and contract freeze

1. **Independent ledger:** instance identity, genesis/keys, approved signed protocol 1.03 codec, signing, verification, durable `.BLK`, import/export/status; no database required.
2. **Native SQL interception:** supported SQLite C API writes on authorized masters produce durable authenticated `.BLK` history or fail safely, while official `.DLDB` state remains **unmodified**. Limited isolated provisional SQL evaluation for tests may be used before any projector exists; no persistent alternate official store.
3. **Ledger-to-SQLite projection:** customized `.DLDB`, projector-only writes, exact types, `.STAT` regeneration, progress transactions, full rebuild and read consistency.
4. **Peer exchange:** configured peers, independent offline masters, missing-block reconciliation and eventual convergence.

**Phase 1 contract scope:** The Owner-approved manifest, key-file grammar and 88-byte AAD, timestamp fallback, commands/flags, basic result fields and exit groups are in force. Detailed Phase 1 command/state/error contracts are specified in §13 for deterministic QA. Peer protocol, advisory `.STAT` sidecar internals, and projector/SQLite error details are **later-phase gates**, not Phase 1 CLI blockers. These operational details are *draft engineering obligations*, not changes to the Version 1 signed-wire format. Tests and implementation are assigned by the Project Manager to the Developer and QA under their respective permissions.

## 9. ARCH-003 recovery and path policy — current Owner direction

Support folder `ABC/` beside intended `ABC.DLDB` contains **no `.DLID`**; `instance.identity.json`, `signing-key.v1.json`, optional approved `instance.config.json`, `BLK/`, `STAT/` and temporary `DELn/` are the approved basic layout. ## 10. Persistent signing-key and genesis identity — OWNER APPROVED

The Owner-approved **Version 1 key-file JSON/AAD** remains in SQLite Architecture Plan §8.3: 32-byte Ed25519 seed AES-256-GCM-obfuscated under publicly embedded `application-wide-v1`, fresh 12-byte nonce, 16-byte tag and exact **88-byte** binary AAD. This key-file version is **independent** of signed protocol 1.03. The nonsecret `instance.identity.json` holds instance GUID, expected public key, key-file name and nullable trusted `{ledger_id_hex, genesis_sha512}` binding; `ledger_id_hex` is 64 lowercase hex of the original genesis signer Ed25519 public key (Owner-approved manifest Version 2), independently of `.DLDB` and signed `.BLK`. `.DLID` is removed; its information is merged into the manifest. No mandatory OS keystore or human unlock, and no silent key replacement. Expired/unavailable original keys enter recovery state; all ordinary processing pauses. Recovery remains an explicit operation with old public key/ledger binding verification.

## 11. Phase 1 interoperability — Owner-approved Protocol 1.03 (ARCH-012 1.02 history retained below)

Active signed ledger block header `version=0x0103` (major/minor one byte each); the inherited 1.01/1.02/1.03 row-value tags are **five native SQLite classes** (`0x00` NULL, `0x01` INTEGER, `0x02` REAL, `0x03` TEXT, `0x04` BLOB). Column definitions encode the actual declared type text, not historical `declared_type_tag` or DECIMAL parameters. Historical `0x0001`, 1.01 (`0x0101`) and 1.02 (`0x0102`) signed-block formats are incompatible with active 1.03 (`0x0103`); reject them rather than reinterpret their bytes under the active grammar. The independent `DDLB` transport batch version `0x0001` remains unchanged. Full signed genesis is 227 bytes in active 1.03 (this size first appeared in historical 1.02; 211 bytes in historical 1.01). Canonical event order is `(timestamp_utc_ms, block_guid, signer_public_key)`.

**Approved out-of-range timestamp fallback:** A signed int64 epoch millisecond value outside UTC years 0001–9999 maps to `BLK/OUTOFRANGE/T<16 lower hex>-<block-guid>-<full-sha512>.BLK`, where 16 hex digits are the signed timestamp's 64-bit pattern XOR `0x8000000000000000`. Mirror the stem in `STAT/OUTOFRANGE/`; include this branch in inventory reconciliation. Timestamp age alone never makes an otherwise authenticated block invalid.

## 12. Local `.XBLK` historical archive (Owner-directed) and approved projection-delay setting (2026-11-09)

**Compact local names — Owner-approved directory/file convention:** `BLK/YYYY/YYYYMM/YYYYMMDD/` and separate matching `STAT/YYYY/YYYYMM/YYYYMMDD/` contain `YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>.BLK` and the same stem with `.STAT`. `HHMMSSssss` is derived from the signed UTC millisecond timestamp with the fourth fractional digit zero. The proposed invalidation archive uses `YYYYMMDD-HHMMSSssss-<block-guid>-<signer-public-key>.XBLK`, where the signer public key is 64 lowercase hex digits. File naming is metadata, not a signed wire change. Owner direction: no specialized same-timestamp/GUID/signer `.XBLK` collision feature is required for Version 1; rename operations must never overwrite an existing file and must preserve original bytes if a destination unexpectedly exists.

**Historical invalidation — Owner-directed:** When newly available earlier authority history makes a formerly authorized signed block inapplicable, retain its exact bytes locally but remove/invalidate its advisory `.STAT` through the STAT manager, rename `.BLK` to `.XBLK` without overwriting existing files, and reconcile projection through full replay (or future equivalent selective replay). While archived, `.XBLK` **never propagates**: exclude it from peer inventory, announcements, ordinary block export and peer service. Reevaluate archived files whenever canonical historical authorization changes. If a former `.XBLK` is authorized again at its signed position, validate the retained signed bytes, recover the full-block SHA-512, rename it back to the standard `.BLK` filename, update `TREE.HASH` and restore normal push/pull eligibility; materialization still follows normal projection rules. `.XBLK` is not a corrupt-signature category. A no-overwrite failure pauses the transition and reports an error without deleting retained bytes. This approved local-only exception means equality of advertised active inventories does not imply equality of locally archived historical bytes.

**Projection delay — Owner-approved behavior:** Expose configurable nonnegative `projection_delay_seconds`, **default 0**, delaying **only** ordinary row/schema projection until `signed_timestamp_utc_ms <= node_UTC_ms - delay_seconds*1000`, with overflow-safe arithmetic. Inbound verification, durable acceptance, current canonical authority evaluation and master-signing eligibility are not intentionally delayed. Report `pending_by_age` separately from `pending_authority`, `reconciling`, and `failed` (serialized field names are draft). Return consistent but intentionally stale SELECT results while eligible work is held; apply normal read barriers during replay. Re-evaluate cutoff safely when configuration changes; never promise finality, missing-peer completeness, or absence of late-block rebuild. Exact flag/JSON schema, maximum value and clock-jump behavior remain to be finalized by Developer/QA and approved before public interface freeze.

### 13.1 Common parsing, paths, output, atomicity

- `--instance-root ABS` is a required absolute path to the intended same-basename support root. Options are long-form, case-sensitive; no positional aliases or short flags are defined. All `UUID` values are canonical lowercase RFC 9562 hyphenated strings; SHA-512 digests are exactly 128 lowercase hexadecimal characters; public keys are exactly 64 lowercase hexadecimal characters. Decimal integer arguments are ASCII base-10 with optional leading `-` only for **signed** timestamps, no whitespace, decimal points, plus sign or exponent; reject overflow before any filesystem mutation.
- Exactly **one complete JSON object plus final LF** goes to stdout for **each finite command**, including failures; stdout contains no progress text or private material. UTF-8 without BOM. `message` and human diagnostics may vary, but **all code/status keys, required nulls and enum values below are stable**. Additional unrecognized schema fields are not emitted in Version 1 of the Phase 1 CLI contract. CLI errors go to stderr only as human-readable additional diagnostics, never as a replacement for stdout JSON. Machine-readable JSON numbers are nonnegative counts/byte lengths that fit signed 64-bit; timestamps are **decimal strings** when represented in JSON to avoid binary64 precision loss.
- Success is `{"ok":true,"data":<object>,"error":null}`. Failure is `{"ok":false,"data":null,"error":{"code":<SCREAMING_SNAKE_CASE>,"message":<string>,"retryable":<bool>,"details":<object>}}`. Every success `data` requires a literal `operation` string matching the qualified command (`instance.init`, `block.publish`, etc.). For `status`, `operation="status"`. No private seed/ciphertext/AES key appears in any response.
- An output file, backup member, or signed `.BLK` is acknowledged as `durable:true` **only after complete content and its final destination-directory entry have met the platform's documented durability procedure**; a short write, failed flush, or uncertain rename returns an I/O failure/uncertain-result diagnostic, never a false durable acknowledgment. Use unique temporary paths and **no-overwrite** final publication. Crash-recovery must never delete the only surviving signed bytes or identity record. If a platform cannot provide the required acknowledgment, fail closed with `DURABILITY_UNCERTAIN` (exit 6). Exact fsync/FlushFileBuffers behavior is subject to Windows 11 QA qualification.
- A healthy instance holds an exclusive same-host identity lock for mutating and ordinary ledger commands; `DUPLICATE_INSTANCE` (exit 4) names the instance GUID, not a secret. Diagnostic `instance status`/`status` remain available in recovery. Identity-recovery mode blocks `ledger init/join`, `block publish/import/get/export`, `master countersign-revocation`, key backup, normal config operations, and all ordinary SQL/replay/synchronization until recovery succeeds; only `instance status`, diagnostic `status`, `instance recover`, `key restore` and `ledger recover-genesis` **when the surviving original identity and genesis can be validated** are admissible. `ledger recover-genesis` cannot bypass a missing/corrupted signing key.

### 13.3 Publication, genesis and identity recovery

- `block publish` is available through both the CLI and an equivalent database-independent managed ledger-library operation. For ordinary events the library accepts the exact Version 1.03 **uncompressed** non-revocation event payload bytes; it generates a fresh block UUID unless the caller provided the already approved optional GUID, and **always** generates its own current UTC millisecond timestamp and returns a structured outcome equivalent to CLI `data`; it does not require a `.DLDB`, SQL parser, projector or peer service. It uses the **persisted local** Ed25519 key, constructs the standard signed `0x0103` envelope and checks the known canonical authorization state at the chosen position **before** durable `.BLK` publication. Only a presently authorized master may publish; a replica key alone confers no publication rights. Invalid events (including REAL NaN), unavailable keys, unmet revocation signatures, limits, and missing authorization fail **without publishing** a new authenticated block. No import-only test escape hatch bypasses verification. **An explicit-GUID retry whose original publication was later archived uses §13.3.1 (`BLOCK_ARCHIVED`); it does not create a new publication.**
- `REVOKE_MASTER` uses the exact signed A consent package, with A-generated block GUID and consent timestamp; B generates the separate final block timestamp. The public CLI has no timestamp input and B uses `block publish --revocation-consent-file ABS` for event kind `0x21`; generic `--event-file` refuses `0x21` to prevent bypassing A-consent parsing/validation. The CLI constructs the 137-byte `0x21` payload and obtains the valid countersignature using the exact existing §6.3 message before publication. The corresponding library APIs generate A's consent UUID/time at A and B's official current-UTC block time at B; no caller-set time fields exist. The final block must reuse the consent UUID, not regenerate it. **When that same GUID already exists only as a matching `.XBLK`, the retry returns `BLOCK_ARCHIVED` as specified in §13.3.1 before attempting a fresh final timestamp or evaluating new consent expiry.** QA may alternatively independently construct full authenticated signed blocks and submit them using `block import`. This preserves the event-kind code and authority model, but **changes the approved signed wire to Version 1.03** and the revocation event body to 137 bytes.
- `ledger init` uses the existing persisted key to create a **single approved Version 1.03 self-signed empty-payload 227-byte genesis block**, flushed to `.BLK` before atomically pinning `{ledger_id_hex, genesis_sha512}` in the manifest. On durable genesis plus interrupted manifest binding, subsequent `ledger init` must return `RECOVERY_REQUIRED`/`GENESIS_BINDING_INCOMPLETE` and must **not create another genesis**. Evidence includes the valid local-signed genesis and initialization artifacts; no assumption that absence of the manifest binding equals a fresh attempt. Multiple conflicting locally authored genesis candidates trigger `GENESIS_CONFLICT`, never automatic selection.
- `ledger recover-genesis` is the **Owner-approved explicit idempotent recovery interface for BOTH interrupted `ledger init` and interrupted `ledger join`** after the exact signed genesis `.BLK` became durable but the Version 2 manifest binding did not. It requires the **original local instance** manifest and decryptable signing key, whose instance GUID and derived public key must still match each other; recovery never regenerates or replaces that identity. Search retained local `.BLK` records (including `OUTOFRANGE`) for the **exact independently supplied `--ledger-id` and full `--genesis-sha512`**, and validate the existing raw 227-byte `0x0103` genesis framing, empty payload and payload hash, Ed25519 self-signature, exact `genesis.signer_public_key == genesis.ledger_id == supplied ledger ID`, and SHA-512 of the **entire signed genesis** equal to the supplied fingerprint. **Locally created ledger (`ledger init`):** additionally require the genesis signer/ledger ID to equal the local instance public key. **Joining replica (`ledger join`):** do **not** require genesis signer/ledger ID to equal the replica's public key; the replica retains its independent Ed25519 identity and is not granted master authority by joining. A missing matching durable genesis, invalid signature, conflicting genesis for the selected ledger, different existing manifest trust pin, or unavailable/mismatched local identity must fail closed with the existing recovery/genesis/identity diagnostics, without rewriting signed bytes or adopting another identity. If already bound to the exact supplied ledger ID/fingerprint, return idempotent success without changing the binding; if unbound with one matching durable genesis, atomically commit exactly that binding while preserving the local instance GUID/public key/key-file reference. A crash during recovery may be retried with the same two identifiers; no second genesis is created. This command does **not** bootstrap a fresh join with an unpersisted genesis: that uses `ledger join --genesis-file`.
- `instance recover --from` and `key restore --directory` recover from the **original identity** only: verify AES-GCM authentication with the approved 88-byte AAD and rederive the same Ed25519 public key; reject a different instance GUID, identity, pinned genesis, or overwrite of live unrelated records. **ARCH-011 explicit exception:** when the canonical original signing-key file survived **but manifest and genesis were never durably created**, `instance recover --from <signing-key.v1.json> --confirm-unbound-initialization` may restore a **matching unbound** manifest after checking all local evidence and the operator's explicit assertion of interrupted setup. Without that confirmation, or if durable binding/genesis/contradictory remnants exist, remain in recovery. No key is generated or replaced. Idempotent retried recovery must not erase the original key. Residual temp files are diagnosis/recovery evidence, never permission to run `instance init` automatically. No `.DLID` is created. Exact acceptance in §14.4.

### 13.3.1 Owner-approved `BLOCK_ARCHIVED` retry contract (ARCH-014)

This applies to **both** an ordinary `block publish --event-file ABS --block-guid UUID` retry and a `block publish --revocation-consent-file ABS` retry (where the signed A consent already supplies the original GUID). The caller must have a healthy, matching local instance identity and syntactically valid arguments; recovery-mode restrictions still apply. Before obtaining a new current-UTC timestamp, checking fresh-publication authorization, or checking consent expiry for a **new** revocation, locate and authenticate any already durably retained record with the same ledger ID and GUID, including its `.XBLK` archive. Verify local signer and exact event/consent intent against the original signed bytes. If that matching record is **archived**, report the original completed publication and its *current* classification separately:

- **Failure envelope and process result:** `ok:false`, `data:null`, `error.code:"BLOCK_ARCHIVED"`, `error.retryable:false`, **exit 4**. This is a completed historical publication whose present state is archived, **not** a newly successful active publication. Do not turn it into `NOT_AUTHORIZED`, `CONSENT_EXPIRED` or an active-success response merely because authorization or time changed after the original durable publication. A missing or corrupt identity remains subject to the normal identity/recovery gate; invalid arguments are `INVALID_ARGUMENT`.
- **Required `error.details` schema:** `original_publication` is an object with the original `block.publish` standard fields `operation:"block.publish"`, `ledger_id_hex:hex32`, `block_guid:uuid`, `sha512:hex64`, `timestamp_utc_ms:string`, `authorization:"authorized"`, `durable:true`, `path:path` (**historical `.BLK` path, not a representation that the file is active**). For a revocation, also include the original `consent_timestamp_utc_ms:string` and `consent_age_ms:integer` (the signed timestamp delta, `0..900000`). `current` is an object with required `state:"archived"`, `status:{pending,quarantined}`, `authorization:{pending,unauthorized}`, `reason:string` (the current classification reason), `path:path` (current local `.XBLK` path), and `retained:true`. Required `new_publication:false` and `mutated:false` are booleans at the `error.details` level. No private-key material is exposed.
- **No side effects:** Never rewrite, re-sign, rename, reactivate, export, propagate, or otherwise mutate any existing `.BLK`/`.XBLK`, identity/configuration, status counts or signed history during this retry. A retry does not acknowledge new durability; `original_publication.durable:true` refers only to the earlier successful durable publication. Archive reauthorization remains a separate history-reconciliation operation.
- **Other outcomes:** If the matching retained original is still active `.BLK`, preserve the previously approved idempotent success (exit 0, original active metadata, no new signing). If a retained GUID has different authenticated signer or event/consent bytes, return the existing `BLOCK_GUID_CONFLICT` (exit 4, nonretryable) without modifying it. If there is **no** retained match, apply normal current-UTC publication, authority and (for revocation) signed consent-age rules; do not treat missing evidence as historical success.

**QA cases:** Verify archived ordinary and revocation retries, `BLOCK_ARCHIVED` exit 4 and exact `error.details` fields, no new timestamp/signature/storage/counter change, historical-versus-current path distinction, active idempotent retry, nonmatching GUID collision, and missing-key recovery gate. The tests are QA-owned; this clause does not assert implementation or test completion.

### 13.4 Import, variants, get/export, and error selection

- The `DDLB` container remains **Version 1**: magic `DDLB`, `uint16_BE(1)`, `uint64_BE(count)`, repeated `uint64_BE(length) || exact_block_bytes`. Parse and bound each length before allocation; reject trailing/unaccounted bytes, truncation and arithmetic overflow. Imported signed `0x0103` blocks must pass framing, payload SHA-512, signature, event/REAL validation and ledger-identity checks before durable retention. **New blocks lacking verifiable historical master authority are never durably retained:** they return `rejected` / `AUTHORITY_UNRESOLVED` (retryable) or `NOT_AUTHORIZED` (known false). Missing schema/projector evidence does not constitute missing authorization. Unknown signed-protocol versions return `UNSUPPORTED_VERSION` (exit 2), are **not durably retained in Phase 1**, and do not affect counters; `opaque` and its retention are reserved for a later separately approved phase. Import into a bound instance of a different ledger fails `LEDGER_IDENTITY_MISMATCH`.
- **Single authoritative per-item `block import` result schema (ARCH-014):** Every item has **all** fields `index` (zero-based integer), `ledger_id_hex` (64 lowercase hex or null), `block_guid` (UUID or null), `sha512` (128 lowercase hex or null, of exact signed bytes), `status` (`retained|pending|quarantined|rejected`), `reason` (machine-readable string), `authorization` (`authorized|unauthorized|pending|not_evaluated`), `duplicate` (boolean), `durable` (boolean), and **`retryable` (boolean, required)**. Valid newly accepted authorized `.BLK`: `status=retained`, `authorization=authorized`, `reason=AUTHORIZED_RETAINED`, `durable=true`, `duplicate=false`, `retryable=false`; an exact already durable duplicate is `retained`, `duplicate=true`, `durable=true`, `retryable=false`, but is **not counted as newly persisted**. New inbound unresolved authority: `rejected`, `AUTHORITY_UNRESOLVED`, `authorization=pending`, `durable=false`, `duplicate=false`, `retryable=true` (retry after obtaining evidence). New inbound known unauthorized: `rejected`, `NOT_AUTHORIZED`, `authorization=unauthorized`, `durable=false`, `duplicate=false`, `retryable=false` for immediate retry (later evidence may justify a new attempt). Different incoming signed bytes sharing a retained GUID: `rejected`, `BLOCK_GUID_CONFLICT`, `durable=false`, `duplicate=false`, `retryable=false` without touching history. Only **formerly accepted** records later reclassified may have stored `pending` or `quarantined` status as `.XBLK`. Unsupported versions/malformed inputs are rejected, never opaque-retained, with `durable=false`; other error retryability must be truthful to the specific condition, not inferred from aggregate `PARTIAL_IMPORT`. `sha512` refers to raw signed bytes, not DDLB framing. Missing projector/schema information never creates authority-pending status.
- **Batch results and partial import:** On complete success, `data.total_count` equals input count; `data.durable_count` counts **newly** persisted signed blocks, `data.duplicate_count` counts exact repeats, and `data.rejected_count=0`. The ordered `results` array uses the exact preceding schema. When some succeed but others fail, return exit 3 / `PARTIAL_IMPORT`, with `data:null`, all four counts and **every item result (including per-item `retryable`)** in `error.details`; the top-level error retryability does not replace per-item retryability. If none succeed, return the first error in input order with its ordinary exit group, while preserving results/counts. Independently accepted blocks remain durable—DDLB is not one filesystem transaction. Incoming unauthorized/unresolved blocks and nonidentical reused-GUID variants are **never** persisted or counted as new success.
- `block get`: return the **unchanged signed bytes of one active `.BLK`**. Incoming nonidentical signed bytes that reuse an existing retained GUID fail `BLOCK_GUID_CONFLICT` non-destructively; the already accepted active block remains unchanged. `--sha512` identifies a variant but **does not grant permission to read archived `.XBLK`**; for an exact digest present only in archive, return `BLOCK_NOT_FOUND` with `error.details.reason="ARCHIVED_NOT_EXPORTABLE"`. A nonexistent variant also returns `BLOCK_NOT_FOUND`. For unbound roots with blocks from multiple ledgers, require `--ledger-id` when the query would otherwise be ambiguous. Path output is atomic/no-overwrite; no local `.XBLK` is exported by this normal command.
- `block export`: produce **DDLB Version 1** bytes containing exact, unchanged, currently active `.BLK` signed blocks from **one** ledger. With no filter, select all active blocks of the pinned ledger; for unbound roots auto-select only when exactly one ledger ID is represented, otherwise require `--ledger-id HEX64` or return `AMBIGUOUS_LEDGER` (exit 4). `--id` selects one block GUID; `--sha512` is valid only with `--id` to select the exact signed-byte digest, **not** to expose archived `.XBLK`. Inclusive `--from-timestamp-ms` / `--to-timestamp-ms` filters may appear singly or together but cannot be mixed with `--id`; when both are present require lower ≤ upper. Never export pending, unauthorized or locally archived `.XBLK`. A different signed variant reusing any retained GUID is rejected before persistence as `BLOCK_GUID_CONFLICT`; **there is no active `BLOCK_ID_DISPUTED` export branch or same-GUID arbitration subsystem**. Sort by canonical `(signed_timestamp_utc_ms, raw_block_guid, raw_signer_public_key)`; use full-block SHA-512 only as a deterministic final comparator if needed for byte-identical-ordering metadata, never as a winner-selection mechanism. Return a structurally valid DDLB with count zero for an empty permitted selection. Peer missing-hash filters are Phase 4, not Phase 1.
- Any get/export where no ledger can be inferred because the unbound store is empty must use `--ledger-id HEX64` or return `AMBIGUOUS_LEDGER`. A bound instance never silently switches ledger; an explicit conflicting `--ledger-id` returns `LEDGER_IDENTITY_MISMATCH`. Existing output path collisions are `OUTPUT_EXISTS` (exit 4) and must not overwrite. Retained block existence and successful export do not imply canonical authorization or projection application.

### 13.5 Exact Phase 1 status fields and recovery diagnostics

`instance.status` fields are defined in §13.2. `status` returns the following **required** nested objects:

```json
{
  "ok": true,
  "data": {
    "operation": "status",
    "instance": {"state": "uninitialized", "instance_guid": null, "public_key_hex": null, "recovery_codes": []},
    "binding": {"ledger_id_hex": null, "genesis_sha512": null, "state": "unbound"},
    "signing": {"available": false, "authorized": false},
    "blocks": {"retained_count": 0, "pending_count": 0, "quarantined_count": 0, "disputed_count": 0, "opaque_count": 0},
    "projection": {"state": "not_installed", "applied_count": null},
    "peers": {"state": "not_installed", "connected_count": null}
  },
  "error": null
}
```

The example uses null identity fields for a **newly uninitialized** instance (`instance.state="uninitialized"`, `binding.state="unbound"`); an initialized unbound instance reports its own instance GUID, public key and `signing.available=true`. Local master authorization is distinct from possessing a signing key. Phase 1 projector reporting is always `projection.state="not_installed"`, `applied_count=null`; no block is represented as SQLite-applied. `pending_count` includes only formerly accepted `.XBLK` history with currently unresolved historical authorization, never projection backlog or new rejected input. `retained_count` includes authenticated durable `.BLK`, genesis, and later archived `.XBLK`; `quarantined_count` is a disjoint archival subset for subsequently unauthorized/inapplicable blocks. Under ARCH-014 `disputed_count=0` (reserved) and `opaque_count=0`. No `.XBLK` is an ordinary export/advertised inventory item. Counters are coherent local snapshots, not completeness proofs about unknown peers.

When config exists but fails strict parsing or instance-GUID matching, `status` and `instance status` remain diagnostic-only available, with `instance.recovery_codes` including `CONFIG_CORRUPT` or `CONFIG_IDENTITY_MISMATCH`, **without claiming loss of the signing identity**; `instance.state` remains `bound` or `unbound` if the original key/manifest are healthy. `config get/set` and ordinary operations that depend on those settings fail until explicit operator recovery; never report effective limits from invalid input. If original identity verification fails, `status` remains callable as a **diagnostic-only** operation: `instance.state="recovery_required"`, `instance.recovery_codes` contains sorted error identifiers (such as `SIGNING_IDENTITY_UNAVAILABLE`, `IDENTITY_MISMATCH`, `GENESIS_BINDING_INCOMPLETE`), `binding` contains only safely readable manifest fields or nulls, `signing.available=false`, `signing.authorized=false`, `blocks=null`, `projection.state="not_installed"`, `peers=null`. Do not scan/process ledger blocks to compute fake counts while recovery gate is active. Recovery codes are stable symbolic values even though diagnostic `message` text may vary.

### 13.6 Phase 1 `config` contract and resource limits

`config get` has no Phase 1 filters. `config set --name NAME --value DECIMAL_UINT` changes **exactly one** supported parameter, durably persisting it in the **Owner-approved separate** `instance.config.json` file under the existing instance support root, without modifying immutable identity or pinned genesis binding. Missing file selects the defaults below; malformed or mismatched file fails with a diagnostic and blocks ordinary config-dependent operations until explicit operator repair (see §14.5). The only **Phase 1** accepted setting names are:

| Name | Units | Default | Valid values |
| --- | --- | ---: | --- |
| `max_raw_block_bytes` | bytes | `16777216` (16 MiB) | integer `227..9223372036854775807` |
| `max_decompressed_event_bytes` | bytes | `67108864` (64 MiB) | integer `1..9223372036854775807` |
| `max_inflight_import_bytes` | bytes | `134217728` (128 MiB) | integer `227..9223372036854775807` |
| `per_block_timeout_seconds` | seconds | `60` | integer `1..9223372036854775807` |

These are local operational limits, **not signed-wire maxima**. They may be lowered below the size of previously retained immutable blocks without deleting history; a subsequent command that cannot safely process required data returns a structured `RESOURCE_LIMIT`. Streaming implementation may allow in-flight memory smaller than permitted raw block size; do not require a complete block allocation. Values too large for a supported platform to enforce safely fail `RESOURCE_LIMIT` with a platform capability reason, **without storing the change**. Unsupported names, malformed numbers, zero, negative limits and overflows fail `INVALID_ARGUMENT`; no silent rounding, clamping or partial update. Return the entire `limits` object in stable order with all four exact keys. A `projection_delay_seconds` setting is Owner-approved in principle with default 0 but is **Phase 3** scope; do not silently treat it as a working Phase 1 projector setting.

### 13.7 Phase 1 error precedence and conformance handoff

The error envelope/exit groups from §3 remain authoritative. Add the following exact symbolic errors as needed: `GENESIS_BINDING_INCOMPLETE`, `GENESIS_CONFLICT`, `AMBIGUOUS_LEDGER`, `OUTPUT_EXISTS` (exit 4), `DURABILITY_UNCERTAIN` (exit 6). Unknown inputs always yield `INVALID_ARGUMENT` (2) before touching state. When several **state** gates apply, report the first in this fixed sequence: missing/mismatched identity → `RECOVERY_REQUIRED` (4); duplicate same-host identity → `DUPLICATE_INSTANCE` (4); missing trusted ledger/ambiguous selection → `ALREADY_BOUND`/`AMBIGUOUS_LEDGER`/`GENESIS_BINDING_INCOMPLETE` as applicable (4); unauthorized signer → `NOT_AUTHORIZED` (4); unsupported/invalid signed/event payload → `BAD_FRAME`/`UNSUPPORTED_VERSION`/`BAD_SIGNATURE`/`BAD_EVENT` (2); configured bounds → `RESOURCE_LIMIT`/`PROCESSING_TIMEOUT` (5); I/O failures → `IO_ERROR`/`DURABILITY_UNCERTAIN` (6). For explicit-GUID / signed-consent publication retries after healthy identity validation, inspect the authenticated retained GUID and original bytes before fresh-publication authorization, timestamp generation or consent-expiry evaluation: matching active `.BLK` → original success; matching archived `.XBLK` → `BLOCK_ARCHIVED` (exit 4, nonretryable); different bytes → `BLOCK_GUID_CONFLICT` (exit 4, nonretryable). ### 14.3 Owner-approved Protocol 1.03 revocation preparation and publication

**A — prepare signed consent (on the *first* authorized master):**

```text
ledgerctl --instance-root ABS master countersign-revocation \
  --outer-signer-public-key HEX32 --revoked-public-key HEX32 \
  --output ABS
```

The command derives A's `countersigner_public_key` and 32-byte `ledger_id` from verified persistent local identity/binding, validates A's and B's known historical/current authority, requires distinct A/B keys and target equal to one of them, and **generates both** a new canonical 16-byte random block GUID and `consent_timestamp_utc_ms = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()`. There is **no** `--block-guid` or `--timestamp-utc-ms` argument for this public operation. It constructs the exact Technical Design §6.3 **165-byte** `DDL-REVOKE-v3` message and signs it with A's Ed25519 key. Its output file contains the exact **229 bytes** `message[165] || signature[64]`, published crash-safely with no overwrite. This is not a private-key export.

```json
{"ok":true,"data":{"operation":"master.countersign-revocation","ledger_id_hex":"<64 lowercase hex>","block_guid":"<uuid>","consent_timestamp_utc_ms":"<signed int64 decimal>","outer_signer_public_key":"<64 lowercase hex>","revoked_public_key":"<64 lowercase hex>","countersigner_public_key":"<64 lowercase hex>","consent_sha512":"<128 lowercase hex of signed 165-byte message>","signature_hex":"<128 lowercase hex>","path":"<absolute path>","bytes":229,"durable":true},"error":null}
```

**B — publish with its own current UTC block timestamp:**

```text
ledgerctl --instance-root ABS block publish --revocation-consent-file ABS
```

B must be the exact `outer_signer_public_key` named in A's signed consent. B checks all 229 package bytes, signature, ledger identity, intended target and distinct keys, bound identities, historical master authority of both participants at the prospective final block position, and the **15-minute interval**. B then uses its *own* current UTC milliseconds for the block header and copies A's generated block GUID; it creates the exact **137-byte** `0x21` event, signs and durably publishes the entire 1.03 block. Importers/replayers check the same `0 <= (block.timestamp_utc_ms - consent_timestamp_utc_ms) <= 900000` rule using checked arithmetic on **signed times alone**, not their receipt clock. The event contains A's timestamp and Ed25519 signature; B's block header carries B's timestamp. Invalid, future-relative, or expired consents fail without any new file. No caller can override either timestamp. Retry after a fully durable identical block **still active as `.BLK`** returns its original success; if that exact block is now `.XBLK`, return `BLOCK_ARCHIVED` (exit 4) under §13.3.1. Never create a conflicting second block GUID variant. Expiry compares only A and B SIGNED timestamps, not disk flush completion. If a verified previously durable revocation with the consent GUID exists, return the original result **only while active `.BLK`**; if archived `.XBLK`, return `BLOCK_ARCHIVED` (exit 4) with original metadata and current archive status, without re-signing, even if consent age is now greater than 15 minutes. Otherwise reject expired consent and request a fresh A consent/GUID.

```json
{"ok":true,"data":{"operation":"block.publish","ledger_id_hex":"<64 lowercase hex>","block_guid":"<uuid copied from A consent>","sha512":"<128 lowercase hex>","authorization":"authorized","durable":true,"path":"<absolute BLK path>","consent_timestamp_utc_ms":"<signed int64 decimal>","timestamp_utc_ms":"<B signed int64 decimal>","consent_age_ms":42000},"error":null}
```

`consent_age_ms` must equal the signed block timestamp minus A's consent timestamp (0 through 900000 inclusive); the illustrative `42000` is not a fixed value. Generic `block publish --event-file ABS [--block-guid UUID]` accepts only **non-revocation** 1.03 event bodies, generates a random block GUID unless the approved optional GUID is supplied and always generates current UTC internally, and rejects `0x21` (`BAD_EVENT`, exit 2) to avoid bypassing the two-signature workflow. No `--timestamp-utc-ms` is accepted by either publish path. `--block-guid` is optional only for ordinary **non-revocation** publication; the two-master revocation GUID comes exclusively from A's signed consent and cannot be overridden by B. Library APIs provide equivalent `CreateRevocationConsent(...)` and `PublishRevocationConsent(...)` with no time overrides; test-only deterministic clock/UUID injection is not an ordinary public API. Neither CLI nor API exposes a signing seed.

**Required errors/exit groups:** invalid arguments/package/consent signature/15-minute interval: `INVALID_ARGUMENT`/`BAD_EVENT`/`BAD_SIGNATURE` or `CONSENT_EXPIRED` (exit 2); incomplete historical authority: `AUTHORITY_UNRESOLVED` (exit 4, retryable), known unauthorized signer: `NOT_AUTHORIZED` (exit 4); output collision `OUTPUT_EXISTS` (exit 4); resource limit `RESOURCE_LIMIT` (exit 5); filesystem/uncertain durability `IO_ERROR`/`DURABILITY_UNCERTAIN` (exit 6). On failure, no newly authored block is durably published. QA must verify boundary deltas 0, 900000, 900001 and negative delta; malformed packages, wrong participant, tampered intent, duplicate retries and historical authority changes.

No new incoming same-GUID archive or dispute arbitration; differing bytes under a used GUID are refused as `BLOCK_GUID_CONFLICT`. Existing signed raw `block get` and DDLB `block export` semantics remain unchanged.

## 18. Cross-platform management/API contract (Owner directive 2026-11-17)

The `ledgerctl` command names, UTF-8 JSON response envelopes, error codes, signed-block files, DDLB framing, and identity/configuration schemas are platform-independent contracts. CLI input paths are interpreted using the host filesystem but must not affect signed bytes, ledger identity, canonical replay order, or authorization. The implementation must isolate platform-specific atomic file operations, locking, directory durability and path validation behind portable abstractions; a Windows NTFS implementation may be first. Errors and recovery guarantees remain observable on every subsequently supported platform, although OS-specific diagnostics may contain platform details.

Windows 11 remains the initial required QA qualification. Tests for CLI contracts, crypto, protocol bytes and ordinary error handling should run unchanged on Linux/macOS when those platforms are qualified; filesystem failure injection may require platform adapters. Developers must document platform-specific source files, rationale, portability strategy and unverified limitations. This section introduces no new CLI options, signed protocol fields or platform certification claim.
