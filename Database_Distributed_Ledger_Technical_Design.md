## 1. Purpose and layer boundaries — CONFIRMED

Build a public-data, disaster-resilient, cryptographically authenticated distributed event ledger supporting an eventually consistent relational database on top. **The immutable ledger, not a relational database, is the authoritative data history.** The ledger may exist without a database. Only an **empty** database can initially adopt an existing ledger; it derives schema and data solely by consuming ledger events. Existing supported SQLite SQL interfaces and SELECT/query facilities must be retained, including the SQLite native C API where applicable, but there must be no supported direct SQL-to-official-storage mutation path: ordinary INSERT/UPDATE/DELETE or other supported user-managed data/schema changes submitted through any normal client connection must first produce authenticated ledger events; official storage changes only by ingesting ledger events. The implementation may use different internal components, but bypassing this invariant through an alternative SQL client, administrator-accessible supported interface, or unwrapped server endpoint is nonconforming.

An authorized master receives SQL write requests, evaluates them against the relational state it currently knows (or provisional transactional state), and publishes the resulting **concrete atomic changes** to the ledger before they are ever applied to official materialized storage. The same ledger consumer then applies locally produced blocks as it does remotely received blocks. A successful write acknowledgment can precede local SELECT visibility; client developers must accommodate stale reads. The database and application layers may implement stronger transactional protocols, but the underlying ledger neither promises global synchronous agreement nor interprets a client's business transaction as an atomic group.

**Every block is independent. No block references any predecessor, previous block, head, fork, or chain link.** “Blockchain” is a descriptive term for the authenticated historical collection and must not be interpreted as a hash-linked chain. There is no fork-choice election or dropping otherwise valid blocks to choose a preferred branch. A single logical order is calculated over the accepted blocks presently known to a participant.

## 2. Participation, identity, and authority — CONFIRMED

- **Ledger GUID:** immutable globally unique identifier shared by every block belonging to one ledger.
- **Block GUID:** immutable identifier of an individual block, independent of its ledger GUID.
- **Master:** participant holding an authorized Ed25519 private signing key and permitted to publish blocks and delegate master authority.
- **Read-only replica:** anyone may join, verify, retain, exchange, and materialize blocks without signing authorization. **Every newly initialized local instance nevertheless has its own persistent Ed25519 keypair** under SEC-002. The replica's key does not confer authority without a valid grant; a node with an unavailable private key enters a recovery state that blocks ordinary SQL and ledger processing, including read-only replay, until the original identity is restored. Public-key verification does not cryptographically require a private key, but ordinary processing is intentionally paused under ARCH-003. A replica may relay blocks between disconnected masters.
- **Entity GUIDs:** every table, column, and row has its own immutable GUID, independent of SQL-visible names or declared keys. Names may change without changing identity. A deleted GUID cannot be reused; recreating a same-name entity uses a new GUID.
- **Genesis master:** initial sole signing authority established by the special genesis block; other masters are added with ledger events.

**Grant — CONFIRMED:** Any currently authorized master may issue a `GRANT_MASTER` event identifying a public key. A valid grant sets that key's authorization state to **authorized** at the grant's canonical position. Grants do not stack into separately surviving permissions: a redundant grant to an already authorized key is permitted but does not protect it from a subsequent valid revocation. A later valid grant can re-authorize a previously revoked key; no grant retroactively validates earlier blocks.

**Revocation — CONFIRMED:** A `REVOKE_MASTER` event must be approved by **the master being revoked and one other distinct currently authorized master**, in either order. One provides the ordinary Ed25519 outer block signature and the other provides a countersignature inside the payload. The target's original grantor has no special role. At the event's canonical position, a valid revocation sets the **target public key** to unauthorized as a whole, not merely one grant instance. Subsequent blocks signed by that key remain in retained history but have no materialized effect unless a later valid grant restores authorization prospectively. The two-distinct-authorized-signers condition prevents revoking the sole remaining authorized master. A lost final private key is an operational catastrophe, not an exception to this rule.

**Canonical authorization replay — CONFIRMED:** Process grants, revocations, and other events in the total block order defined in Section 4, irrespective of receipt order. A block is applicable only when its signer is authorized at that canonical position. Late-arriving earlier history can invalidate or revalidate dependent grants and projected effects; re-evaluate those consequences without erasing retained block bytes. A previously accepted block is not guaranteed permanently applicable when missing earlier history later arrives. No separate independent grant-lineage model or grant-block-specific revocation is used.

**CONFIRMED:** The `REVOKE_MASTER` payload field order is fixed in Section 6.3. A block identity is the pair (`ledger_guid`, `block_guid`). Repeated identical serialized blocks are idempotent duplicates, not new events. If different serialized bytes claim the same block identity, **neither variant may be chosen by first-arrival order or applied while that identity is disputed**; quarantine conflicting variants for explicit diagnosis. If one variant was already projected before the conflict became known, the official projection must be reconciled to remove effects that are no longer unambiguously applicable; immutable received bytes are retained. Use a full-block SHA-512 digest to detect byte-level differences. Blocks awaiting missing earlier authorization evidence must be retained as **pending**, without materialized effects, and reconsidered/requested again when relevant evidence becomes available. **CONFIRMED Version 1 disposition:** Retain and quarantine both conflicting authenticated variants; neither may be selected by arrival order or arbitrarily overridden. If either was previously projected, reconcile its affected effects out of the unambiguous official projection. A later separately approved, authenticated protocol extension would be necessary to establish a different winner rule. **Current Phase 1 adjustment:** expose `retained`, `pending`, `quarantined`, and `rejected` with machine-readable reasons; `applied` is reserved for Phase 3 and `opaque` for a separately approved future capability. Disputed variants reside only in local `.XBLK`; exact CLI/JSON definitions are Management API §14. The older proposal to sign only the reusable fixed phrase `I AGREE` is **not approved**. There is no additional Version 1 key-compromise recovery mechanism beyond these ordinary signature/authority rules.

## 3. Genesis and database initialization — CONFIRMED

On creation, each **empty** database must choose one of two paths:

- **Create a new ledger:** generate a new ledger GUID and use the **persisted signing identity of the already initialized local instance** to publish a valid self-signed genesis block. The first master receives authority from authenticated genesis and binding, not from installing/selecting a key. The private key must already have been durably saved outside the projection and ledger files before this succeeds.
- **Join an existing ledger:** select an **existing local ledger** identified by its ledger GUID. Adopt its already-established genesis authority and reconstruct the database solely by replaying authenticated ledger events. The joining instance keeps **its own persistent signing identity** even when it joins as a replica; that public key has no master authority until authorized by canonical grant history. A populated unrelated database cannot join.

**CONFIRMED:** A genesis block uses the same fixed binary envelope as other blocks but has an **empty payload** (`payload_size=0`, compression `0x00`, SHA-512 of the empty bytes). Its outer Ed25519 signature is verified against the public key in the header, which becomes the initial authorized master key. Ordinary non-genesis blocks may not claim genesis status merely by being self-signed.

**CONFIRMED trust safeguard:** Joining pins both the trusted `ledger_guid` and SHA-512 of the full signed genesis block. Persist the binding in `ABC/instance.identity.json` outside rebuildable `ABC.DLDB`; there is **no `.DLID`**. The support directory is deterministically the resolved database basename (`ABC/`), and the manifest records the stable instance GUID/public key and pinned ledger identity. No different genesis can be adopted silently; conflicting signed genesis candidates never become trusted by matching GUID alone.

**CONFIRMED protocol 1.01:** The signed block header `version` is two bytes `0x01 0x01` (`0x0101`), with one byte for major version and one for minor. `1.99` is `0x0163`; `2.00` is `0x0200`. Genesis retains the standard 211-byte empty-payload envelope and SHA-512 fingerprint of the **entire signed genesis block**. The former `0x0001` header identifies the historical, incompatible Version 1.00 value/column grammar and must never be decoded as 1.01. Unknown/future formats can be retained opaque without applying effects. Ledger join verifies the trusted full-genesis fingerprint; operational flags belong to the management specification. **`DDLB` transport container version `0x0001` remains separate and unchanged.**

**Owner-approved onboarding:** A genuinely new, demonstrably empty and unconfigured `.DLDB` with no evidence of earlier instance state may explicitly offer new-ledger creation or join-existing-ledger. The operator must invoke initialization; ordinary startup never creates a signing identity. `instance init` first durably saves the key and instance manifest; `ledger init` signs genesis with that existing key. `ledger join` requires the ledger GUID plus discovery/validation and explicit confirmation of the complete signed-genesis SHA-512. Missing trusted genesis or identity evidence blocks binding. The mere absence of the `ABC/` folder is **not proof** of a new instance.

A nonempty or previously initialized `.DLDB`, remaining identity/key/ledger remnants, or mismatched metadata is **not** a fresh instance. Enter `recovery_required`, pause all ordinary SQL and ledger operations, keep diagnostics and original-identity recovery available, and never silently create replacement identity/genesis. A deliberate new identity is a different instance.

## 4. Canonical chronological order and clocks — CONFIRMED

**OWNER-APPROVED 2026-11-09 AMENDMENT TO VERSION 1 CANONICAL ORDER:** Accepted blocks are ordered by the tuple **`(timestamp_utc_ms, block_guid, signer_public_key)` ascending**. Timestamps are signed 64-bit integers representing **milliseconds since 1970-01-01T00:00:00Z**. Compare block GUIDs using their canonical 16-byte RFC 9562 binary representation; then compare signer public keys using raw 32-byte Ed25519 unsigned lexicographic bytes, not Base64 or locale-dependent text. The block GUID is the **secondary** tie-break and signer key the **tertiary** tie-break. Masters should synchronize clocks frequently against an agreed trustworthy UTC reference, preferably atomic-clock-backed. A signer should not intentionally issue more than one block in a millisecond; if needed, advance to the next millisecond. This rule is authoritative for authorization replay, conflicts, field precedence, recovery and event-derived state.

**Owner-accepted Version 1 compromise risk (2026-11-09):** A stolen authorized master signing key can create backdated blocks, including grants, and cause canonical historical authorization and projection to be recomputed retroactively, potentially compromising the whole ledger. This is knowingly accepted. No timestamp cutoff, unilateral revocation exception, or new finality protocol is added.

No block is rejected solely for its timestamp appearing far in the future or past. A block with an incorrect clock is processed according to its declared signed timestamp, **subject to authorization at that canonical position**. Arrival order never defines canonical order. There is no general guarantee that a participant knows all earlier blocks; late earlier blocks may revise derived state.

**CONFIRMED updated tie behavior (Owner 2026-11-09):** Equal-millisecond timestamps, including grants and revocations, are resolved by raw block GUID **before** raw signer public key, never arrival order. This expressly replaces the October 23 v7 **signer-before-block-GUID** rule and can produce a different canonical result if two signed blocks share a timestamp. **Historical chronology:** The canonical-order amendment alone did not alter block bytes, but the Owner subsequently approved a distinct breaking signed-wire revision **1.01 (`0x0101`)**, replacing historical `0x0001` value/column encoding. The active signed header version is therefore changed. Do not mix implementations using the former signer-before-block-GUID order or historical wire grammar; no released ledger migration is required. **CONFIRMED 2026-10-22:** SQL leap-second literals with seconds field `:60` are rejected, not normalized by local clock rules. Operational time synchronization methods remain implementation choices. No clock-skew quarantine is required.

## 5. Custom binary block wire format — CONFIRMED

Blocks are raw binary, not JSON, Base64, CBOR, or serialized SQL. The layout is packed, with no alignment padding. Multibyte integers use **big-endian** byte order and GUIDs use canonical RFC 9562 byte ordering. Fields are laid out sequentially:

| Field | Encoding | Bytes | Zero-based offset |
|---|---|---:|---|
| `version` | unsigned 16-bit | 2 | 0–1 |
| `ledger_guid` | UUID binary | 16 | 2–17 |
| `block_guid` | UUID binary | 16 | 18–33 |
| `timestamp_utc_ms` | signed 64-bit epoch milliseconds | 8 | 34–41 |
| `signer_public_key` | Ed25519 raw public key | 32 | 42–73 |
| `payload_sha512` | raw SHA-512 digest | 64 | 74–137 |
| `payload_size` | unsigned 64-bit byte count | 8 | 138–145 |
| `payload_compression_type` | unsigned 8-bit | 1 | 146 |
| `payload` | transmitted raw payload bytes | N | 147 through 146+N |
| `signature` | Ed25519 signature | 64 | 147+N through 210+N |

The header length is **147 bytes**; the signature is **64 bytes**; each entire block is **211 + N bytes**, with `N = payload_size`. **For the active 1.01 protocol, the first two bytes are `01 01` (hex), including genesis; 1.00 (`00 01`) must not be silently interpreted with the new grammar.** `version` uses 2 bytes, and `payload_size` uses 8 bytes, permitting values beyond 4 GiB subject to practical resource restrictions. The payload field is not Base64 encoded. 

**Hash:** `payload_sha512 = SHA-512(exact transmitted payload bytes)`; this includes any internal compression properties within those bytes. **Signature:** Ed25519 signs the complete exact serialized block bytes from `version` through the last byte of `payload`, excluding the trailing 64-byte signature. The verified signature authenticates header, timestamp, signer's public key, compression method, payload length, hash, and payload. Ed25519 is a signature scheme, **not symmetric encryption**; the data are public. AES-256-CBC is not used to authenticate blocks.

**Compression type — CONFIRMED:** `0x00` = uncompressed raw event payload; `0x01` = **raw LZMA2** compressed event payload, not a `.7z` archive or Base64. For `0x01`, the first byte **inside `payload`** is the LZMA2 decoder-property byte `p`, followed by the raw compressed stream; the property byte is included in `payload_size` and in the transmitted-payload SHA-512. Version 1 encoding uses **`p=20`, a 4 MiB dictionary**. Other dictionary properties are reserved for future protocol versions. Decoding must require the LZMA2 end-of-stream marker and reject trailing garbage. The signature and SHA-512 digest are checked over transmitted bytes before decompression. Other compression type IDs are reserved. Compression is optional for small events.

**CONFIRMED safety/resource policy:** Implementations must provide **configurable** input-size, decoded-size, CPU/time, memory, and decompression limits. No arbitrary small universal maximum is imposed merely because the outer payload length is 64-bit. Apply bounded incremental processing or reject safely before exhausting resources. Malformed blocks, failed hash/signature checks, unknown event kinds, unknown future versions, and unverifiable authority must never mutate official materialization. In Phase 1, unsupported signed versions and unauthenticated/invalid bytes are rejected without durable ledger retention; valid signed blocks with missing historical authority evidence are locally pending `.XBLK` and cannot be projected or exported while archived. This distinction does not authorize application of unvalidated bytes. **CURRENT PHASE 1 CONTRACT (Owner-approved ARCH-011):** Oversized, malformed, incorrectly authenticated, unknown-version or unsupported event bodies never change official storage. An unknown signed-protocol version is rejected with `UNSUPPORTED_VERSION` and **not durably retained** in Phase 1; `opaque` retention is reserved for a separately approved later capability. Missing historical authorization evidence yields a durable, local-only **pending `.XBLK`** after valid framing/hash/signature/event checks, rather than permanent rejection. Blocks with known unauthorized signing positions and authenticated identity disputes are also retained locally as **quarantined `.XBLK`**, never as active/served `.BLK`. Resource-limit violations produce bounded, structured errors, not uncontrolled memory growth. The implementation must expose configurable maximum raw-block bytes, maximum decompressed-event bytes, and in-flight import-memory limits, plus practical processing/time/CPU limits. **CONFIRMED Version 1 operational defaults (all configurable; not protocol-wide maxima):** maximum raw received block 16 MiB, maximum decompressed event payload 64 MiB, maximum in-flight import memory 128 MiB, and per-block processing timeout 60 seconds. Limits must be enforced safely without uncontrolled memory/CPU allocation; timeouts and limit violations return structured diagnostics and never cause unauthenticated storage effects. Peer connections and resource usage must also be bounded. The exact configuration option names and minimum supportable values are documented in the accompanying management API contract.

## 6. Binary event payloads — OWNER-APPROVED PROTOCOL 1.01

**Active binary protocol:** The outer block and signature layout of §5 are unchanged except for the `version` value `0x0101`. The **value and column-definition grammars change incompatibly** from historical `0x0001`. Each non-genesis block contains one binary typed event (`event_kind:uint8` first), never source SQL. For DML, each changed row is one independent signed block; a statement affecting multiple rows is not a ledger-atomic group. Tables, columns and rows retain immutable 16-byte GUID identities. Updates transmit only changed column GUIDs and resulting values.

### 6.1 Event kinds — protocol 1.01

| Code | Event | Uncompressed body following `event_kind` |
|---|---|---|
| `0x01` | `INSERT_ROW` | `table_guid[16] || row_guid[16] || column_count[varuint] || repeated(column_guid[16] || typed_value)` |
| `0x02` | `UPDATE_ROW` | Same structure as INSERT; **only changed columns** |
| `0x03` | `DELETE_ROW` | `table_guid[16] || row_guid[16]` |
| `0x10` | `CREATE_TABLE` | `table_guid[16] || table_name[text] || column_count[varuint] || complete column definitions in declared order` |
| `0x11` | `DROP_TABLE` | `table_guid[16]` |
| `0x12` | `RENAME_TABLE` | `table_guid[16] || new_name[text]` |
| `0x13` | `ADD_COLUMN` | `table_guid[16] || complete column definition` |
| `0x14` | `DROP_COLUMN` | `table_guid[16] || column_guid[16]` |
| `0x15` | `RENAME_COLUMN` | `table_guid[16] || column_guid[16] || new_name[text]` |
| `0x16` | `ALTER_COLUMN` | `table_guid[16] || complete resulting column definition with same GUID` |
| `0x20` | `GRANT_MASTER` | `grantee_public_key[32]` |
| `0x21` | `REVOKE_MASTER` | `revoked_public_key[32] || countersigner_public_key[32] || countersignature[64]` (unchanged §6.3) |

All GUIDs are RFC 9562 network-byte-order; `varuint` is minimal unsigned ULEB128, and `text` is minimal ULEB128 UTF-8 byte length followed by those exact bytes (no terminator). DML entries are sorted by raw column GUID, with duplicates rejected. A zero-count UPDATE is a no-effect shape; actual SQL writes with no changed values need not create blocks.

### 6.2 Value and schema grammar — SQLite-native Version 1.01

| Tag | SQLite storage class | Bytes after tag |
|---|---|---|
| `0x00` | `NULL` | None |
| `0x01` | `INTEGER` | Signed int64 using ZigZag and minimal unsigned ULEB128 (1–10 bytes) |
| `0x02` | `REAL` | IEEE-754 binary64, exactly 8 bytes big-endian; see approved NaN/∞/−0 rules below |
| `0x03` | `TEXT` | Minimal ULEB128 byte count followed by UTF-8 text bytes |
| `0x04` | `BLOB` | Minimal ULEB128 byte count followed by arbitrary bytes |

**Protocol 1.01 — Owner-approved IEEE-754 REAL rules (ARCH-010):** A `0x02` value carries exactly eight IEEE-754 binary64 bytes in network/big-endian bit order. Accept all finite numbers, signed subnormals, **positive and negative infinity**, and both zero sign-bit patterns. Preserve the exact eight signed bytes on decoding, retention, forwarding, and re-export: positive zero `0000000000000000` and negative zero `8000000000000000` are distinct *wire encodings*, even where SQLite treats them as numerically equivalent or normalizes the sign through storage/affinity. Infinity examples: `7ff0000000000000` and `fff0000000000000`. **Reject every NaN encoding** (all sign bits, exponent bits all one, nonzero fraction, whether quiet or signaling) as `BAD_EVENT`; do not rewrite incoming signed bytes to SQL NULL. An originating *SQLite* SQL expression/bind that SQLite converts from NaN to SQL NULL is encoded as the `0x00` NULL tag, never as an illegal REAL NaN. Independent `block publish` likewise rejects a REAL NaN rather than normalizing a supplied event file. Never claim projected SQLite will round-trip the sign of negative zero; the signed ledger retains its exact originating bytes. The same signed-byte rules apply on all platforms. Reject a REAL payload shorter/longer than eight bytes and never silently cast incoming wire values to a different storage class.**

All other value tags are invalid for `0x0101`. There is **no** separate wire `DECIMAL`, `DATETIME`, `BOOLEAN`, or `GUID` value type; application values use the storage class actually produced by SQLite. Internal row/table/column/ledger/block GUID identities remain unchanged. Column declarations such as `VARCHAR(100)`, `DECIMAL(10,2)`, or `BOOLEAN` are retained as declared SQL type **text** and interpreted by SQLite affinity rules, not translated into extra value tags. The ledger promises SQLite-native precision, **not** arbitrary-precision decimal arithmetic. Preserve the actual SQLite storage-class result after affinity and expression evaluation rather than coercing to an invented type. For supported TEXT, transfer exact UTF-8 bytes without Unicode normalization; unsupported conversion of invalid text bytes must fail explicitly, or applications may store arbitrary bytes as BLOB. Resource limits apply.

**Row NULL/omission:** An UPDATE omitting a column leaves it unchanged, whereas an entry with `0x00` assigns NULL. INSERT omits NULL-valued fields, including explicit SQL NULL; a missing field is NULL unless the supported typed-constant schema default was evaluated at the originating master and included as a concrete value. `UPDATE ... SET column=DEFAULT` similarly captures the evaluated result. A zero-column INSERT is valid. On replay, defaults are **not** re-evaluated; no arbitrary fallback value is synthesized.

**Complete column definition (exact ordered bytes, no padding):**

```text
column_guid[16]
name_length[varuint] || name_utf8

declared_type_length[varuint] || declared_type_utf8
column_flags[1]
default_presence[1]
optional_typed_default
```

`column_flags` bit 0 is 1 for nullable, 0 for NOT NULL; all other bits must be zero. `default_presence` is `0x00` (none) or `0x01` (followed by one typed value, including NULL). `name_utf8` and `declared_type_utf8` preserve the originating supported SQL identifiers/declaration text exactly in UTF-8; an empty declared type is allowed where supported by SQLite. The type text, not a numeric declared-type tag, controls native SQLite affinity. `CREATE_TABLE` includes full definitions in declared order, while row change entries are sorted by GUID. Unsupported SQLite schema features or expressions that cannot be represented and replayed deterministically (such as unrepresented generated columns, triggers, virtual tables, collations, constraints or expression defaults) must be **rejected before publication**, never silently dropped. The supported SQL surface must be explicitly qualified by Developer/QA; no claim of full SQLite syntax support is made by this grammar.

**Version separation:** The former `0x0001` wire grammar with nine value tags and tagged declared types is historical and is not accepted as `0x0101`. No distributed-ledger implementation has been released, so this is a documented prospective breaking version change without requiring migration of released user ledgers. The 211-byte envelope, Ed25519 full-block signing, event-kind codes, countersigned revocation intent, and `DDLB` outer batch framing remain unchanged. Canonical replay still sorts `(timestamp_utc_ms, block_guid, signer_public_key)`.

### 6.3 Second signature on revocation — CONFIRMED Version 1 signed intent and payload

The outer `REVOKE_MASTER` block is signed by one currently authorized master. Its payload contains the **revoked target's 32-byte Ed25519 public key**, the **other consenting master's 32-byte Ed25519 public key**, and that countersigner's **64-byte Ed25519 signature**. The two signers must be distinct and currently authorized at the event's canonical position. **The target must be one of the two signers**, in either role. The target's original grantor has no special role. Revocation affects the target's authorization state as a whole, not an individual grant. There is no grant-block reference.

**CONFIRMED by the originator on 2026-10-22:** The countersigner signs the following exact **149-byte** message, formed by concatenating the fields without separators, length prefixes, or padding:

| Signed field | Length and encoding |
|---|---|
| ASCII literal `DDL-REVOKE-v1` | 13 bytes, exactly those case-sensitive ASCII characters, without a trailing NUL |
| `ledger_guid` | 16 raw bytes in canonical RFC 9562 UUID wire order |
| `block_guid` | 16 raw bytes in canonical RFC 9562 UUID wire order |
| `timestamp_utc_ms` | 8 bytes signed two's-complement integer, big-endian |
| `outer_signer_public_key` | 32 raw Ed25519 public-key bytes |
| `revoked_public_key` | 32 raw Ed25519 public-key bytes |
| `countersigner_public_key` | 32 raw Ed25519 public-key bytes |

The countersigner's signature is the 64-byte Ed25519 signature over these **exact 149 bytes**. It is computed first. The outer signer then signs the ordinary complete serialized block (from `version` through the transmitted payload), thereby authenticating the payload including the countersigner's public key and signature. A verifier independently verifies both signatures and the authorization state of both distinct participants in canonical order. A revocation whose target is not one of the two signers is invalid. This rule prevents the sole remaining authorized master from revoking itself. Late earlier authorization history requires re-evaluation rather than permanent rejection by receipt order.

**CONFIRMED by the originator on 2026-10-22:** The `REVOKE_MASTER` uncompressed event body is exactly `event_kind 0x21 || revoked_public_key[32] || countersigner_public_key[32] || countersignature[64]`. The complete uncompressed body is therefore **129 bytes**. The field order is fixed; the 149-byte signed-intent message above is unchanged. A compressed version, if used, compresses the entire 129-byte body using the ordinary outer compression convention.

### 6.4 Protocol specification boundaries

For the active signed-wire `0x0101`, §6.1–§6.2 fully specify the five value tags and column-definition byte order. SQLite native type affinities and actual storage classes determine authored values. Unsupported expression/schema surfaces fail without ledger publication or official storage effects. Exact Phase 1 CLI and timestamp fallback rules are in the current SQLite management specification; subsequent SQL gateway implementation must publish concrete results and never bypass authenticated blocks. Earlier PostgreSQL-specific type/cast documents and the `0x0001` nine-type grammar are historical, not controlling.

## 7. Deterministic reconciliation and conflict semantics — CONFIRMED

A node retains all authenticated blocks it has received; it validates the signer **against canonical authorization history**, then derives the current schema and rows from applicable events in canonical order. **Later modifications win over earlier modifications to the same affected field** unless a deletion applies; **deletions always win for the same immutable entity GUID**, including after earlier or later updates. The same rule applies to rows, columns, and tables. A deleted row/table/column cannot be recreated with the same GUID.

A delayed update to a GUID for which its earlier INSERT has not yet arrived is retained and logged as temporarily inapplicable; it has no visible effect until the missing earlier INSERT is received and the entity can be reprojected. Operations that cannot yet be interpreted because schema blocks are missing are similarly logged and reconsidered after recovery of dependencies. **A valid block is never ignored or permanently excluded solely because it arrives late or has an earlier timestamp.** When an earlier block changes the canonical interpretation of materialized history, the node **must correct the official projection**: it may roll back/recompute affected rows, schema and dependencies, or rebuild its materialized database **from genesis and the retained relevant full ledger history**. Rebuilding from scratch is conforming, even if slower. Any partial/recovery representation must not pretend the late valid block never existed. A block with missing authority/schema dependencies can remain pending until its prerequisites are known; that is not permission to discard it because of age. Unrelated rows need not be rolled back when selective replay is proven safe. Immutable event history itself never rolls back; only the derived materialized database state can be corrected. A raw block may remain retained even where later validation makes it unauthorized/inapplicable; it must not affect the projection.

**No secondary events from normal replay; all logical corrections are ledger-first — CONFIRMED:** Applying or replaying an ordinary block does not publish another block merely as an echo. Only an authorized master may originate a separate signed corrective event for any ledger-derived logical inconsistency, including a name collision, disallowed NULL, incompatible value, datatype or schema inconsistency, or any other automatic logical data/schema repair. Every such correction, including one proposed by the local master, must first become authenticated ledger history and then be ingested and applied through the same normal ledger pipeline used for remotely received events. No automatic correction may directly alter official database data or schema. A proposed or durably retained correction is not yet official materialization: the affected state remains unresolved until its applicable authenticated correction is ingested and applied. A read-only replica may recognize, retain and diagnose an inconsistency and apply a master's authenticated corrective history; it must not independently originate corrective blocks, generate replacement identities/names/values for official state, or mask a problem with an unsigned change. This prohibition does not prevent required local replay or reconstruction that derives a projection from already-authenticated events. Physical storage maintenance and ordinary supported lossless interpretation of recorded values are not permission to invent a new logical repair. The ledger does not distinguish human-proposed from automatically proposed signed changes.

## 8. Schema identity, name collisions, and conversion — CONFIRMED

Every table and every column has an immutable GUID. RENAME_TABLE and RENAME_COLUMN preserve that GUID. Concurrent rename events targeting the same GUID settle by the latest valid canonical event, unless deletion applies. A dropped column supersedes updates targeting it. Recreating a same-name table or column uses a new GUID; deleted GUIDs cannot be reused.

If distinct entities are created under the same SQL-visible table name, or the same column name within one table, both entities survive. The entity introduced first in canonical **creation-block order** retains the original name. Entity-GUID numerical order and receipt order do not determine priority. An authorized master proposes a separate signed corrective rename for a later-created conflicting entity. The ordinary first correction spelling is exactly `original-name-entityGUIDwithoutdashes`, using the complete dashless entity GUID. Neither ordinary replay nor a read-only replica independently invents this rename.

**Identifier-length fallback — latest owner decision:** For the PostgreSQL adapter's 63-byte SQL identifier limit, measure the proposed corrected SQL-visible name in UTF-8 bytes. If the required corrected name would exceed 63 bytes, the authorized master generates a fresh random UUIDv4 unrelated to the entity GUID, ledger GUID and block GUID. Use that UUID's lowercase canonical hyphenated textual representation as the entire replacement name, rather than truncating the required name or its GUID suffix. The random replacement is a name value, not a replacement entity identity, ledger identity or block identity. Carry that exact name in a separate signed RENAME_TABLE or RENAME_COLUMN event identifying the original target entity GUID. SQL quoting does not change the byte limit. Other database adapters' identifier limits belong in their own public adapter contracts; this paragraph does not silently impose a new protocol-wide wire-name length or truncate received names.

The originating master must ingest and apply its own signed correction through normal authenticated ledger processing before that name becomes official. Proposing a rename, publishing it or durably retaining its block alone leaves the affected official name unresolved. The same rule applies to all automatic logical value/NULL/schema corrections. Until application, name resolution must not arbitrarily choose one GUID or discard either entity; the visible ambiguity or error is deterministic for the applied history. Replicas may apply authenticated corrective history but never independently originate a correction or substitute an unsigned name/value.

Signed automatic and user-initiated renames are ordinary rename events under the same canonical ordering, authorization, identity and delete-wins rules. Preserve all valid independently signed corrections. If masters propose different random replacement names for one entity, each event carries its own literal chosen name; the latest applicable canonical rename determines the resulting name for that GUID. Consumers and reconstruction never rerun random name generation. Participants with different known history may temporarily differ; participants with the same complete applicable history derive the same result. No requirement makes independent masters choose the same random UUID.

If a corrected name conflicts again, an authorized master must resolve the remaining conflict through another distinct signed rename, adding another newly generated GUID-based suffix as needed under the ordinary rule. If that proposed corrected name exceeds the PostgreSQL limit, apply the random-UUID fallback again. Random UUIDs do not guarantee a name is collision-free; a remaining collision is diagnosed and resolved by further valid signed history, not by an unsigned local edit or arbitrary winner. Canonical first-creator precedence and the latest valid explicit rename rules remain in force. Do not suppress earlier signed history, repeatedly emit identical corrections for unchanged known state, or create an uncontrolled replay-triggered correction cascade. Convergence describes replay of the same history, not a bound on the number of future independently proposed corrections.

On a column datatype change, apply only declared supported lossless conversions automatically. An incompatible value is retained/diagnosed unresolved, not silently replaced. If a nullable column may be corrected to NULL, a master may publish that explicit value in a separately signed row correction. Otherwise an authorized master explicitly selects a valid corrective value or applicable typed constant default and publishes it in a new signed UPDATE_ROW block. Never invent zero, empty text, epoch minimum or another arbitrary fallback. Every receiving node, including the origin, changes the official logical value only by authenticating, ingesting and applying that correction. Replicas wait for such signed history. Operational progress/diagnostics and failed reconstruction follow Section 10; exact interim SQL error conventions remain in the adapter contract.

For the PostgreSQL adapter, newly submitted SQL identifiers longer than 63 UTF-8 bytes are rejected rather than silently truncated. Authenticated historical names outside the adapter's representable range are retained and diagnosed without inventing an alternate name or changing identity. This input rule is distinct from the automatic-correction overflow fallback above.

## 9. SQL semantics, constraints, and transactions — CONFIRMED

**Current SQLite SQL adapter (Owner-approved 2026-11-07):** Preserve the normal SQLite SQL client interface and C API for **supported** queries and mutations. SQL writes on a master are evaluated provisionally and converted to authenticated ledger events; the official `.DLDB` database is changed **only** by the authenticated projector, which operates independently of publication. Replicas reject user SQL mutation attempts. Historical PostgreSQL-only `COPY`, `MERGE` spelling, command tags and `ZL001`/`ZL002`/`ZL003` SQLSTATE conventions in this section document the prior adapter and are **not mandatory SQLite syntax or error fields**. The SQLite SQL subset, precise error mapping, DECIMAL expression semantics and full API interception boundary must be specified and tested; unsupported mutation paths fail safely rather than writing directly. The existing portable effective-transaction and honest partial-publication guarantees still apply.


The signed-ledger model **does not automatically enforce ordinary relational application constraints** such as primary-key uniqueness or foreign-key referential integrity when deriving authoritative changes. Two rows with different row GUIDs may contain identical business primary keys. Ledger deletions are not vetoed by referencing rows or application locks. Internal storage integrity and synchronization cannot be disabled merely to bypass these application-level rules. User-defined triggers, stored procedures, user-defined functions with effects, and comparable user-defined implicit write facilities are **not supported in Version 1**. This excludes their use as alternate mutation paths; it does **not** require removing SQL built-ins or internal database functions necessary for parsing, expression evaluation, data conversion, indexing, recovery, or supported SELECT/DML. The previously discussed PostgreSQL support matrix below is retained only as historical context; the active SQLite SQL subset remains a later Phase 2 native-interception qualification gate. No PostgreSQL-only command or error contract automatically applies to SQLite. Indexes and SELECT/query support may be used for efficient materialization and reads.

**HISTORICAL PostgreSQL-only SQL scope (not the current SQLite support matrix):** The earlier adapter required ordinary `SELECT`, `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `INSERT`, `UPDATE`, and `DELETE`, with `BEGIN`, `COMMIT`, `ROLLBACK`, and savepoints for provisional local staging. **Additional approved entry paths:** `COPY FROM STDIN` (bulk inserts), `COPY TO STDOUT` (read-only export), `MERGE` (its per-row insert/update/delete effects), and `RETURNING` (reports values from locally evaluated changes). Every resulting row change from `COPY` or `MERGE` must publish its own authenticated ledger block **before official materialization**; none may bypass the same authority rules. `RETURNING` reports locally calculated result values, which are **provisional with respect to later block publication and local projection visibility**. The caller may receive `RETURNING` rows before the corresponding signed block is durably published and before the official SELECT-visible projection catches up. This is an accepted application-design responsibility, not a requirement that the engine make RETURNING synchronously visible. `RETURNING` must not be represented as proof that a multi-block COMMIT is atomic or entirely durable, and statement results may precede later publication failures. `COPY FREEZE`, `COPY PROGRAM`, unsupported user-defined triggers, stored procedures, user-defined functions **with side effects**, and other unapproved mutation paths must be rejected or made unavailable rather than allowed to bypass ledger-authoritative changes. PostgreSQL internal built-ins necessary for supported SQL remain available. This is a baseline feature subset, not a promise to preserve unsupported SQL extensions or direct writes. The accompanying PostgreSQL SQL/execution contracts define required MERGE branches, expression/join/CTE forms, lossless type mappings, utility restrictions and result/error conventions; genuinely unspecified advanced SQL forms are identified there, without narrowing the approved command categories.

SQL clients can use provisional transactions. `BEGIN` starts uncommitted isolated changes; `ROLLBACK` and savepoint rollback discard staged work without emitting blocks. No publication occurs before COMMIT. At COMMIT publish final effective provisional row changes (Option A): an existing row changed 1 → 2 → 3 produces one UPDATE_ROW carrying 3; a row restored 1 → 2 → 1 needs no effective row-change block; INSERT then UPDATE produces one final INSERT_ROW; INSERT then DELETE has no surviving row event; UPDATE then DELETE produces one DELETE_ROW. Preserve appropriately qualified provisional RETURNING values and statement counts for the supported SQLite SQL surface; PostgreSQL-specific command-tag rules are historical. Every independently effective changed row still requires its own signed block. DDL must preserve immutable entity identities, valid dependencies and reconstructible final state, without an arbitrary schema-event count or publication order; unpublished DDL folding is permitted rather than a mandated representation.

Publication is **not group-atomic**. If a crash leaves only 60 of 100 intended blocks durably published, those 60 are permanent ledger history; remaining blocks may never exist. The materialized official database is updated only by authenticated ledger ingestion, including at origin, not by the provisional transaction directly. If the origin can determine that COMMIT stopped after publishing only some intended blocks, it must report failure or explicit partial completion accurately, never claim atomic rollback of already durable blocks. Network disconnects may leave the client uncertain; they do not annul independently durable blocks. Resumable publication is optional, not a fundamental ledger requirement. Applications must handle missing/partial outcomes and stronger business atomicity at a higher layer; compensating operations create new blocks and do not erase history.

Ordinary offline master writes do not wait for cross-master acknowledgment. A higher-assurance application may implement independent locks/reservations and require all masters' confirmation, recognizing that such applications can block during partitions and still need a true protocol to prevent simultaneous conflicting reservations.

**HISTORICAL PostgreSQL SQLSTATE outcome mapping (not an active SQLite requirement):** Preserve normal PostgreSQL command tags/affected-row counts for supported SQL, including matched-but-unchanged rows where applicable. A failed partial `COMMIT` must not return ordinary full success. When the origin can determine partial publication, report a distinct SQLSTATE `ZL001`, an explicit partially-published status, and the known durable block count and GUIDs; durable blocks remain ledger history. When the outcome cannot be determined due to connection loss, do not imply rollback; `08007` can be used where the server can report uncertain transaction resolution, otherwise the client must inspect durable ledger history. Previously emitted `RETURNING` values remain locally evaluated provisional information and do not imply publication or immediate SELECT visibility. Application software, not the ledger database, is responsible for business workflows that require immediate read-after-write visibility or all-or-nothing multi-block results. The accompanying execution/management/SQL contracts define PostgreSQL error fields, JSON DETAIL and supported expression/CTE/cast/error conventions. Request resumption remains optional; it is not required as an implicit retry guarantee. Explicit NULL-versus-omission semantics are now specified in Section 6.2. The initial system makes no promise that ordinary SQL semantics imply global transaction finality.

## 10. Materialization priority, durability, and recovery — CONFIRMED

A received valid block must enter persistent ledger storage before altering the official database. Master-originated blocks follow the same rule. Once blocks are durably received, validate and evaluate their currently known historical authorization promptly; materialize only eligible ordinary data/schema blocks, subject to the Owner-approved configurable projection-age delay (§20). During actual local reconciliation/rebuild, pause affected ordinary processing and protect SELECT consistency; prioritizing eligible local projection remains intentional. This never implies certainty that no missing blocks exist on the wider network. A master can operate while other masters are offline, apart from local synchronization needed to apply known blocks.

Crash-safe progress tracking and idempotent replay or reconstruction must ensure a crash between block durability and materialization can be recovered without permanently omitting or double-applying effects. **CONFIRMED 2026-10-22:** Late valid historical blocks and later-revealed earlier authority history must cause the projection to be corrected through safe rollback/replay of affected materialization **or a complete rebuild from authenticated ledger history**; no timestamp-age cutoff may permanently suppress those corrections. Master/replica outage, out-of-order delivery, partitions, and late authority changes may all require selective re-projection. The ledger itself is immutable; the projection is replaceable. Acknowledgment of successful ledger append implies local durable storage; a block lost with all copies is unrecoverable.

**CONFIRMED 2026-10-22 — local read barrier versus remote catch-up:** An ordinary `SELECT` must **not wait merely because peers may still hold unknown blocks**, because network completeness cannot generally be established. A node may serve a consistent, locally materialized but network-stale state until more blocks become known. Once a node undertakes a local projection modification, selective rollback/replay, or full rebuild to incorporate **blocks it already knows**, ordinary `SELECT` operations requiring that projection must wait until the current local reconciliation produces a consistent result; they must not observe an intermediate or partially rebuilt official state. A complete rebuild **must create a persistent diagnostic/error-log entry** explaining why the rebuild was necessary, the affected ledger/database, its outcome, and information sufficient for an operator to investigate. The entry is operational evidence, not an authenticated ledger block. Implementers may choose locking/projection-swap mechanisms, but must not indefinitely block `SELECT` solely to await hypothetical unseen network blocks. **CONFIRMED operational projection reporting:** Expose projection states `ready`, `reconciling`, `rebuilding`, and `failed`. A full rebuild must persistently log ledger GUID, database identity, UTC start/end timestamps, reason, outcome, and error details when unsuccessful. If reconstruction fails, an affected SELECT must return a clear error rather than stale/inconsistent projected data. Under continuous block arrivals, a node must not starve SELECT indefinitely: it may reconcile a finite known batch to a consistent point, admit reads, and then incorporate later blocks. Implementation-specific WAL/cursor/checkpoint details remain free; exposed status must not claim an inconsistent projection is ready. Exact log encoding and error codes belong to operational API documentation. Rollback/replay versus full rebuild is an implementation choice; neither may ignore applicable earlier blocks.

## 11. Peer-to-peer propagation and offline exchange — CONFIRMED behavior and management interface

Every node may receive, verify, store, serve, relay, and export an intact block, regardless of whether it may originate blocks. Block validity is transport-independent. Permit direct peer connections (TCP/QUIC or suitable supported protocols), decentralized peer discovery with configurable bootstraps, BitTorrent-inspired DHT, peer exchange, LAN service discovery, NAT traversal and relaying, HTTP(S), multipeer downloads, and real-time announcements. Nodes normally advertise new validated blocks to peers with resource/bandwidth controls. **No peer discovery or master quorum is necessary for an ordinary local write**.

Combine rapid announcements with periodic cryptographic **inventory reconciliation**, including Merkle-style summaries or equivalent, and comparisons by block ID/hash that do not depend exclusively on timestamps. Export and import must include individual blocks, timestamp ranges, a full ledger, and incremental missing-block batches; large whole-ledger archives can be imported as offline batch jobs, from arbitrary media. The ledger does not require a database to exist; a returning master can catch up through a read-only replica.

**HISTORICAL PostgreSQL-adapter management note (superseded for active SQLite Phase 1 by Management API §§3, 13–14):** Preserve compatible database client communication and provide a documented **`ledgerctl` command-line interface producing machine-readable JSON results** alongside a later SQL engine integration. The interface must permit new-ledger initialization, joining/pinning by ledger GUID and genesis fingerprint, raw signed-block publication/import, exact raw-block retrieval, export of individual or selected/all blocks, peer configuration, and inspection of retained/pending/quarantined/applied/rebuild/synchronization status. Implementations may additionally offer SQL administration functions or other APIs, but must provide the standard test-facing `ledgerctl` surface. The **exact subcommand names, option names, byte inputs/outputs, JSON schemas, errors, and launch/configuration contract** are specified in the accompanying v0.4 management/execution contracts and JSON schemas, rather than inferred by the verifier. Blind verification requires separate owner approval of the exact artifacts. Detailed peer discovery, gossip, retries, routing, transport libraries/protocols and scheduling remain engineering freedoms, provided locally configured peers demonstrably exchange all relevant blocks during offline/local-network testing.

**CURRENT Phase 1 export clarification (ARCH-011):** `block get` returns the **exact original raw signed block bytes** without reserialization. **Every `block export` invocation** creates a Version 1 `DDLB` container, including zero- and one-block selections. A DDLB container uses the **CONFIRMED Version 1 binary framing**: ASCII magic `DDLB` (4 bytes) || version `0x0001` (uint16 big-endian) || block_count (uint64 big-endian) || exactly `block_count` repetitions of (serialized_block_length uint64 big-endian || exact raw signed block bytes), with no extra footer or trailing data. Every batch preserves each full signed block **byte-for-byte**, including all header fields, raw payload, SHA-512 digest and trailing 64-byte Ed25519 signature. The container is merely unsigned transport framing; it does not modify, re-encode, re-sign, replace, aggregate, or vouch for individual block signatures. Export ordering is deterministic canonical order, using the full-block SHA-512 digest as a tie-breaker for disputed same-identity variants; each block remains independently verifiable. Truncated or overlong framing must fail safely. A partially completed import may retain preceding independently validated/durable blocks; a batch is not an all-or-nothing transaction. Ledger block identity is (`ledger_guid`, `block_guid`); a full-block cryptographic digest distinguishes conflicting variants. Exact identical duplicates are idempotent. Different signed bytes with the same identity are **quarantined for diagnosis**, not resolved by first-arrival order. **Historical/future-only:** Opaque storage for unknown future signed versions is not implemented in Phase 1; those imports return `UNSUPPORTED_VERSION`, are not retained, and count as zero opaque blocks. Blocks awaiting missing historical authorization evidence are retained **locally as pending `.XBLK`**, and are never exported or advertised while archived; malformed or inapplicable inputs never mutate official storage. Such cases receive machine-readable statuses. Resource limits remain configurable as defined in Section 5.

**HISTORICAL (PostgreSQL-adapter) management surface, superseded for Phase 1 by Management API §§3, 13–14:** The earlier CLI described an instance selector and operations equivalent to `ledgerctl <instance-selection> init`, `join --ledger-guid <UUID> --genesis-sha512 <HEX>`, `block import --input <file>`, `block export --output <file>`, `block get --id <UUID> --output <file>`, `block publish --input <file>`, `peer add --endpoint <address>`, `peer remove --endpoint <address>`, and `status` using a consistent per-instance selector. The `<instance-selection>` placeholder is engine-specific; `--pgdata <directory>` is an illustrative PostgreSQL adapter spelling rather than a database-independent requirement. Return a single JSON result envelope with fields `ok` (boolean), `data` (object or null), and `error` (object or null); raw signed bytes travel in files, not JSON strings. For this PostgreSQL candidate, stable input/error codes and complete return schemas are integrated in `Distributed_Ledger_Management_API_Specification.draft.md` and its schemas; exact-artifact approval is recorded separately against file hashes. Conflicting authenticated same-identity variants remain quarantined with **no arbitrary manual winner** in Version 1. Peer communications must be bounded and cryptographic authority must never be inferred merely from peer connection. Configured localhost peers must work in the offline test environment; no mandated public DHT/NAT/TLS library or discovery algorithm. TLS is optional for Version 1 deployment rather than a mandatory dependency on a particular library. Defaults are in Section 5.

**Current Phase 1 status vocabulary (ARCH-011; supersedes historical generic statuses):** `retained` = durably retained, authenticated and currently authorized active `.BLK`, **not** projected in Phase 1; `pending` = cryptographically authenticated local `.XBLK` awaiting missing historical authorization evidence; `quarantined` = local `.XBLK` currently unauthorized/inapplicable **or** involved in an authenticated identity dispute; `rejected` = not durably retained following invalid framing, version, identity, signature or event validation. `opaque` is reserved, not emitted in Phase 1; `applied` becomes possible only with the Phase 3 projector, never in Phase 1. Dispute takes classification precedence over pending/unauthorized. `retained_count` is inclusive of active and archived retained signed variants, and `disputed_count` is a subset of `quarantined_count`. Identical bytewise duplicates are idempotent. Exposed counts and errors must use these statuses consistently.

**Flood resistance / inbound validation — CONFIRMED requirement:** Every node must inspect every received block for framing, protocol version, well-formedness, hash/signature integrity, ledger identity, and signer authorization before it has any database effect. A hostile actor may flood arbitrary invalid blocks. Reject invalid inputs safely and limit untrusted resource consumption (including decoding, disk, CPU, memory and networking) without treating plausible timestamps alone as grounds for rejecting otherwise valid authorized blocks. An out-of-order block whose missing authorization evidence has not arrived must not be materialized before its authority is established. Exact inventory, caching and DoS budgets remain implementation choices.

## 12. Intended guarantees and deliberate non-guarantees

**Intended:** Public cryptographic origin/integrity verification, signed historical authorization, deterministic canonical replay on the same accepted history, append-before-apply, one-row-per-block updates, delete-wins identity semantics, eventual convergence for participants that ultimately receive equivalent relevant events, permissionless block redistribution, complete reconstruction from validated genesis and all ledger history, independent progress during network partitions, and crash recovery for durably accepted events.

**Not promised:** Simultaneous SELECT visibility, knowledge of an objectively complete history at an arbitrary instant, automatic rollback of **ledger blocks**, all-or-nothing execution of multi-block SQL transactions, preservation of foreign-key/unique constraints, instant failover without surviving block copies, globally irreversible application business outcomes, and successful application-level strong locking when required masters are unreachable. **Required despite these non-guarantees:** correcting/rebuilding the derived database projection when an earlier valid block changes canonical materialization; retaining history and never suppressing an applicable block simply because it arrived late.

## 13. Acceptance scenarios (conceptual, not hidden verification details)

1. A new ledger initializes a genesis signer; an empty replica adopts the ledger and derives an identical state when fed the same history.
2. A grants B; B grants C; a late invalidation of B's grant invalidates C's dependent authority and relevant projected effects.
3. A signer key has no authority at a block position before its own grant; a later revocation invalidates subsequent blocks, not prior ones.
4. A and B publish independently while disconnected; a replica relays blocks to a disconnected master when peer links permit.
5. A block arrives late with an earlier timestamp; the node corrects affected materialization by selective rollback/replay **or complete rebuild from the validated ledger**, without treating the block as too old to apply.
6. Partial-column updates on the same row preserve separately modified columns; deletion of the row, table, or column GUID wins over modifications.
7. Same-name columns/tables with distinct GUIDs both survive; corrective naming blocks are produced by an authorized master, not by direct projection writes.
8. Duplicate primary-key values across distinct row GUIDs survive in Version 1.
9. `BEGIN`+`ROLLBACK` emits no blocks; partial failure during `COMMIT` can preserve only a published prefix of independently durable row blocks.
10. Crashes between ledger persistence and projection recover idempotently; replicas converge once their accepted block sets and authority histories agree.
11. Unsupported or temporarily uninterpretable blocks produce diagnostics, remain available for dependency recovery, and never silently mutate official storage through a bypass.

## 15. Current SQLite architecture and delivery sequence — OWNER APPROVED

1. **Independent ledger first:** signed protocol **1.01**, exact `.BLK` bytes, independent Ed25519 identity, genesis, historical authorization, CLI, durability and import/export before any SQLite projection.

3. **Projection in Phase 3:** the authenticated projector alone modifies `.DLDB`; SQLite transactional progress is authoritative, `.STAT` regenerable. Full replay initially; delayed projection optional (0-second default), no hypothetical-network wait for SELECT.

## 20. Compact local block names, local-only invalidation and approved projection delay — Owner direction (2026-11-09)

**Approved local filename compacting:** Under each database-basename support directory, use `BLK/YYYY/YYYYMM/YYYYMMDD/` and matching `STAT/YYYY/YYYYMM/YYYYMMDD/`. The standard filename stem is `YYYYMMDD-HHMMSSssss-<block-guid>-<full-block-sha512>`, with `.BLK` or `.STAT` extension. A four-digit fractional field encodes millisecond timestamp as `sss0`; all date/time fields are UTC and zero-padded. This changes *local file organization only*, not the signed-block wire bytes, timestamps, GUIDs, signatures or canonical replay order. Sort inventory filename stems by canonical ASCII order; the sorted inventory is not required to reproduce the order of all signed events in every disputed-variant case. Handle valid signed timestamps outside supported calendar ranges with an explicitly designed non-calendar fallback.

**Owner-directed historical invalidation and local-only archival (2026-11-09):** A block that was once historically authorized may become unauthorized when an earlier signed grant/revocation arrives. Its original signed bytes remain intact and are retained locally. Invalidate/remove its advisory `.STAT` through the sole STAT manager; move/rename the corresponding `.BLK` into the compact `.XBLK` form `YYYYMMDD-HHMMSSssss-<block-guid>-<signer-public-key>.XBLK` (full public key: 64 lowercase hex characters); then reconcile official state by full replay or a future equivalent selective replay. While a file is `.XBLK`, **never announce, push, serve, export or relay it**, and exclude it from peer `TREE.HASH` inventories. Recheck archived `.XBLK` when newly received canonical historical authority changes; if its signer becomes authorized again at its signed block position, verify its bytes, restore its canonical `.BLK` name using SHA-512 of the unchanged full signed bytes, reinstate it in the active inventory, and allow ordinary best-effort push/periodic pull. No archived bytes become official effects until normal authenticated projection has applied them. This is a new owner-directed operational exception to the prior generic serve/relay-all-history language; it does not alter block wire bytes or erase archive history.

**Limits and deliberate tradeoff:** The Owner accepts ignoring the extraordinarily unlikely collision of `.XBLK` filenames for equal timestamp, block GUID and signer; never overwrite existing destination files or discard an incoming signed variant on unexpected conflict. Since `.XBLK` is **local-only and absent from peer inventories**, two nodes can match active inventory roots while privately retaining different archived histories, and temporarily differing authorization knowledge can prevent a peer from obtaining a block until a holder revalidates and restores it to `.BLK`. This is accepted as the simpler Version 1 synchronization policy; it is not a guarantee of complete historical inventory equivalence. The exact peer/cache binary serialization and safe rename/scan/restart transaction mechanics still require implementation review.

**Projection delay — OWNER APPROVED:** A configurable `projection_delay_seconds >= 0`, default **0 seconds**, buffers only ordinary data/schema materialization: signed blocks are received, verified, durably retained, and evaluated for current historical authorization immediately. Relational projection waits until the signed timestamp is at or before local UTC time minus the configured delay, subject to all other dependencies. Report age-deferred work separately. The delay reduces some avoidable replay but creates intentional, consistent local SELECT staleness, is no guarantee of global completeness, and never prevents arbitrarily late blocks from requiring correction. Critically, a newly known earlier revocation may trigger immediate re-evaluation of current signing authority and already projected effects despite the delay. Test using deterministic projection status/checkpoints, not arbitrary sleeps.

## 22. ARCH-011 — Owner-approved Phase 1 authority classification, recovery, countersigning and configuration

**Authority and variant states:** Protocol 1.01 signed block bytes, canonical ordering `(timestamp_utc_ms, block_guid, signer_public_key)`, Ed25519 signatures, the exact 149-byte `DDL-REVOKE-v1` consent message, and DDLB Version 1 framing remain unchanged. A successfully retained **authorized** block has per-item `status="retained"`, `authorization="authorized"`, `reason="AUTHORIZED_RETAINED"`; Phase 1 has no SQLite projector, so this **never** means `applied`. A cryptographically valid block whose historical authority depends on missing evidence is `pending`, stored locally as `.XBLK`; a known unauthorized/inapplicable or authenticated same-identity disputed block is `quarantined`, also stored locally as `.XBLK`. Dispute classification takes priority over authorization state, which is reported separately. Changes to earlier authenticated authority history trigger deterministic reclassification without rewriting signed bytes; only authenticated, authorized, undisputed blocks are restored as active `.BLK` and become eligible for ordinary `block get/export` and later Phase 4 peer exchange. No `.XBLK` is exported, announced, or hashed into the active peer inventory. No-overwrite and original-byte preservation remain mandatory; accepted compact `.XBLK` name collision risk is **not** a new Version 1 blocker.

**Phase 1 counting:** `retained_count` counts unique locally durable, fully authenticated *signed byte variants* distinguished by full-block SHA-512, across active `.BLK` and archived `.XBLK` and including genesis. `pending_count` and `quarantined_count` count disjoint **subsets** of those variants, not projection backlog; `disputed_count` is an additional **subset of quarantined** counting every retained variant involved in an authenticated `(ledger_guid,block_guid)` conflict. `opaque_count=0` in Phase 1 because unknown signed versions are rejected and never retained. Exact duplicates do not increment counts. All counts are consistent snapshots, and late history can reclassify but not silently delete the underlying signed variants. Detailed Phase 1 status and import enums are in Management API §§13.4–13.5 and 14.

**Revocation countersigning:** The approved additional CLI/library interface `master countersign-revocation` signs only the exact 149-byte consent message already specified in §6.3 using the second authorized master's locally held persistent Ed25519 key, never exposing private seed. The bound `ledger_guid` and local `countersigner_public_key` are supplied by verified local identity; caller supplies exact block GUID, signed UTC milliseconds, outer-signer key and revoked target key. Both signers must be distinct and historically authorized at the specified canonical position; the revoked target must be one of them. The raw 64-byte signature is written with no-overwrite durability guarantees; its hex is also available in JSON. `block publish` must reuse the same GUID/time and verify consent; otherwise refuse publication. See Management API §14.3.

**Interrupted initial identity recovery:** When the original `signing-key.v1.json` survived but no manifest or genesis was ever durably created, a deliberately requested `instance recover --from <original-signing-key-path> --confirm-unbound-initialization` can reconstruct only the **original unbound** manifest after verifying the complete signed-key JSON/AES-GCM AAD/seed/public key/instance GUID and absence of contradictory binding/history evidence. This exception to the normal requirement for existing binding evidence does **not** authorize replacing an earlier identity or recovering an actually bound instance as new. Repeated exact recovery is idempotent; partial/crashed recovery remains recoverable. See Management API §14.4.

**Local configuration:** The Owner approved a separate `ABC/instance.config.json` Version 1 for the four already approved Phase 1 operational limits, with missing-file defaults, crash-safe atomic replacement, strict validation and fail-closed corruption diagnostics. Neither identity GUID/public key nor pinned ledger GUID/genesis SHA-512 may be changed by configuration. Details are in Management API §14.5 and SQLite Architecture §20.

**Scope and owners:** All classification and `.XBLK` retention/reconsideration above are **Phase 1 ledger requirements**, independent of SQLite, `.STAT` projection, and peer networking. Developer implements the library/CLI and durable filesystem operations; QA independently creates vectors/fault-injection acceptance tests; PM and Owner review evidence. Native SQL capture, projection/STAT transitions and peer `TREE.HASH` synchronization remain Phases 2–4. An accepted architecture is not a claim of completed implementation or test certification.
