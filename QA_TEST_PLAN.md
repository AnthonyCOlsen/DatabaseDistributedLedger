## 1. Mission, authority and coordination

Verify that authenticated independent `.BLK` events are the only authority for official SQLite `.DLDB` state, and that signatures, historical authorization, deterministic ordering, crash recovery, exact values, and eventual multi-master convergence work as approved. Prefer deterministic automated checks, independent reference calculations, reproducible evidence, and explicit pass/fail/untested counts.

- **Owner** approves requirements, scope, architecture, and exceptions; **PM** coordinates phase handoffs and receives QA reports through Owner.
- **QA** may use Codex to add/modify/delete test scripts and fixtures. QA may make *minimal test-enabling production-code changes* only, notifying the Developer of each such change and rationale. Coordinate concurrent work; production functionality belongs to Developer, design text to Architect-Designer.
- **Test-only fault hooks** are Owner-approved. Add after the Developer hands over the applicable phase, while sharing planned locations in advance; disable in production. Do not create project folders without Owner approval.

Adversarial privileged OS/filesystem compromise is out of initial QA scope; ordinary filesystem durability, identity safety, and data-integrity checks remain in scope.
- Keep unmodified upstream SQLite tests intact. Any fork test exclusions/replacements need exact test IDs, reversible classification, replacement coverage, and PM/Owner approval. ## 2. Architecture invariants QA must protect

1. Signed independent Version 1 blocks remain exact-byte immutable; each block is not hash-linked. Genesis pins ledger GUID plus **full signed genesis SHA-512**.
2. Canonical history order, **amended by Owner 2026-11-09**, is `(signed timestamp UTC ms, raw block GUID, raw signer public key)`, ascending. This supersedes signer-first vectors and can change same-timestamp replay interpretation.
3. Authority comes only from authenticated genesis and canonical `GRANT_MASTER`/two-signature `REVOKE_MASTER`, never mere private-key possession. Late authority changes can invalidate/revalidate earlier applications.
4. `ABC.DLDB` has `ABC/ABC.DLID`, `ABC/instance.identity.json`, `ABC/signing-key.v1.json`, `ABC/BLK/`, `ABC/STAT/`, and possibly retired `ABC/DELn/`; **no nested GUID directory**. Identity and pinned ledger/genesis survive projection deletion/rebuild.
5. SEC-002: every instance (including replica) has its own persisted Ed25519 identity. Owner-approved strict key JSON uses 32-byte seed, AES-256-GCM, 12-byte fresh nonce, 16-byte tag, publicly embedded versioned wrap key, and **88-byte AAD**. This is **obfuscation, not secrecy against a file-holder**.
6. Under ARCH-003, **missing/corrupt/mismatched existing identity pauses ALL routine SQL and ledger activity**, including SELECT, import/export, relay and replay; only diagnostics/status/explicit original-identity recovery remain. Never silently regenerate or rebind.
7. A durable acknowledged `.BLK` precedes any official projection effect; only the authenticated projector modifies official `.DLDB`. `.STAT` and `TREE.HASH` are rebuildable/advisory, not authority. Progress and official SQLite effects commit together.
8. Full replay rotates `STAT/` to next free `DELn/` under the exclusive STAT manager while processing is paused; an external blocking lock prevents replay and is diagnosed/retried; safe retired `DELn/` cleanup is asynchronous.
9. Historically invalidated `.BLK` may be renamed to local `.XBLK` **without modifying its bytes**; `.XBLK` is excluded from `TREE.HASH`, announcements, ordinary export, serving, and relay. After historical reauthorization it may return to canonical `.BLK` and reenter inventory/propagation. This is **intentional**, not an unresolved defect. Matching active inventories do **not** imply identical local archives.
10. `projection_delay_seconds` is nonnegative, default **0**, and delays only ordinary row/schema projection by signed timestamp/UTC cutoff, not verification, durable retention, or current authorization. SELECT may be locally stale yet consistent. Delay is not finality.
11. Exact DECIMAL uses arbitrary-precision integer coefficient/scale with canonical normalization. Supported SQL arithmetic/compare/sort/round-trips must not silently pass through approximate SQLite REAL or fixed .NET decimal. Unsupported non-exact operations fail explicitly.

## 4. QA-002: deterministic `.XBLK` state-transition scenario

Reference-model fixture (times are illustrative signed timestamps, not runtime clock waits):

1. Genesis authorizes A. An applicable event grants B at `t=100`.
2. B publishes a data event at `t=300`, initially applicable and projected.
3. Import a **valid two-distinct-authorized-signature** revocation of B at `t=200`, delivered late. Recompute authority in `(timestamp, block GUID, signer)` order. B's data event becomes inapplicable; assert `.BLK → .XBLK` with identical SHA-512 of raw bytes, STAT invalidation, official projection correction, absence from active inventory/export/relay.
4. Import A's valid grant of B at `t=250`, delivered later. After full canonical re-evaluation, B's `t=300` event is once again applicable; assert verified `.XBLK → .BLK`, restored SHA-512 filename, STAT/projection correctness and (Phase 4) restored propagation.
5. Repeat interrupted transitions, restart, duplicate import, and full reconstruction. Assert final **logical state**, not byte-for-byte equality of SQLite projection files. Compare against an independent QA reference order/model; don't use the candidate's own statuses as sole oracle.

**Important:** Test temporary differences in active advertised `.BLK` sets separately from permanently excluded local `.XBLK`; the design explicitly accepts non-equivalence of private historical archives.

## 5. Owner-approved deterministic fault-hook plan

Add minimal, test-only, production-disabled checkpoints **after each phase handoff** and notify Developer of all changes outside test scripts. Prefer an explicit barrier handshake / externally observable state and bounded status polling over arbitrary sleeps. Recommended hook locations:

- **Phase 1:** before/after key-file, identity-manifest and `.DLID` durable publication; before/after `.BLK` rename/durable acknowledgment.
- **Phase 2:** after SQL provisional evaluation, before/after each block durability/partial COMMIT, before any official projector (which is absent in Phase 2).
- **Phase 3:** before/after SQLite projection+checkpoint transaction, STAT manager invalidation, `STAT → DELn`, `.BLK ↔ .XBLK` rename, `TREE.HASH` cache invalidation if implemented, read admission and replay completion.
- **Phase 4:** before/after active-inventory generation/announcement, peer send/receive, reconnect/missing-set reconciliation.

Each injected process crash is followed by independent file/hash and logical-state checks. Never claim a `STAT` marker or a cache hash proves a block was applied.

## 7. Evidence and defect-report convention

For each executed test record: test ID, commit SHA and working-tree state; OS/filesystem/native SQLite version; test command and fixture SHA-256; environment and antivirus state if relevant; fault checkpoint and exit behavior; expected independent oracle; observed result; pass/fail; logs/file SHA-512 and replay/checkpoint evidence; severity, reproduction and Developer notification; rerun result. Never relabel a partial/inconclusive result as PASS.

Severity guidance: **P0/blocker** = unauthorized official effect, lost acknowledged block, wrong signature/authority handling, unrepairable projection or proven convergence failure; **P1** = serious durability/availability/status/interface defect without demonstrated core-history violation; **P2** = noncritical diagnostics/usability. Final severity depends on actual evidence and impact.
